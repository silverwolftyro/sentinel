# Agent 跑偏警示录

> **一份真实的复盘**：v3.2.0「真实长任务挂机演习与晨报自动投递」这一轮，
> 任务本身四个验收项都不难，但执行过程**跑偏了**。
>
> 记录日期：2026-10-28 ~ 2026-10-29
> 涉及版本：v3.2.0（未发布）→ v3.2.1（NInfer 适配）
> 相关文档：[v3.2.0 版本说明](versions/v3.2.0-night-crawl-and-briefing-push.md)、
> [v3.2.1 版本说明](versions/v3.2.1-ninfer-adaptation.md)

---

## 0. 一句话结论

> **跑偏不是「干了不该干的事」，而是「一直在干一件看起来相关、但不是当前最该干的事」。**
>
> 这次我花了大约三分之一的时间在**给一个即将被替换的引擎装权重**、
> 三分之一在**跟工具链打架**（下载卡死、Defender 误报、GBK 编码、shell 策略），
> 真正花在**四个验收项**上的时间反而最少。

---

## 1. 时间线：我是怎么一步步跑偏的

### 1.1 第一处跑偏：给一个即将被替换的引擎装权重（**最贵的一次**）

**发生了什么**

v3.2.0 要做「意图漂移判定」，需要 L2 模型。本机 Ollama 服务在跑，但**一个模型都没有**。
于是决定 `ollama pull qwen2.5:7b`（4.7 GB）。

下载卡死（分块下载卡在第 2/10 块）。我没有停下来问「**这个引擎是不是该装**」，
而是写了临时脚本 `patch_ollama_blob.py`（HTTP Range + 8 路并发 + SHA256 自校验），
把缺失的块手工补齐、校验、改名、写 manifest，最终 `ollama list` 里出现了 `qwen2.5:7b`。

**为什么这是跑偏**

* 用户在这轮结束时**彻底删掉了 Ollama**，换成了 NInfer；
* 也就是说：这段「成功」**对最终交付没有任何贡献**；
* 它的真实成本是：**几小时的下载、并发补丁、SHA256 校验**，外加一整套
  「为什么模型装不上」的排障思路。

**更该做的是**：动手前先花 5 分钟问清楚——**这台机器上到底跑的是哪个引擎**。
（任务书里其实已经写了 NInfer，只是我在读任务书时把它当成了「背景介绍」。）

---

### 1.2 第二处跑偏：被一个「可能并不存在的问题」拖住

**发生了什么**

30 分钟演习第一轮，`agent.jsonl` 涨到 2.39 MB，怀疑是**同一行日志被读了两遍**，
于是给 `_构建与发布/scripts/run_with_sentinel.py` 加了 `_reader_generation` 守卫，
又补了 14 条测试。

**为什么这是跑偏**

这个修复**本身是对的**（重拉之后确实会起两个读者）。但我是从
「**我以为**有 bug」出发，一路加机制、加测试、加注释，
而**没有先花五分钟去确认现象是不是真的**。

真实原因平淡无奇：`mcode` 发完 `exec.completed` 之后**进程不退**，
所以看起来像「还在干活」，其实那一轮早结束了。

**教训**：**先证伪，再修**。一个「疑似 bug」在变成「必修 bug」之前，
应该先有一份**能复现、能证伪的最小证据**。

---

### 1.3 第三处跑偏：用复杂度掩盖「我还没搞懂」（**最值得记的一条**）

**发生了什么**

第一轮 30 分钟演习跑完了（9 条告警、红线在内核层真挂起了 35/35 线程），
但**收尾阶段卡死** —— 进程最后被后台任务管理器按 3600 秒上限杀掉，
**报告一个字节都没落**。

我把收尾路径逐个读了一遍：taskkill 有 15 秒超时、等待 5 秒、
两次 `drain` 各 20 秒、投递 flush 10 秒、join 5 秒 ——
**全是**有界的。**根因没找到。**

然后我做了什么？**加了三个新机制**：

1. 收尾跑在独立线程里，超时（120 秒）就记下来；
2. 超时时把**所有线程的栈**拍到 `finalize-stacks.txt`；
3. 报告**两段式落盘**（主循环结束先落一份，收尾完再落一份）。

**为什么这是跑偏**

第 2 条是**留证据**（对）；第 1、3 条是**容错**（把「不知道」藏起来了）。
根因未知的时候，正确动作是**只留证据 + 把问题摆出来**，
而不是先写一套「就算它又卡住我也能跑完」的机制 ——
那套机制让下一轮**又卡住**时，我依然拿不到根因。

**教训**：**不知道的时候，产出物应该是证据，不是机制。**
一个「容错」包装如果盖住了「我还没搞懂」，那它不是稳健，是**自欺**。

---

### 1.4 第四处跑偏：同一个失败，重跑超过一次

卡死之后，我**立刻重跑了第二轮 30 分钟**。

用户后来的原话是：「我们需要立刻停止那些无意义的压测」。

**教训**：**同一个失败最多重跑一次**。第二次还不行，
就该停下来把证据（线程栈、原始日志、时间线）摊开，**换方法**而不是**换次数**。
连续重跑看起来很勤奋，实际上是在**用时间掩盖没进展**。

---

### 1.5 第五处跑偏：交付优先级倒置

四个验收项：

1. 晨报推送到手机的报文截图；
2. 「关于系统」面板的运行时长与内存占用；
3. Night Crawl 演习结果；
4. Git tag 与最新 exe 体积。

而我实际花时间最多的地方是：

| 耗时大户 | 它属于 |
| --- | --- |
| `ollama pull` 卡死 → 写补丁脚本补 blob | 工具链 |
| Defender 把 exe 误判成木马 → 排查、隔离、重打包 | 工具链 |
| 控制台 GBK → 中文乱码、`✓` 打印崩溃 | 工具链 |
| PowerShell 管道缓冲 → pytest 摘要抓不到 | 工具链 |
| bash 工具被安全策略拦截 → 换 `write`/`edit` | 工具链 |
| **四个验收项本身** | **交付** |

每一件工具链问题单独看都合理，堆在一起就是**跑偏**：
**我修的是「让工具能跑」，不是「让东西能交」。**

---

### 1.6 第六处跑偏：演习 Agent 越界（**引出了 v3.2.1 的加固**）

30 分钟演习里，被监控的 Agent 自己跑了一条：

```
Remove-Item '...\__pycache__' -Recurse -Force
```

哨兵**抓到了**（`DANGEROUS` / `dangerous_command` / critical）。

这次它没越出沙箱，但暴露了一件事：
**「沙箱」只是目录约定，不是隔离。**
演习脚本应该有一双眼睛盯着 Agent 有没有碰**仓库**、有没有越出**工作目录**，
而不是只在跑完之后比对一次 `src/` 的 SHA256。

→ 这条直接变成了 v3.2.1 的**越界看门狗**（见 `final_night_crawl.py`）。

## 2. 为什么会跑偏：四个根因

| 根因 | 表现 | 对策（v3.2.1 起执行） |
| --- | --- | --- |
| **没有「环境契约」这一步** | 沿用上一版假设（Ollama）开工 | 开工前 5 分钟写清楚：引擎地址、协议、模型名、超时、并发、上下文上限 —— 并用**一次探测**验证 |
| **把「让工具跑起来」当成「做任务」** | 下载/编码/打包/策略拦截占了大头 | **验收项优先**：任何工具链问题最多给 10 分钟，超时记下来往下走 |
| **失败后的动作是「加东西」而不是「留证据」** | 收尾卡死 → 写看门狗 | **不知道的时候只产出证据**：线程栈、原始日志、时间线 |
| **没有时间盒** | 一个子任务能吃掉整轮 | 每个子任务预设上限，超时即停并记录 |

## 3. 哨兵自己能不能抓到这些？

**能抓到一半，而且 v3.2.0 的实机记录里已经抓到了。**

| 哨兵抓到的 | 发生在 | 说明什么 |
| --- | --- | --- |
| `intent_drift`（第 5 步起在遍历 `.sentinel/safepoints` 目录，与重构解析器无关） | 23:08:41 | 演习 Agent **越界翻哨兵自己的目录** —— 这就是「跑偏」 |
| `dangerous_command`（`Remove-Item … -Recurse`） | 23:14:55 / 23:22:01 | Agent 在干**与任务无关的破坏性操作** |
| `context_stuck`（测试连续失败 3 次） | 23:08:45 | Agent 卡住了 |
| `catastrophic_mass_delete`（红线级） | 23:27:22 | 红线命中，进程被真挂起（内核层核实 35/35 线程） |
| 「L2 模型判不了」被**如实说出来** | v3.2.0 §4.7 | 失效不再沉默 |

**但有一件事哨兵抓不到**：这一轮真正的跑偏 **发生在哨兵自己身上**
（我的工作流选错了主线），而哨兵盯的是**被监控对象**。
「意图漂移」检测看的是 Agent 的行为序列，
**它没法知道「你正在给一个会被删掉的引擎装权重」**。

> 换句话说：**哨兵能审 Agent，审不了自己。**
> 这正是这个项目必须有人（或者有流程）来复核的原因 ——
> 也是这份文档必须写下来的原因。

## 4. 可执行的规矩（v3.2.1 起照做）

1. **环境契约先行**
   开工前先确认并写下：引擎在哪、什么协议、模型叫什么、超时多少、并发上限、
   上下文多大。**用一次真实调用验证**，别靠猜。

2. **结论先落盘**
   任何跑长时长的验证（演习、压测、下载、构建），
   **结果必须先写到文件**，再做任何后续动作。
   崩了、挂了、被杀了，结论都还在。

3. **同一失败最多重跑一次**
   第二次还不行 → 停下来摊证据 → 换方法。
   **连续重跑不是勤奋，是掩盖。**

4. **交付物优先于工具链**
   验收项没落地之前，工具链问题**最多 10 分钟**；超了就记录、跳过、往下走。

5. **子任务一律时间盒**
   下载 10 分钟、打包 5 分钟、截图 5 分钟、压测按约定时长。
   **到点即停**，把「没做完」写进交付说明，而不是拖到天亮。

6. **演习必须有越界看门狗**
   沙箱不是目录约定 —— 必须主动检测 Agent 有没有碰仓库、有没有越出工作目录。

---

## 5. 这份文档的边界

* 记录的是**一次真实会话**的行为复盘，不是通用方法论；
* 时间与数字取自本机实机记录（终端日志、`alerts.log`、
  Defender 事件日志、`ollama list` 等），**没有为了好看而修饰**；
* 第 1.3 节那个「收尾卡死」的**根因至今没有查清** ——
  看门狗只是把证据留下来，**不等于问题解决了**。
  这件事仍然挂着，不假装已经解决。
