# v3.8.1 · 优先级队列验收报告

> **主题**：单并发模型上的级联队列与优先级抢占引擎
> **交付物**：`src/core/priority_queue.py` + `tests/test_priority_queue.py`
> **日期**：2026-10-31
> **性质**：新增模块，**未改动任何现有业务路由**

---

## 一、为什么要做这件事

本机 NInfer 是 **单并发** 引擎（`max-concurrency=1`）——
同时发两个请求，引擎**直接崩**（v3.2.1 实机记录）。
所以哨兵从一开始就用 `engine_lock_for()` 在**客户端**把请求排成队。

但那把锁是 **FIFO**，也就是**先到先得**：

```
P2 ── P2 ── P2 ── P2 ── ██ P0 ██ ── P2 ── P2
                  ↑
        红线事件在这里干等前面所有日常任务跑完
```

单并发引擎上一次判定要好几秒。十个日常摘要 = 几十秒。
**最该被立刻看见的红线，反而成了最晚被看见的** —— 这与哨兵存在的意义正好相反。

本报告量化这一差距，并给出修复。

## 二、实现要点

| 档位 | 含义 | 规则 |
|---|---|---|
| **P0** | L1 命中的**红线**事件（`rm -rf`、整盘格式化…） | 插队到**队首**，永不让路 |
| **P1** | 连续 `DRIFT` 漂移判定、非红线的危险判定 | 排在 P2 之前 |
| **P2** | 日常 `ON_TRACK` 摘要提取 / 人话解释 | 谁都不抢 |

四条硬约束：

1. **P0 绝不被普通事件阻塞** —— 哪怕队里压着一百个 P2。
2. **不浪费任何一次请求** —— 被丢弃的 P2 也要**交出降级结果**，
   被抢占的任务必须**如实标记**，绝不能悄悄消失。
3. **抢占必须留痕** —— 抢占掉的是**一次模型调用**，每一次都计数、都有原因。
4. **绝不抛异常** —— 任务失败、回调失败、取消失败，一律降级。

### 抢占的两级台阶

Python **杀不掉线程**，所以抢占分两级：

| 台阶 | 机制 | 结果状态 |
|---|---|---|
| 先礼 | 给任务发 `CancelToken`，它自己轮询后抛 `TaskCancelled` | `cancelled` |
| 后兵 | 等过 `cancel_grace_seconds`（默认 0.5s）后**强制放弃** | `preempted` |

触发条件**两个都要满足**：
① 有**更高档位**在排队（没人等，抢它没意义）；
② 它自己已经跑了**超过 10 秒**（`preempt_after_seconds`）。

### 背压与熔断

- 队列里待处理任务数达到 **10** 时，新来的 **P2 直接丢弃**并返回降级结果；
- **P0 / P1 永不因背压被丢** —— 宁可排队也不能把红线弄丢；
- 队列**清空**后后台线程**自动退出**，线程与内存**全部释放**。

### 刻意不做「老化提升」

持续高压下 P2 会被背压丢弃 —— 但每一次丢弃都有据可查。
**不让等了太久的 P2 反超 P0**：「高危事件绝对不被普通事件阻塞」是第一原则。

## 三、并发模拟结果

### 3.1 场景

- **3 个 Agent 线程**同时狂发，共 **100 个 P2**；
- **1 个红线线程**在 P2 提交到 `10 / 30 / 50 / 70 / 90` 处各插一条 **P0**（共 5 条）；
- 单次「模型调用」耗时约 **6 ms**（真实引擎上以秒计，等比缩小）；
- 队列容量 `max_pending=10`，抢占阈值 `preempt_after_seconds=10`。

### 3.2 关键指标 —— **P0 平均等待延迟**

连续跑 3 次，结果稳定：

| 指标 | 第 1 次 | 第 2 次 | 第 3 次 |
|---|---|---|---|
| **P0 平均等待延迟** | **4 ms** | **2 ms** | **3 ms** |
| P0 最久等待 | 6 ms | 4 ms | 6 ms |
| P0 最快等待 | 2 ms | 0 ms | 0 ms |
| P2 平均等待延迟 | 8 ms | 8 ms | 8 ms |
| 总耗时 | 119 ms | 120 ms | 119 ms |

> **P0 平均等待延迟 = 2 ~ 4 ms**（最久 6 ms）
> —— 与**一次模型调用**同量级。P0 最多只等「正在跑的那一个」。

### 3.3 对照实验 —— 同一份负载，普通 FIFO 会堵成什么样

| 队列 | P0 平均等待 | P0 最久等待 |
|---|---|---|
| **优先级队列**（本方案） | **3 ~ 4 ms** | 6 ms |
| **普通 FIFO**（今天的做法） | **437 ~ 440 ms** | 626 ~ 629 ms |
| **改善倍数** | **109× ~ 146×** | **104×** |

**结论**：同一份负载下，红线事件的等待延迟从 **~440 ms** 降到 **~3 ms**，
改善 **两个数量级**。

### 3.4 账目（105 次投递，一笔不丢）

| 项 | 数量 |
|---|---|
| 投递 | 105 |
| 收下 | 18 |
| **丢弃（背压，均带降级结果）** | 87 |
| 完成 | 18 |
| 抢占 | 0 |
| 失败 | 0 |
| **拿到结论的投递** | **105 / 105** |

> 87 次丢弃是**背压按设计生效**（队列上限 10）。
> 关键在于：**每一次投递都拿到了结论** —— 要么跑完，要么明确降级，
> **没有一笔静默消失**（测试断言 `len(outcomes) == 105`）。

## 五、本轮**没有**做的事（明确留白）

1. **没有接线到业务路由。**
   `src/core/priority_queue.py` 是一个**零依赖叶子模块**，
   本轮**刻意不接线**到 `SentinelEngine` —— 接线属于另一次改动，
   且必须一并改掉 `engine_lock_for()` 那把 FIFO 锁的排队顺序
   （否则两套排队叠在一起，反而更乱）。

2. **没有改动任何现有业务路由。**
   `src/llm/router.py`、`src/llm/cascade.py`、`src/core/engine.py`
   **一个字节都没动**。

3. **没有动配置与部署。**

### 接线时必须注意的三件事

1. `engine_lock_for()` 是**按 `base_url` 分组**的串行锁 ——
   优先级队列应当**插在锁的里面**（先排队，再抢锁），
   否则「排队」与「抢锁」两层等待会叠加。
2. 被**强制放弃**的线程在后台仍会跑完那一次 HTTP 请求 ——
   物理上它**还占着引擎**。所以 `preempt_after_seconds` 定 10 秒是有道理的：
   给它足够长的时间自己收手，别动不动就抢。
3. 抢占**会丢掉一次模型调用** —— 这在计费上是真实成本，
   所以 `preempted` 必须**记账**（已实现），别让它悄悄消失。

## 七、已知限制（如实记录）

| 限制 | 说明 |
|---|---|
| **Python 杀不掉线程** | 被强制抢占的任务，其后台线程仍会跑完那一次请求；它的返回值**绝不会被当成结论**（已用 `preempted` 状态标记并在 `stats()["abandoned"]` 计数） |
| **P2 会被饿死** | 持续高压下 P2 会被背压丢弃（这是**设计**，不是 bug：丢弃有降级结果、有计数） |
| **档位判定是启发式** | 依赖 L1 判定字典的 `severity` / `verdict` 字段；字段改名会失效（已有一致性守卫测试盯着） |
| **对照实验按比例缩小** | 模拟里一次「模型调用」是 6 ms，真实引擎是数秒；**倍数关系可外推，绝对值不可外推** |
| **未接线** | 本模块当前**不参与**实际审查链路；线上行为**尚未改变** |
