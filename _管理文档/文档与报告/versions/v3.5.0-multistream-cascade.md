# v3.5.0 —— 多流隔离 · L2 极速缓存 · 级联审核

> v3.4.0 把托盘化、卸载、雷达排除这些体验坑填平了，
> 但内核还剩一个最疼的：**并发日志混杂**。
>
> 多个 Agent 并行时，它们往**同一个**日志文件里写，
> 哨兵读到的是一条**交织**的流：
>
> .. code-block:: text
>
>     {"type":"tool_call","thread_id":"A", ... "ls"}
>     {"type":"tool_call","thread_id":"B", ... "rm -rf /"}
>     {"type":"tool_call","thread_id":"A", ... "read a.py"}
>
> 共享一个滑动窗口的话，「A 读了 a.py」和「B 要删库」
> 被当成**同一个 Agent 的连续行为** —— 这就是「串台」。
>
> 这一版做五组事：
>
> 1. **任务一：日志流按线程指纹强制隔离**（防串台）——
>    适配器提取 `thread_id` / `session_id` / 工作目录路径特征；
>    引擎维护 `Dict[str, IntentTracker]`，各路互不干扰；
>    看板把同一份日志拆成多个**虚拟会话卡片**；
> 2. **任务二：NInfer (L2) 极速与缓存优化** ——
>    剥离易变内容、静态前缀前置吃满 Prefix Cache、
>    关闭思考、10 秒超时、429/503/超时立刻回退 L1；
> 3. **任务三：滑动窗口与后台滚动摘要** ——
>    短期 3-5 步（原子对不可拆），长期满 10 条后台异步摘要；
> 4. **任务四：级联模型路由 L1 → L2 → L3** ——
>    L2 判正常静默丢弃（省云端算力），L2 报警才叫 L3，
>    **双盲**才亮红灯；
> 5. **任务五：更新 GUI 与发布** ——
>    设置页分「L2 本地 / L3 云端」两个区，
>    看板顶部加节省计数器。
>
> ⚠️ **红线一字未改** —— R1–R9 与 v2.1.0 **完全一致**。
> 退出时依然**只结束哨兵自己拉起的子进程**；
> 雷达挂载进来的用户进程**绝不**去杀（R6）。
> 哨兵依然只读，不碰别人的进程，不自动接管任何东西。

## 1. 红线：这一版一个字都没改

| 红线 | 这一版怎么守的 |
| --- | --- |
| R1 只读监听 | 被监控的 Agent 日志**一个字节都没动**；这一版只新增了「读日志内容算指纹」 |
| R2 不干预代码 | 新增的全是**内存状态**、**界面元素**与**配置项**，不含任何写文件的动作 |
| R3 不注入进程 | 多路隔离与级联审核**都不给任何进程发信号** |
| R4 本地闭环 | 指纹、记忆、摘要全在本机；**只有用户自己配了 L3 云端**，被审查内容才会出本机 |
| R5 旁路失败 | L2 超时/429/503 → **立刻回退 L1 原始判定**；摘要失败 → **历史一条不丢**；级联没装 → 行为与 v3.4.0 一字不差 |
| R6 不终止进程 | 这一版**没有任何**杀进程的逻辑；退出时的边界与 v3.4.0 完全一致 |
| R7 不悄悄改系统设置 | 新增的全是配置文件里的 `llm.cascade` 段与 `memory` 段，用户不填就完全不生效 |
| R8–R9 | 与 v2.1.0 一致 |

⚠️ 特别说明两条容易紧张的：

- **「双盲亮红灯」是收紧，不是放松** ——
  只有 L2 与 L3 **同时**判定有问题才会发最高级 Webhook。
  凑不齐双盲（只有一边、或者模型不可用）**一律不升级**：
  宁可漏报也不要误报最高级警报（本地小模型误报是家常便饭）。
- **「L2 不可用就回退 L1」不是降级凑合** ——
  L1 正则判定本来就一直在跑，它才是第一道防线。
  L2 只是**加**了一道过滤，不是**换**掉了 L1。

## 2. 任务一：日志流按线程指纹强制隔离

### 2.1 问题出在哪

多个 Agent 并行时，它们可能往**同一个**日志文件里写。
于是哨兵读到的是一条**交织**的流：

.. code-block:: text

    {"type":"tool_call","thread_id":"A","tool_call":{"name":"Bash","arguments":{"command":"ls"}}}
    {"type":"tool_call","thread_id":"B","tool_call":{"name":"Bash","arguments":{"command":"rm -rf /"}}}
    {"type":"tool_call","thread_id":"A","tool_call":{"name":"Read","arguments":{"file_path":"a.py"}}}

如果不加区分，这三行进的是**同一个**滑动窗口 ——
于是「A 读了 a.py」和「B 删库」被当成**同一个 Agent 的连续行为**。
漂移检测于是把 A 的正常动作判成「突然要删库」，用户收到一条莫名其妙的告警。

这就是「串台」。

### 2.2 指纹从哪来

新模块 [`src/adapters/fingerprint.py`](../../../src/adapters/fingerprint.py)：

| 优先级 | 来源 | 键名 |
| --- | --- | --- |
| 1 | **线程 ID** | `thread_id` / `threadId` / `thread` / `conversation_id` / `conversationId` / `conversation` |
| 2 | **会话 ID** | `session_id` / `sessionId` / `session` |
| 3 | **工作目录** | `cwd` / `working_directory` / `workingDirectory` / `workdir` / `project_dir` / `projectDir` / `root_path` / `rootPath` |

- 支持最多 **2 层**嵌套探测（`_MAX_DEPTH = 2`）——
  覆盖「顶层 → item → thread」这种常见嵌套；
- `normalize_path()` 做三件事：反斜杠换正斜杠、去尾斜杠、转小写；
- `fingerprint_label()` 把指纹渲染成人话（「工作区 N.E.K.O」）；
- `fingerprint_stream_key()` 把空指纹归到 `default`。

### 2.3 一条**刻意的克制**：认不出就不认

指纹提取不出来时返回**空串**，调用方据此把所有认不出的事件
归到「默认那一路」—— 和 v3.4.0 之前的行为**完全一样**。

⚠️ **为什么不拿「工具参数里的文件路径」当指纹？**

因为那会把**同一个 Agent** 拆成一堆碎片
（读 `D:\项目\N.E.K.O\src\a.py` 得出 `…\src`，
读 `…\tests\b.py` 得出 `…\tests` ——
同一条线程被切成两个「路」，隔离反而把上下文打碎了）。

**宁可不合，也不要错拆。**

### 2.4 引擎怎么分路

[`src/core/engine.py`](../../../src/core/engine.py) 里：

| 成员 | 作用 |
| --- | --- |
| `_intent_trackers: Dict[str, IntentTracker]` | 每个指纹一路追踪器 |
| `_tracker_lock` | 保护上面那张表 |
| `_memories: Dict[str, Any]` | 每个指纹一路记忆 |
| `IntentTracker.sibling()` | 造一个**同配置**的新追踪器 |
| `_tracker_for(event)` | 按指纹取/建追踪器 |

⚠️ `sibling()` **不用 `copy.deepcopy`** ——
追踪器持有队列、事件与线程，深拷贝会把**线程**也拷一份
（更糟的是拷出一个**死锁**的锁）。它显式重建：**只带配置，不带状态**。

目标也是**按路锚定**的：A 路的目标不会盖到 B 路头上。

### 2.5 看板怎么拆

- `AlertStore.streams()` 按指纹把告警与流水分组，返回
  `[{"key", "label", "alerts", "ontrack", "last_seen"}]`；
- 左侧会话卡片下面挂出**虚拟会话卡片**（`.session-stream`）；
- 点一张卡片 → 右侧的告警与实时审核流水**只显示那一路**；
- 顶栏出现一个「只看：xxx」按钮，点一下恢复显示全部。

## 3. 任务二：NInfer (L2) 极速与缓存优化

### 3.1 为什么要剥

本地小模型（NInfer）跑在 12G 显存的物理极限上，
**每一次 Prompt 都要重新算**。

而 Prefix Cache 的原理很简单：**前缀完全相同 → 直接复用**。
所以只要 Prompt 里混进一个会变的东西，整段前缀的缓存就**全部作废**。

| 内容 | 例子 | 为什么它毁缓存 |
| --- | --- | --- |
| 时间戳 | `2026-10-29 23:41:05` | 每次请求都不一样 |
| 尾部行号 | `[TAIL] #123` | 每读一行就变一次 |
| 随机 UUID | `01a17af0-3b2c-…` | 天生每次都不同 |
| 长随机十六进制 | `a3f9c2…`（32 位以上） | 同上 |
| Epoch 毫秒 | `1793294465000` | 同上 |

### 3.2 怎么剥

新模块 [`src/llm/normalize.py`](../../../src/llm/normalize.py)：

- `strip_volatile(text)` —— 把会变的内容换成**固定占位符**：
  `<时间戳>` / `<UUID>` / `<随机ID>` / `[TAIL]`；
- `volatile_fingerprint(text)` —— 归一化之后的哈希，**测试**里断言
  「两次请求的静态前缀完全一致」；
- `build_static_prefix(system_prompt, goal=, facts=)` ——
  拼出「静态系统提示 + 事实卡片」这一整段。

三条纪律：

1. **只动送给模型的 Prompt**，**不动**告警载荷 ——
   证据链里必须留原文，时间戳与 UUID 是排障的关键；
2. **占位符是固定字符串** —— 同样的输入永远得到同样的输出；
3. **只剥「纯易变」的东西** —— 文件路径、命令、工具名**一个字都不动**。

### 3.3 前缀怎么排

.. code-block:: text

    ┌──────────────────────────────┐  ← 静态部分：逐字不变 → 命中缓存
    │ System Prompt（模块级常量）    │
    │ + 事实卡片（本次会话内不变）   │
    ├──────────────────────────────┤  ← 易变部分：每次都不同
    │ User Prompt（最近窗口 + 本步） │
    └──────────────────────────────┘

`build_static_prefix()` 把事实卡片**按键名排序** ——
dict 的插入顺序不保证，排序之后同样的事实永远得到同样的字节。

### 3.4 请求体

`src/llm/api_client.py` 新增 `reasoning_effort` 与 `timeout_floor`：

```json
{
  "model": "bonsai2-27b",
  "stream": false,
  "temperature": 0,
  "max_tokens": 256,
  "response_format": {"type": "json_object"},
  "reasoning_effort": "none",
  "messages": [...]
}
```

⚠️ **为什么必须显式设 `timeout_floor`** ——
客户端对本机引擎有 **600 秒**的下限（那是给 27B 思考模型留的时间）。
L2 是「极速过滤」，那条下限太长，会把单并发队列直接堵死。
所以 L2 必须显式把下限压到 **10 秒**。

⚠️ **网关不认这两个字段怎么办** ——
400 时 `_drop_unsupported_fields()` 摘掉不认的那个再试一次，
**而且记住**（以后都不发了），省一次注定失败的往返。

### 3.5 超时降级与熔断

| 情况 | 哨兵怎么做 |
| --- | --- |
| L2 超时（>10 秒） | 立刻返回 `{"status":"unavailable"}`，**回退 L1 原始判定** |
| L2 收到 429 / 503 | 同上 |
| L2 连续失败 N 次 | 熔断（默认 3 次），之后**不再调用** L2 |
| L3 不可用 | 只记「单边判定」，**不亮红灯** |

`CascadeVerdict.payload` 就是这个契约的可序列化形态：

```json
{"status": "unavailable", "reason": "HTTP 429：触发限流（稍后重试）", "transient": true}
```

## 4. 任务三：滑动窗口与后台滚动摘要

新模块 [`src/core/memory.py`](../../../src/core/memory.py)（**只用标准库**）。

### 4.1 短期记忆：原子对不可拆

窗口以「**步**」为单位，而「一步」是「一个调用连同它的回执」：

.. code-block:: text

    第1步 [Bash] rm -rf build → deleted 3 files

如果窗口在中间截断，模型看到的就是：

- 只有 `rm -rf build`，没有回执 → 误判成「命令失败了，Agent 在重试」；
- 只有 `deleted 3 files`，没有命令 → 根本不知道发生了什么。

所以挤出去的时候**整步一起走**，绝不只挤走一半。

### 4.2 长期记忆：后台异步摘要

被挤出窗口的事件不是直接丢掉 —— 它们累积到一定数量（默认 **10** 条）时，
在**后台异步**触发一次摘要：

.. code-block:: text

    新摘要 = LLM(旧摘要 + 新挤出来的事件)

三个刻意的设计：

1. **后台异步** —— 摘要绝不在主循环里同步做；
2. **摘要失败不丢历史** —— 失败的摘要**不会**把旧摘要清掉，
   累积的事件也留着，下次再试；
3. **不引依赖** —— 摘要用哪个模型由调用方用「一个可调用对象」注入。

### 4.3 上下文怎么拼

`StreamMemory.context()` 的顺序是**背景在前、窗口在后**：

```text
【历史背景】
（旧摘要）

【最近步骤】
第1步 [Bash] ls
第2步 [Read] a.py
```

⚠️ 顺序有讲究：历史背景放**开头**，静态前缀放最前面 ——
这样前缀才能被缓存命中。

## 5. 任务四：级联模型路由（L1 → L2 → L3）

新模块 [`src/llm/cascade.py`](../../../src/llm/cascade.py)。

### 5.1 三级各司其职

========= ========================== ==================================
层级      做什么                      代价
========= ========================== ==================================
**L1**    正则规则层 —— 命中就拦      **零**（本地内存运算，微秒级）
**L2**    本地小模型（NInfer）——      本地算力，**不花钱、不出网**
          三值判定：还在做吗？          （但慢：单并发，一次几秒）
**L3**    云端强模型 —— 交叉验证      **要钱、要出网**（但最准）
========= ========================== ==================================

**让便宜的去筛，让贵的去判。**

L2 判 `ON_TRACK` 的那些事件 —— 也就是**绝大多数**正常操作 ——
**根本不该走到云端**。这就是「省下 Y 次云端调用」的由来。

### 5.2 双盲亮红灯

| L2 | L3 | 结果 | 亮红灯？ |
| --- | --- | --- | --- |
| 不可用 | — | `unavailable` → **回退 L1 原始判定** | ❌ |
| `ON_TRACK` | — | `on_track` → **静默丢弃** | ❌ |
| 有问题 | 不可用 | `single`（单边判定，**记账**） | ❌ |
| 有问题 | 也有问题 | `escalated` → **升级 + Guardian 介入** | ✅ |
| 有问题 | 说没问题 | `cleared` → **判定被推翻** | ❌ |

⚠️ 只有 L2 说有问题、L3 说不 —— 那就不亮红灯。
（本地小模型误报是家常便饭，让它单方面拉响最高级警报，
只会训练用户忽略警报。）

### 5.3 三条硬约束

1. **L2 不可用时立刻回退 L1** —— 绝不死等、绝不堵队列；
2. **L3 不可用时**只记「单边判定」，**不**亮红灯；
3. **一切降级都要记账** —— 「模型判不了」必须**看得见**，
   否则用户以为自己在享受级联，其实在裸奔。

### 5.4 与现有路由器的区别

⚠️ 级联**没有**塞进 `ModelRouter`。

- `ModelRouter` 是「失败 / 严重 / 连续次数触发的**升级**」；
- v3.5.0 是「L2 **正向判定** → L3 **交叉验证**」。

两码事，所以新写了 `src/llm/cascade.py`。

### 5.5 配置

```yaml
llm:
  cascade:
    enabled: false          # 默认关闭 —— 关着行为与 v3.4.0 一字不差
    require_agreement: true # 双盲才亮红灯
    breaker_threshold: 3    # L2 连续失败几次就熔断
    breaker_open_seconds: 60
    l2:                     # L2 本地（拦截过滤）
      provider: openai_compatible
      base_url: http://127.0.0.1:8888/v1
      model: bonsai2-27b
      timeout: 10
      timeout_floor: 10     # 必须显式压低本机引擎的 600 秒下限
      max_tokens: 256
      reasoning_effort: none
    l3:                     # L3 云端（终极裁判）
      provider: openai_compatible
      base_url: https://api.example.com/v1
      model: strong-model
      api_key_env: OPENAI_API_KEY
```

## 6. 任务五：更新 GUI 与发布

### 6.1 设置页

【模型路由】页面新增第 ② 区「级联审核（L2 本地 → L3 云端）」，
里面再分成两个配置区：

- **②-1 L2 本地（拦截过滤）** —— 判「正常」就丢弃，省下云端调用；
- **②-2 L3 云端（终极裁判）** —— 只有 L2 报警才会被叫醒。

⚠️ 两个区的地址、模型、密钥、超时**完全是两回事**，
混在一起必然配错 —— 所以刻意分开。

数字输入框**留空 = 不写进配置**（别拿 0 把默认值顶掉）。

### 6.2 看板

顶部多一行轻量计数器：

> L2 已过滤 X 次冗余，为您节省 Y 次云端调用

⚠️ 数字**如实**显示：被过滤的次数与省下的云端调用次数
是**同一个数**（每丢一次就省一次），绝不拿别的数字凑数。
悬停能看到更细的账：L2 判了几次、升级了几次、亮了几次红灯。

### 6.3 日志格式契约

引擎与看板之间新增一对契约行：

| 标记 | 谁写 | 谁读 | 作用 |
| --- | --- | --- | --- |
| `CASCADE_JSON` | 引擎 | 看板 | 级联统计（按计数签名**节流**） |
| `ALERT_UPDATE_JSON` | 引擎 | 看板 | 双盲命中后的**升级**（合并进同一张卡片） |

⚠️ 级联只做**追加升级**：L1 告警**照旧立即发出**，
级联只更新同一张卡片 + 发一次升级通知 + 触发 Guardian 介入，
**不延迟红线响应**。

## 9. 已知边界（说清楚，别假装没有）

- ⚠️ **指纹依赖 Agent 自己写进日志的字段** ——
  日志里没有 `thread_id` / `session_id` / `cwd` 时，哨兵**认不出来**，
  所有事件归入默认那一路（行为与 v3.4.0 一致）。
  哨兵**不会**去猜、更不会拿工具参数里的路径凑数。
- ⚠️ **虚拟会话卡片是「看」的隔离，不是「挂起」的隔离** ——
  看板拆成多路之后，**挂起**的仍然是**进程**（不是线程）；
  同一进程里的多路，守卫者只能整体挂起。
- ⚠️ **L3 云端要花钱、会让日志出本机** ——
  只有用户自己配了 L3 并打开 `llm.cascade.enabled` 才会发生。
  L2 本地层的数据**不出本机**。
- ⚠️ **摘要质量取决于注入的模型** ——
  `src/core/memory.py` 本身**不含**任何模型调用；
  摘要函数由调用方注入，注入失败时**历史一条不丢**。
