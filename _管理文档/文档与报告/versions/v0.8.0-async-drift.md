# v0.8.0 —— 异步漂移审计与真实 Agent 管道接管

> **一句话**：让哨兵**不再拖慢被监控的 Agent**，并且第一次**盯住一个真的在跑的东西**。

## 1. 本次目标

1. **异步漂移审计** —— 7B 推理不能阻塞主事件循环；
   窗口攒满就丢队列，主线程立刻读下一行；
   模型太慢时按背压策略丢弃并留下痕迹。
2. **自动提取任务目标** —— 不再依赖用户手动敲 `--task-goal`；
   从流里第一条用户请求里提取。
3. **真实 Agent 管道接管** —— 写一个启动器，
   拉起**真的** `mcode exec`，把它的流式输出同时打印 + 审查；
   红线时挂起它，看板里点恢复。
4. **测试与发布** —— 异步队列测试 + 自动锚定测试 + 文档 + Git 标签。

## 2. 异步漂移审计

### 2.1 问题

v0.7.0 的判定是**同步**的：

```python
for event in events:
    verdict = self.intent_tracker.observe(event)   # ← 里面问了一次模型
```

`evaluate_drift()` 是一次本地 7B 推理 —— 实测**好几秒**。
这段时间里，主循环卡在那儿不读日志：Agent 写日志的速度、
哨兵跟上的速度，一起被拖慢。

### 2.2 解法：后台线程 + 有界队列

```
主线程                          后台线程（sentinel-drift）
------                          ------------------------
observe(event)
  攒够 5 步
  投递窗口 ────────────────────▶  队列（maxsize=3）
  立刻返回                        │
  继续读下一行日志                ├─ 取窗口
                                 ├─ 问模型（慢，随它去）
                                 ├─ 折算连续计数
                                 └─ 回调 on_result(verdict)
                                           │
                                           ▼
                                    引擎产告警 → Notifier
```

关键点：**主线程从头到尾不知道模型有多慢**。
它只是往队列里塞东西，塞不进去就扔。

### 2.3 背压：宁可漏判，不可堵死

队列是**有界**的（`max_pending=3`）。满了怎么办？

```python
try:
    self._queue.put_nowait(job)
except queue.Full:
    self.dropped += 1
    logger.warning("[WARN] 漂移检测超载：待判定窗口已达 %d 个，丢弃当前窗口")
    return False
```

丢弃而不是阻塞。理由很直接：
**哨兵是审查侧，它的卡顿不能变成被监控 Agent 的卡顿**
（红线 R5）。漏掉一次漂移判定只是少一条警告；
把主循环堵住会让**整个监控失去实时性**。

### 2.4 代码上怎么落的

```python
class IntentTracker:
    def __init__(self, ..., max_pending=3, wait_for_result=True, ...):
        self._queue = queue.Queue(maxsize=self.max_pending)
        self._worker = None
        self._stop = threading.Event()
        self._pending = 0
        self._idle = threading.Event()
        self._idle.set()

    def attach_async(self, on_result):
        """切到异步模式并挂上回调。"""
        self.on_result = on_result
        self.async_enabled = True
        self.wait_for_result = False

    def observe(self, event):
        ...
        self._submit(job)          # 投递，不阻塞
        if not self.wait_for_result:
            return None             # 异步模式：结论走回调
        return self._await(job)     # 同步模式：等结论（测试/脚本用）

    def _worker_loop(self):
        while not self._stop.is_set():
            try:
                job = self._queue.get(timeout=0.2)
            except queue.Empty:
                continue
            try:
                self._process(job)
            finally:
                self._queue.task_done()
                ... # 维护 _pending / _idle
```

**双模式**是刻意的：
`wait_for_result=True`（默认）时 `observe()` 仍然返回结论，
测试和脚本化调用**一行都不用改**；
引擎接管追踪器时会调 `attach_async()` 把它切成异步。

### 2.5 两个容易踩的坑

#### ① 换目标后，在途的旧判定要作废

```python
with self._state_lock:
    if job.goal != self.goal:
        logger.debug("漂移结论已作废（目标已变更）")
        return None
```

窗口在投递时**快照**了目标。如果用户中途换了目标，
那条在途结论针对的是旧目标 —— 拿来算新目标的连续次数就是错的。
所以直接丢弃。

#### ② 收尾必须 `drain()`

批量模式跑完时，漂移判定可能还在后台跑着。
不 `drain()` 就退出，**告警就丢了**。

```python
if self.intent_tracker is not None:
    self.intent_tracker.drain(timeout=self.drain_timeout)
```

## 3. 自动提取任务目标

### 3.1 逻辑

引擎在监听流的初始阶段找第一条 `user_message` 事件：

```python
def _maybe_anchor_goal(self, event):
    if self.intent_tracker is None:
        return
    if str(event.get("type") or "") != EVENT_USER_MESSAGE:
        return
    text = " ".join(str(event.get("text") or "").split())
    if not text:
        return
    goal = text[:GOAL_MAX_CHARS]
    if not self.intent_tracker.set_goal(goal):
        return
    print(_console_safe(f"[SENTINEL] 已自动锚定任务目标: {goal}"))
```

### 3.2 优先级：谁都不许覆盖「人明确说过的」

| 来源 | 优先级 | 说明 |
| --- | --- | --- |
| 命令行 `--task-goal` | **最高** | 人明确说的，`explicit=True` |
| 看板顶栏输入框 | **最高** | 同上（`explicit=True`） |
| 流里自动提取的 `user_message` | 中 | 覆盖配置里的默认值 |
| 配置文件 `task_goal` | 最低 | 只是兜底 |

`IntentTracker.set_goal(goal, explicit=False)` 里那条判断就是这条语义：

```python
if self.goal_explicit and not explicit:
    return False   # 人已经明确交代过了 —— 自动锚定不许覆盖
```

### 3.3 mcode 不回显 Prompt —— 包装脚本补上

实测 mcode v0.6.12 的 `stream-json` 里**没有** `user_message` item，
用户的原始请求根本没进流。

所以包装脚本在启动后**主动补**一条：

```python
def feed_user_message(self, prompt):
    event = {
        "source": "mcode", "type": "user_message",
        "text": prompt, "timestamp": time.time(), ...
    }
    self.engine.process_event(event)
```

引擎侧的处理路径与读日志时**完全一致** ——
不是给包装脚本开后门，而是包装脚本把用户那句话
**还原成**它本该在流里的样子。

## 4. 真实 Agent 管道接管

### 4.1 架构

```
┌────────────┐   stdout(stream-json)   ┌──────────────────┐
│ mcode exec │ ───────────────────────▶ │  run_with_sentinel │
└────────────┘                          └────────┬─────────┘
             ▲                              分支 A │ 实时打印到控制台
             │                                     │
             │                              分支 B │ 解析成统一事件
             │                                     ▼
             │                            ┌──────────────────┐
             │                            │  SentinelEngine  │
             │                            │  process_event() │
             │                            └────────┬─────────┘
             │                                     │ 红线级
             │                            ┌────────▼─────────┐
             └──── 挂起 / 恢复 ────────────│     Guardian      │
                                            │  psutil suspend  │
                                            └──────────────────┘
```

**看板与引擎同进程** —— 这是关键：
看板上的【放行并忽略】按钮恢复的，
正是引擎挂起的那个 mcode 进程。
如果看板在另一个进程里，按钮就管不到它。

### 4.2 引擎的「单步入口」

```python
def process_event(self, event: Event) -> Optional[Dict[str, Any]]:
    """处理单个事件：规则层 → 上下文模式 → 意图漂移。"""
```

`run()` 内部也走它。外部脚本直接调它，
不必先把日志落盘再让引擎去读文件。

### 4.3 三个真实世界才有的坑

#### ① mcode 的 `node` 进程在 `exec.completed` 之后**不退出**

实测：mcode 打完 `exec.completed` 之后 node 进程还活着，
stdout 管道不关闭。干等 EOF 的读取循环会**永远卡住**。

解法：读取循环带超时，以 `exec.completed` 事件作为终止信号：

```python
if '"exec.completed"' in text:
    exec_done = True
# ...
except queue.Empty:
    if exec_done and time.monotonic() - last_line_at > grace:
        break
```

#### ② `mcode` 是 npm 的 `.cmd` 垫片

`subprocess.Popen(["mcode", ...])` 解析不到 ——
它只认真正的可执行文件。改用 `shutil.which` 按 PATHEXT 定位：

```python
for name in ("mcode", "mcode.cmd", "mcode.exe", "mcode.bat"):
    found = shutil.which(name)
    if found:
        return found
```

#### ③ 挂起错了进程

`Popen` 拿到的 PID 是 `cmd.exe` 垫片的 —— **挂起它 Agent 照样跑**。

解法：沿进程树往下找，跳过垫片进程：

```python
for child in parent.children(recursive=True):
    if child.name().lower() in ("cmd.exe", "conhost.exe"):
        continue   # 垫片 —— 挂起它没有意义
    return child.pid
```

#### ④ 进程树清理的顺序

先 `terminate()` 掉 `cmd.exe`，后面的树清理就被跳过了 ——
真正的 `node.exe` 变成**孤儿继续跑**。
Windows 上必须**先杀树**：

```python
subprocess.run(["taskkill", "/PID", str(proc.pid), "/T", "/F"], ...)
```

## 7. 已知限制

1. **L2 解释仍是同步的** —— 一次模型调用会阻塞主循环几秒。
   漂移**判定**已经异步化，但「给告警配一句人话解释」还没有。
   守护者干预不受影响（它排在解释之前）。
2. **挂起的是 Agent 进程，不是它派生的子进程** ——
   Agent 已经 spawn 出去的 shell 子进程会继续跑完。
   Windows 的进程挂起是**进程级**的，做不到子进程级隔离。
3. **mcode 不回显 Prompt** —— 自动锚定靠包装脚本把用户那句话补成
   `user_message` 事件；日志里本来就带 `user_message` 的格式则直接自动锚定。
4. **漂移判定仍然要等模型** —— 异步只是让它**不挡路**，
   结论本身还是要好几秒才出来。
