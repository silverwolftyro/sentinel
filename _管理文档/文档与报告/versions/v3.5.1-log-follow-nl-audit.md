# v3.5.1 —— 日志跟随锁定 · 自然语言流水 · 空态引导

> v3.5.0 把内核的三块硬骨头解决了（并发串台、L2 缓存、级联双盲），
> 但看板上还剩四个**体验反人类**的地方：
>
> 1. 没有 Agent 在跑时，雷达**空荡荡**的 —— 用户不知道该去怎么启动日志；
> 2. 右侧「被监控日志」**强制锁死**在底部 —— 想回看历史，
>    刚往上滚就被新日志一把拽回来，根本没法看；
> 3. 中间「实时审核流水」全是 `[TAIL] #6 thinking | ...` 这种**机器码**，
>    用户不知道 Agent 到底在干嘛；
> 4. 界面**没有呼吸** —— 用户不知道系统是活着还是卡住了。
>
> 这一版是**纯前端体验版**：引擎判定、级联路由、红线规则**一字未动**，
> 改的全是「怎么把话说明白」。
>
> - **任务一：空态引导** ——
>   雷达扫不到任何在跑的 Agent 时，不再只写「未发现」，
>   直接给出**可执行的命令**，并附一个【复制命令】按钮；
> - **任务二：日志跟随锁定（Follow）** ——
>   只有你在底部时新日志才自动跟随；滚轮往上一翻**立刻解除跟随**，
>   右下角浮着【↓ 回到最新】，不在底部时高亮，点一下平滑滚到底并恢复跟随；
> - **任务三：自然语言流水 + 三色分类** ——
>   流水不再打印 JSON：`[15:32] Agent 正在思考：…` /
>   `[15:33] 正常执行命令：pytest` /
>   `[15:36] 危险！拦截到高危命令：rm -rf /`，
>   正常=**绿**、可疑=**橘黄**、危险=**红**；
> - **任务四：Status Pulse 呼吸灯** ——
>   顶部状态标签旁多一颗呼吸灯：引擎在跑就一直跳动，
>   暂停或停止变灰色常亮；
> - **任务五：发布 v3.5.1** —— CHANGELOG、版本文档、打包 exe、Git 标签。
>
> ⚠️ **红线一字未改** —— R1–R9 与 v2.1.0 **完全一致**。
> 退出时依然**只结束哨兵自己拉起的子进程**；
> 雷达挂载进来的用户进程**绝不**去杀（R6）。
> ⚠️ **引擎判定一字未改** —— L1 / L2 / L3 的规则、阈值、告警口径
> 与 v3.5.0 **完全一致**；这一版只改「呈现」，不改「判不判」。

## 1. 红线：这一版一个字都没改

| 红线 | 这一版怎么守的 |
| --- | --- |
| R1 只读监听 | 被监控的 Agent 日志**一个字节都没动**；这一版只多了「读日志内容算摘要」 |
| R2 不干预代码 | 新增的全是**内存状态**、**界面元素**与**配置项**，不含任何写文件的动作 |
| R3 不注入进程 | 这一版**没有**任何给进程发信号的逻辑 |
| R4 本地闭环 | 摘要提取、颜色判定、文案拼接**全在前端本机**完成，**没有**任何内容出网 |
| R5 旁路失败 | 剪贴板 API 被拒 → 自动退回 `execCommand("copy")`；平滑滚动不被支持 → 回退直接设 `scrollTop`；摘要取不到 → 退回标签式摘要，**不空行** |
| R6 不终止进程 | 这一版**没有任何**杀进程的逻辑；退出时的边界与 v3.5.0 完全一致 |
| R7 不悄悄改系统设置 | 新增的全是界面常量与前端函数，**没有**新增任何配置项 |
| R8–R9 | 与 v2.1.0 一致 |

⚠️ 特别说明一条容易紧张的：

- **「告警进流水区」不是新增一条告警通道** ——
  告警本来就发过 SSE、也本来就进过快照；
  这一版只是让它在流水区**也有一行**，**判定与通知路径一个字没动**。
  引擎判不判、判成什么，仍然完全由 v3.5.0 的规则决定。

## 2. 任务一：空态引导（拯救睁眼瞎）

### 2.1 问题出在哪

雷达扫不到任何在跑的 Agent 时，旧界面只写一句「未发现」。

对第一次用哨兵的人来说，这等于**踢皮球**：
他知道「没东西在跑」，但**不知道该敲什么命令**、
**不知道日志该写到哪个文件**。

### 2.2 引导文案

新增常量 [`src/gui/static/dashboard.js`](../../../src/gui/static/dashboard.js)：

```javascript
var RADAR_EMPTY_TITLE =
  "未发现正在运行的 Agent。若要开始监控，请在终端中运行：";
```

以及兜底的日志路径：

```javascript
var RADAR_EMPTY_FALLBACK_PATH =
  "D:\\项目\\<项目目录>\\logs\\capture.jsonl";
```

⚠️ **路径不是写死的** ——
`radarEmptyCommand()` 优先取后端 `/api/process_activity` 返回的
`capture_path`；只有后端还没回话时才用上面的兜底值。
打包成 exe 之后目录会变，靠后端回话才不会指错地方。

最终拼出的命令：

```text
mcode exec "你的指令" > D:\项目\<项目目录>\logs\capture.jsonl
```

### 2.3 一键复制

`copyRadarCommand(button)` 的行为：

| 步骤 | 做什么 |
| --- | --- |
| 1 | 先试 `navigator.clipboard.writeText()` |
| 2 | 被拒（无焦点 / 非安全上下文 / 权限不足）→ **自动退回** `textarea` + `document.execCommand("copy")` |
| 3 | 成功 → 按钮文字变「已复制 ✓」；失败 → 变「复制失败，请手动选中」 |

⚠️ **第 2 步是产品改进，不是只为演示** ——
无头浏览器、某些内嵌 WebView 里 `clipboard` API 会被直接拒绝，
旧实现只会甩一句「请手动选中」。现在会自动兜底。

### 2.4 引导落在三处

| 位置 | 什么时候出现 |
| --- | --- |
| 侧栏 `#radar-empty` | 雷达扫到 0 个活跃 Agent 且**没有**真实会话时 |
| 雷达弹窗 `renderRows()` 空态 | 同上（弹窗里的空列表） |
| 会话列表 | **保持「暂无会话」不变** —— 不重复展示同一句引导 |

## 3. 任务二：日志滚动跟随（Follow）

### 3.1 旧行为为什么反人类

旧逻辑是「追加日志行之后**无条件**滚到底」。

于是：用户往上滚想回看历史 → 新日志一到 → **一把被拽回底部**。
回看历史这件最基本的事，**根本做不成**。

### 3.2 新逻辑

新增常量：

```javascript
var LOG_FOLLOW_THRESHOLD = 50;
```

「在底部」的判定（[`logAtBottom()`](../../../src/gui/static/dashboard.js)）：

```javascript
var gap = box.scrollHeight - box.scrollTop - box.clientHeight;
return gap < LOG_FOLLOW_THRESHOLD;
```

⚠️ **为什么是 50 而不是 0** ——
滚动到底时，浏览器的亚像素误差会让 `gap` 在 0 上下抖；
卡得太死会把跟随**误判**成解除，用户莫名其妙就不跟了。

三条新函数各司其职：

| 函数 | 职责 |
| --- | --- |
| `logAtBottom()` | 判断当前**在不在**底部 |
| `onLogScroll()` | 监听 `scroll` 事件 → 更新 `state.logFollow` + 刷新按钮 |
| `scrollLogToLatest()` | **平滑**滚到底部 + 恢复跟随 |
| `updateLogFollowUi()` | 不在底部 → 显示并高亮【↓ 回到最新】；在底部 → 隐藏 |

### 3.3 【↓ 回到最新】按钮

- 位置：日志面板**右下角悬浮**（`.log-follow`），
  放在 `.panel__body` **之外**、面板容器之内 ——
  这样它**不会**跟着日志内容滚动；
- 不在底部时**高亮**（`.log-follow--visible`），在底部时**隐藏**；
- 点击 → `scrollLogToLatest()` → `scrollTo({behavior:"smooth"})`
  平滑回底 → `state.logFollow = true` → 按钮自动隐藏。

### 3.4 一个容易漏的坑：轮询冲掉阅读位置

看板每 15 秒轮询一次 `/api/state`。即便**日志内容没变**，
只要重画一次，浏览器的滚动位置就可能被重置 ——
用户正在看的那一段历史直接消失。

所以多做了两件事：

| 函数 | 作用 |
| --- | --- |
| `logContentUnchanged(lines)` | 内容与当前一致 → **不重画** |
| `replaceLogLines(lines)` | 内容变了 → 重画但**恢复原来的 `scrollTop`** |

⚠️ 也就是说：**你在哪儿，就停在哪儿**，
只有你自己点了【回到最新】或者自己滚回底部，跟随才会重新接管。

## 4. 任务三：自然语言流水 + 三色分类

### 4.1 三档颜色

新增常量：

```javascript
var AUDIT_LEVEL_OK = "ok";
var AUDIT_LEVEL_WARN = "warn";
var AUDIT_LEVEL_DANGER = "danger";
var AUDIT_SNIPPET_LIMIT = 40;
```

| 等级 | 颜色 | 触发口径 |
| --- | --- | --- |
| `ok` | **绿** | L1/L2 判定 `ON_TRACK` |
| `warn` | **橘黄** | `LOOP` / `STUCK` / `LEAK` / `DRIFT` / `TIMEBOX` 等非红线判定 |
| `danger` | **红** | `DANGEROUS`、`severity == "red_line"`、`level == "critical"` |

### 4.2 摘要从哪来（后端）

后端只提供**已经截断的原料**，不下发原始 JSON：

[`src/core/live_audit.py`](../../../src/core/live_audit.py) 新增：

```python
MAX_SNIPPET_LENGTH = 40

def extract_snippet(event, limit=MAX_SNIPPET_LENGTH):
    ...
```

取值顺序：

| 事件类型 | 取什么 |
| --- | --- |
| `thinking` / `text` | `event["text"]` |
| `tool_call` | `tool["command"]` → 文件路径 / 搜索模式 → 工具名 |
| 其它 / 非 Mapping | **空串**（不编造内容） |

[`src/core/engine.py`](../../../src/core/engine.py) 的 `_emit_on_track()`
载荷**追加** `"snippet": extract_snippet(event)`。

⚠️ **只追加，不改动** —— v3.5.0 的 `ONTRACK_JSON` 既有字段**一个不少**，
`summarize_event()` 的标签式摘要也**保留不动**
（v3.3.1 的回归依赖它）。

### 4.3 人话怎么拼（前端）

| 函数 | 产出 |
| --- | --- |
| `clipText(text, limit)` | 压到 40 字；先切后 `trim`，避免悬空空格再接省略号 |
| `auditVerb(summary)` | 从标签式摘要里认出「读取 / 执行 / 搜索 / 思考」 |
| `auditSentence(entry)` | 拼出完整的一句话 + 定颜色 |
| `auditSentenceFromAlert(alert)` | 告警专用的一句话 + 定颜色 |
| `auditClock(stamp)` | 时间戳 → `[HH:MM:SS]` |

实际产出（**实机跑出来的**，不是编的）：

```text
[17:39:32] Agent 正在思考：我先确认一下这个模块的边界条件，再决定要不要改它的签名；如果只改内部实现，对外…
[17:39:32] 正常读取：core/engine.py
[17:39:32] 正常执行命令：python -m pytest -q tests/
[17:39:32] 警告：连续 3 次读取同一个文件，疑似死循环: src/core/auth.py
[17:39:32] 危险！拦截到高危命令：rm -rf /
```

⚠️ **LOOP 的文案用的是规则里真实的 `reason`** ——
`连续 3 次读取同一个文件，疑似死循环: src/core/auth.py`，
不是前端现编的句式。

### 4.4 一个真实的 bug（已修）：告警流水被轮询抹掉

⚠️ 这一段是**实机排障**的记录，值得写下来。

**现象**：告警卡片**有**（说明引擎判定与 SSE 都没问题），
但流水区**没有**橘黄行与红色行。

**误判过程**：先怀疑 SSE 没发、后端没解析。
实测证明两处都**没问题** ——
`parse_alert_line()` 用的全是 `line.find(marker)`，**对 logging 前缀免疫**，
告警行能正确解析；SSE 也确实发过 `alert` 事件。

**真正的根因**：看板每 15 秒轮询 `/api/state` →
`applyState()` → `renderLiveAudit(data.ontrack)` → `clearLiveAudit()`，
把前端临时追加的告警流水行**整块抹掉**。

**修法**：把告警改成**服务端权威** ——
[`src/gui/server.py`](../../../src/gui/server.py) 里新增
`_audit_stream_entry(normalized)`，
让告警以 `stream_kind: "alert"` 进 `_ontrack` 快照：

- SSE 路径与快照路径**走同一个** `auditSentenceFromAlert()`，
  保证**同一句话、同一个颜色、同一个时刻**；
- 刷新页面、切会话都不丢；
- `AlertStore.streams()` 里告警流水**不计入**「正常」计数
  （已在 alerts 那栏数过），只更新 `last_seen`，避免「X 告警 / Y 正常」重复计数。

⚠️ **告警的识别判据是 `stream_kind` / `type`，绝不是 `event_type`** ——
告警条目自带 `event_type: "tool_call"`（触发它的事件类型），
拿它当判据会**误判**。

## 9. 已知边界（说清楚，别假装没有）

- ⚠️ **摘要是「截断 + 拼接」，不是「理解」** ——
  `extract_snippet()` 取的是事件的**原文前 40 字**，
  前端把它和动词拼成一句话。
  它**不做**语义判断，也不参与任何风险判定；
  告警判不判**只看** L1 / L2 / L3 的规则结果。
- ⚠️ **告警的判定口径与 v3.5.0 完全一致** ——
  颜色只是**呈现**，把「严重」映射成红色而已，
  不会新增任何一条告警路径。
- ⚠️ **「回到最新」按钮只管日志面板** ——
  实时审核流水区是**追加**的，不会自动滚动，
  它也没有跟随锁定（流水本来就短）。
- ⚠️ **空态引导需要「真的一个活跃 Agent 都没有」** ——
  只要雷达扫到哪怕一个在跑的进程，引导就**不出现**
  （那正是有东西在跑的时候，不需要教用户怎么启动）。
- ⚠️ **命令里的路径来自后端** ——
  打包成 exe 之后目录会变，
  `capture_path` 由后端 `/api/process_activity` 给出；
  只有后端没回话时才用前端兜底常量。
- ⚠️ **告警卡片的分路仍有一个已知问题** ——
  `normalize_alert()` **丢弃了 `fingerprint` 字段**，
  导致生产环境告警卡片一律归入 `default` 路。
  这是 **v3.5.0 就有的既有问题**，本次**刻意不动**
  （改了会动到 v3.5.0 的语义），记在这里备案。
