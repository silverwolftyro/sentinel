## 1. 红线：这一版一个字都没改

**本版未新增任何红线修订。** R1–R9 与 v2.1.0 **完全一致**，**一字未改**。

逐条对照：

* 哨兵**依然只读** —— 本版写的晨报归档、内存采样都落在**哨兵自己的地盘**
  （`_管理文档/文档与报告/晨报归档/`、`logs/`），
  **绝不**写进用户被监控的项目目录；
* 本版**没有**新增任何写用户文件 / 改用户代码 / 终止用户进程的路径；
* 晨报推送是**往外发消息**，不是往外**写**用户的东西 ——
  报文里只含统计数字，**不含**用户的日志内容；
* 守护者**依旧要用户亲手武装**，本版只在演习脚本里临时武装，
  **产品代码没有**任何自动武装路径；
* 配置写回仍然只用 `config_loader.save_config()`
  （外科手术式，保留注释，写前备份 `.bak`）；
* `tail_stream` 的缓冲上限**只丢「一行超长的残片」**——
  它本来就不是一条完整记录，**不会**丢任何**完整行**；
* 代码卫生只动哨兵**自己**的代码，**不碰**用户项目；
* 本版新增的「L2 判不了要说一声」（见 4.7）**只是打印一行字** ——
  既不写用户文件，也不碰用户进程，更**不会**把日志内容送去云端。

> ⚠️ 唯一新增的「写」在晨报归档目录里，那是**哨兵自己的报告目录**。

## 2. 任务一：晨报的远程自动投递

### 2.1 为什么

「早上醒来去电脑里翻文件」这件事本身就不成立 ——
夜里挂机的意义就是**醒来就在手机上看到结果**。

而且完整晨报是**几 KB 到几十 KB** 的 Markdown 文档。
整篇塞进钉钉 / 飞书的消息体，很容易**被截断** ——
用户在手机上看到的是一段莫名其妙断掉的话，
一点也拼不出「昨晚到底拦住了什么」。

### 2.2 做了什么

| 位置 | 职责 |
| --- | --- |
| `src/core/briefing.py` → `build_briefing_summary(stats, *, title="")` | 把统计压缩成**纯数据**摘要（`title` / `markdown` / `text` / `stats`） |
| `src/core/channels.py` → `WebhookChannel.build_briefing_payload(summary)` | 按 dingtalk / feishu / serverchan / bark / generic 组报文 |
| `src/core/channels.py` → `WebhookChannel.send_briefing(summary)` | **入队**（不做网络 I/O） |
| `src/core/notifier.py` → `Notifier.push_briefing(summary, *, timeout=10.0)` | 等队列跑完，按**真实投递结果**返回成败 |
| `_构建与发布/scripts/run_with_sentinel.py` | 两条路径（退出收尾 / 看板按钮）都在**落盘后自动推送** |

摘要的核心三项（任务书点名）：

| 字段 | 含义 |
| --- | --- |
| `intercepts` | 总拦截次数（= `DANGEROUS` 判定数） |
| `red_line` | 红线次数 |
| `token_saved` | 挽回 Token 数 |

外加 `drift` / `stuck` / `leak` / `loop` / `on_track` / `total_tokens` /
`duration_text` / `total_events` 作为补充。

### 2.3 摘要与告警是两种东西

⚠️ 这个区分很重要，所以**分成了两层**：

* `build_briefing_summary()` **不认识任何通道** —— 它只产出纯数据；
* 报文格式由 `channels.py` 负责 —— 摘要和告警的标题、语气、字段都不一样。

摘要的语气是「**这一夜的总结**」，告警的语气是「**刚发生了一件坏事**」。

### 2.4 晨报投递不过告警的三道闸门

| 闸门 | 告警走吗 | 晨报走吗 | 为什么 |
| --- | --- | --- | --- |
| 等级过滤（`min_level`） | ✅ | ❌ | 晨报不是「一条告警」，没有等级 |
| 合并窗口（`merge_seconds`） | ✅ | ❌ | 晨报是**一次性**总结，合并没有意义 |
| 触发类型（`triggers`） | ✅ | ❌ | ⚠️ 用户配了 `triggers: [DANGEROUS]` 的话，晨报会被当成「不是 DANGEROUS 告警」而**永远推不出去** |
| 防骚扰窗口（`dedup_seconds`） | ✅ | ❌ | 同上 |

### 2.5 「已推送」必须是真话

投递是**后台线程**做的（不能卡住主循环）。
但晨报是**收尾时**才推的 —— 那时用户正要关进程，
等一下返回「已推送」很可能只是「已入队」。

所以 `push_briefing()` **先入队，再 `flush(timeout=10)`**，
最后按 `channel.last_delivered` 返回**真实**结果。
宁可让收尾多等几秒，也不要对用户说谎。

### 2.6 实测（终端实拍）

```text
[SENTINEL] [night-crawl] 晨报已保存：D:\项目\<项目目录>\_管理文档\文档与报告\晨报归档\晨报-2026-10-28.md
[SENTINEL] [night-crawl] 晨报摘要已推送到你的手机。
```

Mock Webhook 收到的报文（`generic` 格式）：

```json

  "title": "🌅 哨兵晨报 · 2026-10-28",
  "text": "值守 1 分 12 秒 · 处理 36 条事件\n拦截 1 次（红线 1 次）\n挽回 Token 4.2k",
  "card": "## 🌅 哨兵晨报 · 2026-10-28\n\n⏱ **值守 1 分 12 秒** · 处理 36 条事件\n\n🚦 **拦截 1 次**（红线 1 次）\n💾 **挽回 Token 4.2k**",
```

## 3. 任务二：哨兵自身的性能监测（防资源黑洞）

### 3.1 为什么

「监控工具本身不能变成资源消耗大户」——
一个越吃越胖的监控器，比没有监控更糟：
用户会怀疑它、关掉它，然后整夜的值守就白搭了。

所以这一版让哨兵**自己量自己**，并且把结果**摆在用户眼前**。

### 3.2 `src/selfmon.py`（新叶子模块，只用标准库）

| 能力 | 实现 |
| --- | --- |
| 内存 | `GetProcessMemoryInfo` 的 `WorkingSetSize`（+ 峰值 + 私有提交量） |
| CPU | `GetProcessTimes` 的「内核时间 + 用户时间」÷ 墙钟时间 |
| 运行时长 | 进程创建时间到现在 |
| 线程数 | `threading.active_count()` |
| 平台 | Windows 走 `ctypes` 调 Win32；其它平台退回标准库 |

**为什么不引 `psutil`**：`psutil` 是**可选**的（没装也能用），
主力实现走 `ctypes` —— 打包版**不需要**额外装东西。

### 3.3 三个「不编数字」的硬规矩

1. **取不到就是 `None`** —— 绝不编造数字；
2. **CPU 百分比必须两次采样才有意义** —— 第一次返回 `cpu_ready=False`，
   页面显示「采样中…」而不是骗人的 `0.0%`；
3. ⚠️ **多核上 CPU% 可以超过 100%**（16 核跑满是 1600%）——
   那不是 bug，是「用掉了 16 个核」，文档里写明了。

### 3.4 Win32 调用的两个坑

* **必须显式声明 `argtypes` / `restype`** ——
  `ctypes` 默认签名把句柄当成 32 位整数，
  64 位 Windows 上的伪句柄 `GetCurrentProcess()` 会被截断，
  `GetProcessTimes` 直接返回失败；
* ⚠️ **`FILETIME` 的纪元是 1601-01-01**，不是 Unix 纪元 ——
  换算成时间戳要减掉 `11_644_473_600` 秒。
  忘了减会得到一个「1970 年 + 48000 年」的时间戳。

### 3.5 引擎侧周期自检

挂在**主循环**里是刻意的 —— 引擎空闲时（半夜 Agent 也没动静）
采样频率自然跟着事件频率走，**不会空转**。

```text
[SENTINEL] 自检：CPU 0.6% · 内存 71.5 MB · 运行时长 0 分 55 秒
```

默认间隔 `selfcheck_interval = 300`（5 分钟）。

### 3.6 设置页【关于系统】（第 ⑤ 项）

独立子页 `/settings/system`（v3.0.2 的 MPA 结构下最一致的做法）：

| 字段 | 来源 |
| --- | --- |
| 版本号 | `src.__version__` |
| 运行时长 | 采样结果的 `uptime_text` |
| 内存占用 / 峰值 / 私有提交 | 采样结果的 `memory_mb` / `memory_peak_mb` / `private_mb` |
| CPU 占用 | 采样结果的 `cpu_percent`（第一次显示「采样中…」） |
| 线程数 | 采样结果的 `threads` |
| 进程 ID | 采样结果的 `pid` |
| 配置文件路径 / 监听地址 / 会话数 | 服务器自己的状态 |

对应端点：`GET /api/system`。

页面脚本遵守既有契约：`window.SentinelPage = { init, destroy }`，
5 秒刷新一次，`destroy()` 里清掉定时器。

> 实拍：[`assets/settings-v3.2.0-system.png`](../assets/settings-v3.2.0-system.png)

### 3.7 `tail_stream` 的内存防线

被跟随的日志写出**超长行**（迟迟不换行）时，
跟读器的末尾半行缓冲会**无限增长** —— 那就是内存黑洞的入口。

v3.2.0 给它加了硬上限：

| 项 | 值 |
| --- | --- |
| 上限 | **1 MiB**（`max_buffer`） |
| 超限行为 | 丢掉**最老**的残片 |
| 日志 | **只记一次** warning（不刷屏） |

单次读取本身已有 **4 MiB** 上限，轮转与截断也都能识别。

## 4. 顺手修的两个真缺陷

### 4.1 `WebhookChannel.close()` 会丢掉队列里的晨报

⚠️ 原来的写法是直接 `self._stop.set()` ——
而投递线程的循环条件是 `while not self._stop.is_set()`，
于是**队列里还没投出去的报文会被直接丢掉**。

这个坑在「晨报推送」上暴露得特别明显：
晨报是**收尾时**才入队的（此刻用户正要关进程），
入队完很快就 `close()` —— 报文还在队列里，线程就停了，
手机上**什么也没收到**，而哨兵还印了一句「已推送到你的手机」。

**修法**：`close()` 先 `flush(timeout=10.0)` 再停线程。

### 4.2 `triggers: []` 被当成「一个都不推」

配置文档写的是「只推这些触发类型（**留空 = 推全部**）」，
但实现把空列表当成「一个触发类型都不匹配」——
于是**用户清空列表 = 静默丢掉所有通知**。

深夜出事，手机上**静悄悄地什么都没收到**，
而哨兵这边一切正常 —— 这比崩溃还难查。

**修法**：装配时把空列表归一成 `None`（= 不过滤），
`WebhookChannel` 自身也做同样的防御。

```python
# 旧：triggers=[] → tuple() → 不是 None → 全部过滤掉
self.triggers = tuple(...) if triggers is not None else None
# 新：空列表 = 不过滤
self.triggers = cleaned or None
```

⚠️ **非空列表的过滤能力一点没动** —— 用户配了
`triggers: [intent_drift]` 依然只推漂移。

### 4.3 顺手改掉的第三处：`selfcheck` 名字撞车

引擎里原本把采样结果存在 `self.selfcheck`，
而方法也叫 `selfcheck` —— **实例属性优先级高于类属性**，
`__init__` 一执行就把方法覆盖成了一个字典，
引擎主循环第一次自检就会 `TypeError: 'dict' object is not callable`。

属性改名为 `self.selfcheck_data`，并补了回归测试守着。

### 4.4 ★ 晨报其实**没送到**，终端却在说「已推送」

⚠️ 这是本版**最严重**的一个 —— 因为它**说谎**。

**怎么发现的**：30 分钟演习的 Mock Webhook 收到 **3 条告警 + 0 条晨报**，
而终端明明印着「晨报摘要已推送到你的手机」。

**根因有两层**：

| 层 | 问题 |
| --- | --- |
| 收尾顺序 | 真实顺序是「关引擎 → 推晨报」，而 `engine.close()` 会把 `notifier` 关掉（Webhook 的投递线程随之停止）。晨报在那之后才入队 → **队列里没人送了** |
| 成败判断 | `Notifier.push_briefing` 看的是 `channel.last_delivered` —— 那是「最近一次」的结果，可能是**更早的一条告警**留下的，于是它返回 `True` |

**结果就是**：手机上什么也没收到，而哨兵说「已推送到你的手机」。
用户早上醒来只会觉得「哨兵坏了」。

**三处一起修**：

1. `AgentSession.close()` 改成 **「定结束时间 → 推晨报 → 再关引擎」**；
2. `WebhookChannel` 的投递线程在 `close()` 之后**可以复活**
   （`_ensure_worker()` 会撤掉停止信号）——
   否则关掉的通道接单就是「静静躺着没人送」；
3. `Notifier.push_briefing` 改用**送达计数**（`delivered_count`）
   判断「**这一条**到没到」，不再拿陈旧的成功冒充。

顺带修掉一个副作用：原来的收尾会把晨报**推两次**
（手机上收到两份一样的晨报，归档文件里多出一节）。

### 4.5 不读 stdin 的 CLI 继承了父进程的 stdin

`mcode exec` / `codex exec` 这类**一次性**模式不读 stdin，
原来的写法是 `stdin=None`（继承）。

继承意味着子进程可能拿到一条**永远不关闭**的管道 ——
它一旦因为某种原因去读 stdin（比如想确认操作），就会**永久阻塞**。

改成 `stdin=subprocess.DEVNULL` —— 读不到就立刻 EOF 退出，
而不是挂在那里等天荒地老。会读 stdin 的 CLI 仍然拿管道
（v2.0.0 的直写通道不受影响）。

### 4.6 演习脚本自己踩的两个坑

演练脚本一开始也漏了两处，**实机跑才暴露出来**：

| 问题 | 后果 | 修法 |
| --- | --- | --- |
| 没起 `session.run()`（读 stdout 的线程） | Agent 的 stdout 管道**没人读** → 缓冲区写满 → Agent 卡死在写日志上，一个字都吐不出来 | 起后台线程走**生产路径** |
| 没喂任务目标（`feed_user_message`） | 任务目标是空的 → **DRIFT 永远判不出来** | 照着生产流程补上这一口 |

这两条都写进了版本文档，因为「演习脚本和生产流程要走同一条路」
本身就是个值得记住的结论。

### 4.7 ★★ 意图漂移检测**静悄悄地死掉**（L2 模型没装）

⚠️ 这是本版**最隐蔽**的一个 —— 因为它**什么都不说**。

**怎么发现的**：30 分钟演习跑完，`DRIFT` 一次都没判出来，
而终端只有一句不像样子的提示：

```text
调用模型失败（OllamaError: 本地模型不存在：qwen2.5:7b（请先执行：ollama pull qwen2.5:7b）），以上为规则层原始判定
```

顺着这句话查下去，根因是：

```powershell
> ollama list
NAME    ID    SIZE    MODIFIED
                          # ← 一个模型都没有
```

**Ollama 服务在跑，但本机一个模型都没装。**
于是每一次漂移判定都**降级**；
而降级在口径上等于「**没漂移**」（红线 R4：缺失绝不等同于有问题）。

三件事叠在一起，于是**意图漂移检测彻底死掉，而且一声不吭**：

| 层 | 发生了什么 | 用户看见的 |
| --- | --- | --- |
| 模型层 | 每次判定都抛「模型不存在」 | 一条混在告警里的括号说明 |
| 追踪器 | 降级 → 连续计数归零 → 永远凑不齐 `threshold` | **什么都没有** |
| 晨报 | 「意图漂移：0 次」 | 看起来一切正常 |

> 换句话说：**「0 次漂移」和「根本没在判」在报告里长得一模一样。**

⚠️ 这比「判错」严重得多 —— 判错用户还能看见，判不了用户**看不见**。

**修法：不改判定口径，只让它别再沉默**

红线 R4 一个字没动：**降级依然算「未漂移」**，绝不把「不知道」当成「有问题」。
这一版只做三件事 —— **把失效说出来**：

| 位置 | 做什么 |
| --- | --- |
| `src/llm/router.py` | `ModelRouter` 记下 `degraded_calls`（降级次数）与 `last_degraded_reason`（最近一次原因） |
| `src/core/engine.py` | 漂移结论为降级时，终端**明确说一声**（**同一个原因只说一次**，免得刷爆终端） |
| `src/core/briefing.py` | 晨报**如实标注**「有 N 次判定降级 —— 那段时间的漂移检测等于没开」，连推给手机的摘要里也带这一句 |

终端实拍：

```text
[SENTINEL] L2 模型判不了，本次意图漂移判定按「未漂移」处理（调用模型失败（OllamaError: 本地模型不存在：qwen2.5:7b…））。这段时间漂移检测等于没开 —— 把主力模型装好，或改 llm.provider 指向可用的模型。
```

⚠️ **没有**改成「模型挂了就把内容送到云端」 ——
那会悄悄突破红线 R4（本地闭环）。
本版坚持：**要么本机判，要么明说判不了**。

顺带在 `config/config.example.yaml` 与本机 `config/config.yaml` 里
加了一句提醒（这个坑值得写在配置旁边）：

```yaml
  # ⚠️ 这个模型名必须**真的装在本机**：`ollama pull qwen2.5:7b`。
  # 忘了拉 = 模型判不了 = 意图漂移检测**等于没开**（v3.2.0 实机踩过）。
  # 自检：终端打 `ollama list`，能看到模型名才算装好。
  model: "qwen2.5:7b"
```

> 这一版的正式演习因此改用**本机 Ollama 真模型**（`qwen2.5:7b`，4.7 GB）
> 来判漂移 —— 漂移**判定本身**全程在本机完成。

⚠️ **但「数据一步没出本机」这话只对了一半，得写准。**

本机 `config/config.yaml` 里 `llm.routing` 是**开着**的
（v1.2.0 的多级模型路由），于是有**两条路径**会把被审查的日志片段
（送模型前已按 `redact_before_llm` 脱敏）送到**云端模型**：

| 触发条件 | 配置项 | 用的模型 | 内容出不出本机 |
| --- | --- | --- | --- |
| 普通告警解释、**第一次**漂移判定 | — | `ollama:qwen2.5:7b`（本机） | 不出 |
| **连续漂移后的升级判定** | `drift_escalate_threshold: 1` | `openai_compatible:deepseek-chat` | **出** |
| **红线级拦截的解释** | `escalate_on_red_line: true` | 同上 | **出** |

这不是 v3.2.0 引入的 —— **v1.2.0 就有**，
配置项旁边本来就写着「启用它 = 允许被审查的日志内容**离开本机**」。
但既然本版把模型用量写进报告，就得照实写：

* **本地 Ollama 判漂移**（红线 R4 的默认姿态）**一个字没改**；
* 本版**没有**因为「本地模型扛不住」就偷偷把内容转去云端 ——
  4.7 那节那个「L2 判不了就说一声」的修法，恰恰是**不**做这件事；
* 要不要开云端升级，**是用户自己的开关**，本版只是把它的后果说清楚。

### 5.2 它真的做了什么

* **真拉 Agent**：`mcode exec --output-format stream-json --cwd <目录> --max-steps 60 --permission smart "重构一个中等规模的模块"`；
* **真造工作目录**：生成一个约 180 行的 `legacy_parser.py`（含重复分支逻辑）
  + `tests/test_legacy_parser.py` + `README.md`；
* ⚠️ **沙箱落在仓库外面**（系统临时目录）——
  见下面 5.2d，那是个**实机跑出来**的教训；
* **真注入三个场景**（走**真实适配器解析链路** —— 注入素材用 mcode v0.6
  事件溯源格式，经真实 L1 规则 + 真实 L2 判定 + 真实守护者）：

| 场景 | 注入时刻 | 触发 |
| --- | --- | --- |
| STUCK | 窗口的 **4%** | 3 轮 `pytest` 连着失败 |
| DRIFT | 窗口的 **33%** | 5 条 reasoning + 10 条完全不相干的运维命令，**连喂两轮共 30 步**（本机 Ollama 真模型判定） |
| DANGEROUS | 窗口的 **66%** | `find . -name '*.tmp' -delete` → 命中 `catastrophic_mass_delete` 红线 |

时间表**按演习时长按比例**排 —— 固定秒数只对「30 分钟」成立，
拿去跑 5 分钟的短演习，三个场景会全挤在前两分钟里，告警互相盖住。

⚠️ **危险删除放后段**，是因为它会把 Agent **挂起** ——
挂起之后就没有后续事件了，窗口的尾巴得留给它。

⚠️ **DRIFT 为什么要喂 30 步**：漂移判定是**滑窗 + 连续计数** ——
窗口 5 步、连续 2 次才告警，也就是**至少 10 步连续跑题**。
只喂 8 步的话第二个窗口会被真实 Agent 的事件稀释，判定就飘了。
现在一轮 15 步（5 条 thinking + 10 条命令）、连喂两轮，
**六个窗口全是纯跑题**，判定不再靠运气。

注入的跑题动作**一条规则都不碰**（有回归测试守着）——
`sudo`、`dd of=/dev/`、`find -delete` 这类都被剔除掉了，
否则「跑题」会顺带变成「危险」，拦截次数的统计就脏了。

### 5.2b ★ Agent 退出即重拉（演练脚本自己踩的坑）

⚠️ `mcode exec` 是**一次性**命令 —— 干完活就退出。

实测重构一个 180 行的模块只要**三分钟**，
而演习窗口是 **30 分钟**、危险删除注入在第 **8 分钟**。

没有这一段的话：注入发生的时候 Agent 早就走了，
守护者拿着一个**已经不存在的 PID** 去挂 ——
结果是 `NoSuchProcess`，红线**拦得住但挂不住**。

实测踩到过：`guardian_intercept = false`，错误是
`NoSuchProcess: process PID not found (pid=18268)`
（18268 是启动器 PID，真正的 node 进程 21000 早就退出了）。

**修法**：Agent 退出就**再拉一个**
（走 `session.relaunch()` —— 生产路径里「回滚并重试」用的同一个函数，
它会同时把守护者**重新指向新进程**）。

于是：演习窗口是 30 分钟，Agent 就得在这 30 分钟里**一直有活着的目标**。

### 5.2c ★ stdout 读取线程与任务目标

演练脚本一开始还漏了两处，**实机跑才暴露出来**：

| 问题 | 后果 | 修法 |
| --- | --- | --- |
| 没起 `session.run()`（读 stdout 的线程） | Agent 的 stdout 管道**没人读** → 缓冲区写满 → Agent 卡死在写日志上，一个字都吐不出来 | 起后台线程走**生产路径** |
| 没喂任务目标（`feed_user_message`） | 任务目标是空的 → **DRIFT 永远判不出来** | 照着生产流程补上这一口 |

这两条都写进版本文档，因为「**演习脚本和生产流程要走同一条路**」
本身就是个值得记住的结论。

### 5.2d ★★ Agent 越界改了**仓库源码**（最惊险的一次）

⚠️ 第一次正式跑 30 分钟演习时，**Agent 把哨兵自己的源码改了**。

**怎么发现的**：演习跑到一半，仓库里凭空多出一个目录
`src/core/briefing/`（`archive.py` / `collect.py` / `constants.py` /
`render.py` / `stats.py` / `_probe.py`）。

**它干了什么**：任务原本只说「重构一个中等规模的模块」，
Agent 就**自己找**了一个中等规模的模块 ——
它挑的是仓库里的 `src/core/briefing.py`（全项目最大的模块之一），
然后把那个文件**拆成了一个同名包**。

⚠️ 那不只是「改坏了」，还埋了一颗**导入遮蔽**的地雷：
同名的**包目录**和**模块文件**躺在一起，
`import src.core.briefing` 到底加载谁，取决于路径解析顺序
（PEP 420 的命名空间包优先级低于普通模块，但这种局面**不该存在**）。

**两个修法**：

| 修法 | 说明 |
| --- | --- |
| **沙箱挪到仓库外面** | 演习工作目录改用系统临时目录 —— Agent 顺着目录往上走也**够不着**被监控的代码库 |
| **任务点名文件** | 不再说「重构一个中等规模的模块」，改成「把**当前目录下**的 `legacy_parser.py` 重构成更清晰的结构」 |

**还加了一道「可验」的证据**：演习开始前给仓库的 `src/` 拍一次
SHA256 指纹，结束时再拍一次比一比 ——
报告里直接给出 `source_untouched` 与 `source_diff`。

⚠️ 这不只是「检查一遍」——
**红线 R1 说「哨兵绝不改用户的代码」，光说没用，得能验。**

> 这一节是整个 v3.2.0 里最有价值的一段：
> 它证明**演练本身**发现了一个真实存在、而且不修就一定会踩到的坑。

* **真挂起**：守护者在**内核层**挂起进程
  （`NtQueryInformationThread` class 35 查线程状态）；
* **真推 Webhook**：内置 Mock Server 记录全部报文
  （`body["type"] == "briefing"` 区分晨报）；
* **真出晨报**：走生产路径 `launcher.AgentSession` → 真实 `session.close()`
  → `write_briefing()` → 自动推送；
* **真量内存**：每 30 秒采一次，用**后半段斜率**判泄漏
  （>2 MB/分且涨 >8 MB 才算泄漏）。

### 7.1 ★ Defender 把 exe 误判了（开机自启差点静默失效）

**这是发布当夜实机踩到的，不是假想。**

| 项 | 事实 |
| --- | --- |
| 时间 | 2026-10-28 **22:59:00**（打包完成 10 分钟后） |
| 判定 | `Trojan:Win32/Bearfoos.A!ml`（ThreatID `2147731250`） |
| 对象 | `_构建与发布\dist\sentinel.exe`（刚打出来 11 分钟） |
| 处置 | 隔离文件（`ActionSuccess = True`）**并结束正在运行的两个进程** |
| 后果 | 开机自启**静默失效** —— 快捷方式还在，exe 没了；开机后什么也不发生，**也不报错** |

**这是误报**，理由三条：

1. 威胁名带 **`!ml`** —— 机器学习（ML）启发式判定，**不是签名命中**；
   它没有匹配任何已知木马特征码，只是「看着像个打包过的可执行文件」；
2. 本项目源码**全程可审**：只读监听、不注入进程、不终止用户进程，
   没有混淆壳、没有下载器、没有凭据窃取 —— 与该木马家族的行为特征不符；
3. **同一台机器上 v3.1.0 的 exe 从未被命中** ——
   Defender 的威胁历史里**只有这一条**记录（`Get-MpThreatDetection` 只返回一条）。

⚠️ 但这条误报本身**暴露了一个真问题**，比误报更值得记：

> **开机自启是「静默失败」的** ——
> exe 被杀毒软件隔离之后，快捷方式**依然存在**，
> 哨兵**不会说一个字**，用户只会觉得「它最近怎么不干活了」。

**处置**（本版已做）：

* 重新打包并**逐字节自检**（`--help` 首行 `哨兵 Sentinel v3.2.0`）；
* 交付时附带一份 **zip 副本**（`_构建与发布\dist\sentinel-v3.2.0-win-x64.zip`）——
  压缩包里的 exe 不会被实时扫描按「可执行文件」处理；
* 开机自启**重新复测**（快捷方式 → VBS → 2 个进程 → 端口 8000 HTTP 200）。

**用户侧要做的（需要管理员权限，本版无法代劳）**：

```powershell
# 把打包目录加进排除项（管理员 PowerShell）
Add-MpPreference -ExclusionPath 'D:\项目\<项目目录>\_构建与发布\dist'
```

或者在「Windows 安全中心 → 病毒和威胁防护 → 保护历史记录」里
把 `sentinel.exe` **还原**（还原后建议立刻加排除项，否则下次扫描还会再被隔离）。
