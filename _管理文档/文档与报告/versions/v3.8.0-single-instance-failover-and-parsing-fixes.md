## 2. 单例锁：为什么是「互斥体」而不是「绑端口」

### 2.1 选了哪个原语

| 方案 | 本版是否采用 | 理由 |
| --- | --- | --- |
| **Windows 命名互斥体**（`CreateMutexW`） | ✅ **采用** | 内核对象，创建即存在；进程死了内核**自动回收**；不占端口、不依赖网络栈 |
| 绑定特定端口 | ❌ | 端口可能被别的程序占着；而且哨兵**本来就要起 HTTP 端口**，端口语义会被污染 |

互斥体名固定为 **`SentinelDesktopSingleInstance`**，
**故意不带 `Global\` 前缀** —— 带了就跨用户会话共享，
一个用户跑着哨兵会把另一个用户的哨兵挡在门外。

### 2.2 第二个实例会发生什么

```text
CreateMutexW("SentinelDesktopSingleInstance")
  → GetLastError() == ERROR_ALREADY_EXISTS (183)
  → 拒绝：CloseHandle(自己刚建的句柄) + 打印终端提示 + 退出码 3
```

⚠️ **必须 CloseHandle 自己刚建的那个句柄** ——
`CreateMutexW` 在「已存在」时也会**返回一个有效句柄**，
不关就是**句柄泄漏**（每多双击一次漏一个）。

终端提示固定为：

```text
[SENTINEL] 哨兵已在运行中 —— 不会启动第二个实例。
```

桌面端还会弹一个 **10 秒自动关闭**的提示框
（`MessageBoxTimeoutW`，不是阻塞的 `MessageBoxW`），
免得双击之后毫无反馈。用 `SENTINEL_SINGLE_INSTANCE_DIALOG=0` 可关掉弹窗。

退出码 **3** 是专门留给「已被别的实例占着」的 ——
与「正常退出（0）」「启动失败（2）」区分得开，
脚本能一眼看出「这不是启动失败，是重复启动」。

### 2.3 建不出互斥体时怎么办

**优雅降级**：`acquire_single_instance()` 返回 `mode="unavailable"` ⇒ **放行**。

⚠️ 绝不因为锁服务出问题就把哨兵卡死 ——
「宁可漏拦一次重复启动，也不能让哨兵起不来」。

非 Windows 平台用 `fcntl.flock` + 临时目录锁文件兜底，
同一套 API、同一套语义。

### 2.4 进程内幂等

模块级 `_SINGLETON` 缓存当前进程拿到的锁，
**重复调用 `acquire_single_instance()` 不会自己把自己锁在门外**。
这很重要：`sentinel_entry.py` 和 `run_with_sentinel.py`
是**两条不同的启动路径**，都有权上锁。

### 2.5 哪些情况**不上锁**

| 命令 | 上锁 | 理由 |
| --- | --- | --- |
| `--help` / `--version` | ❌ | 只读打印，不该被拦 |
| `--scan` | ❌ | 无副作用的批处理扫描，可以并发跑 |
| 桌面 dashboard 模式 | ✅ | 这才是「哨兵本体」 |

`run_with_sentinel.py` **仅在 dashboard 模式**上锁。

## 3. 进程树同生共死：Windows Job Object

### 3.1 做法

把**哨兵自己**放进一个 Job Object：

```text
CreateJobObjectW(...)
  → SetInformationJobObject(JobObjectExtendedLimitInformation,
       LimitFlags = JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE (0x2000))
  → AssignProcessToJobObject(job, GetCurrentProcess())
```

⚠️ **为什么是「把自己放进去」而不是「把子进程放进去」** ——
「创建子进程 → 立刻 Assign」存在**竞态窗口**：
子进程可能在 `AssignProcessToJobObject` 之前就已经自己 fork 出去，
那个漏网的进程就**不在 Job 里**了。
而**子进程默认继承父进程的 Job** ——
「把自己放进去」⇒ 整棵后续进程树**自动在 Job 内** ⇒ **零竞态、零孤儿**。

### 3.2 句柄故意不关

```python
# ⚠️ 这里绝对不能 CloseHandle ——
#    一关 Job 就等于自己把 Job 关了，
#    JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE 立刻生效 ⇒ 把自己也杀了。
```

Job 句柄**故意泄漏到进程退出**（靠 OS 回收），
这是微软文档里对 `KILL_ON_JOB_CLOSE` 的标准用法。

### 3.3 失败降级

`AssignProcessToJobObject` 失败（权限不足、已在别的 Job 里等）
⇒ **优雅降级**：打日志、继续跑，**不阻断启动**。
用 `SENTINEL_JOB_OBJECT=0` 可强制关掉这个特性。

### 3.4 与 R6 的关系

R6 是「退出时**只**结束哨兵自己拉起的子进程」。
Job Object **只管哨兵自己的进程树**，
雷达挂载进来的**用户进程不在这个 Job 里**（它们是别的进程组的），
所以**不违反 R6**。

### 3.5 实测（见 §6.1）

杀父进程后，Job 里的子进程 **100% 跟着死**；
手动杀掉全部进程后**零残留**。

## 4. 托盘销毁：先 `icon.stop()` 再 `os._exit`

### 4.1 原来的坑

`_force_exit()` 里原本靠 `finally` 清理托盘，
但 **`os._exit()` 根本不会执行 `finally`** ——
托盘句柄漏掉 ⇒ 桌面留一个**点不掉、关不掉的幽灵图标**。

### 4.2 现在的做法

```python
def _force_exit(...):
    try:
        stop_tray_icon()   # ← 显式先停图标
    finally:
        os._exit(code)     # ← 然后才退
```

`stop_tray_icon()` 会**先把 `_TRAY["icon"]` 置空再 `stop()`** ——
防止重复 stop（重复 stop 会抛异常）。

另外补了 `bind_shutdown_server(server)` 与
`install_shutdown_console_handler()`：
Ctrl+C / 关闭窗口时也走同一条「先停图标再退出」的路径。

## 5. 任务二：L2 掉线热切 L3 与预算熔断

### 5.1 什么时候热切

**只在「临时性故障」时热切**：

| 类别 | 判定 |
| --- | --- |
| 异常类型 | `ConnectionError` / `Timeout` |
| HTTP 状态码 | **408 / 429 / 500 / 502 / 503 / 504** |
| 错误文本 | `timeout` / `timed out` / `超时` / `connection` / `refused` / `service unavailable` / `too many requests` … |

⚠️ **L2 只是「输出解析不出来」不热切** ——
那不是掉线，没必要为此烧云端的钱，直接回退 L1。

⚠️ `ApiError` 只有一句文本、`requests.HTTPError` 才有 `response.status_code`，
所以 `http_status_of()` 用**鸭子类型**去问，
拿不到状态码时会把 `HTTP 503：` 补进原因文本再判定 ——
否则 Ollama 抛的裸 `HTTPError` **认不出是临时性故障**。

### 5.2 热切之后发生什么

```text
L2 临时性掉线
  └─▶ L3 已启用？
        ├─ 是 ─▶ 把**原本给 L2 的载荷**原样转给 L3
        │        status = "failover"
        │        failover = True / bridged = True
        │        notice = "[WARN] L2 掉线，已自动切换至 L3 深度审查"
        │        red_light = False        ← 绝不亮红灯
        └─ 否 ─▶ 安静回退 L1（status = "unavailable"，不报错、不卡死）
```

新增常量 `CASCADE_STATUS_FAILOVER = "failover"`，
提示语固定为 `CASCADE_FAILOVER_NOTICE`。

### 5.3 ⚠️ 热切是「单盲」

热切这条路**只有 L3 一个视角**，属于**单盲**：

- **永远不亮红灯** —— 「双盲一致才升级红线」这条原则没有被破坏；
- **绝不挂起 Agent**；
- L3 说有问题 ⇒ 只出**标准级**告警。

### 5.4 预算熔断

| 维度 | 配置键 | 默认 | 含义 |
| --- | --- | --- | --- |
| 次数 | `llm.cascade.l3_fallback_limit` | 100 | 窗口内最多热切多少次 |
| 窗口 | `llm.cascade.l3_fallback_limit_seconds` | 3600 | 窗口多长（秒） |
| 金额上限 | `llm.cascade.l3_fallback_cost_limit` | 0 | 预估总花费上限（0 = 不限） |
| 单次预估费用 | `llm.cascade.l3_fallback_unit_cost` | 0 | 每次热切算多少钱（0 = 不限） |

**两个维度任意一个超了就算熔断**。熔断后：

- **放弃这次云端调用**（**不花钱**）；
- 回退 L1 纯规则；
- 发一条**严重系统告警**：`level="critical"`、
  `rule_id="cascade_l3_budget_exhausted"`、
  `severity=standard`（**不挂起**）。

⚠️ **预算检查发生在「调用之前」** ——
所以窗口内第 N 次热切会**直接被熔断**（N = 次数上限），
不会「先花了一次钱再熔断」。

⚠️ **L3 也挂时，那一次仍然计入热切次数** ——
因为 L3 **确实被调用过**（哪怕失败了），所以它会消耗预算窗口。

### 5.5 L3 也挂了怎么办

**安静回退 L1** —— `status="unavailable"`，
不抛异常、不卡死主队列。
此时 `notice` **仍然保留**热切提示语
（用户需要知道「L2 挂了，本来要切 L3，但 L3 也没成」）。

### 5.6 呈现路线：为什么走「流水」不走「告警归一化」

`normalize_alert()`（`src/gui/server.py`）是**固定键集**，
会丢掉 `cascade` / `bridged` / `single_blind` 这些字段 ——
所以热切提示**不能**走告警归一化那条路。

本版走的是「`ONTRACK_JSON` 流水 + `audit_text` / `audit_level`」：

| 场景 | `audit_level` | 渲染位置 |
| --- | --- | --- |
| 热切提示 | `warn` | 中间实时审核流水 |
| 预算熔断 | `danger` | 中间实时审核流水 |

前端新增 `auditEntryIsNotice()` ——
**带 `audit_text` 的条目在所有压缩档位逐条显示**，
不会被极限摘要合并掉（这是 v3.7.0 建立的约定）。

⚠️ **热切绝不升级告警等级** ——
流水里的 `audit_level="warn"` 只是「这是条提示」，
**不是**把 L1 的判定结果升级了。

### 5.7 设置页

`/settings/pipeline` 新增「③-1 L2 掉线热切与预算熔断」卡片：
热切开关 + 次数上限 + 窗口秒数 + 金额上限 + 单次预估费用。

## 7. 任务三：解析器盲区

### 7.1 根因

`findLogSignal()` 是「**首个命中即返回**」。
Claude 风格的**同一行**事件里 `thinking` 块排在 `tool_use` 块**前面**时，
它先撞上 thinking 节点就再也不往下找了 ⇒
**工具调用整个被顶掉** ⇒ 「日志里有工具名，看板解析不出来」。

### 7.2 修法

**工具类节点整树加权优先**：

1. 先在**整棵树**里找工具节点（`findToolSignal()`）；
2. 找不到，才回退到「首个命中优先」（`findFirstLogSignal()`）。

另外把**前后端的嵌套工具键集合统一** ——

## 12. 已知边界（说清楚，别假装没有）

- **故障切换属于「动作层」，不是「判定层」** ——
  L1 / L2 / L3 的规则、阈值、告警口径与 v3.7.0 **完全一致**。
  本版只决定「L2 挂了之后把载荷转给谁」，
  **绝不因为热切就升级告警等级**。
- **热切是「单盲」** —— 永远不亮红灯、只出标准级告警、绝不挂起 Agent。
- **金额预算是「估算值」** —— `l3_fallback_unit_cost` 是**用户自己填**的
  单次预估费用，**实际账单以服务商为准**。
  两项都为 0 时**金额维度不生效**（只按次数算）。
- **预算检查发生在「调用之前」** —— 窗口内第 N 次热切会**直接被熔断**。
- **L3 也挂时，那一次仍然计入热切次数** —— 因为 L3 确实被调用过。
- **热切只在「临时性故障」时发生** —— L2 只是「输出解析不出来」不热切，
  直接回退 L1（那不是掉线，没必要烧云端的钱）。
- **非 Windows 平台的单例锁用文件锁** —— 语义等价，
  但底层机制与 Windows 命名互斥体**不是一回事**。
- **单例锁锁的是「哨兵桌面实例」** —— `--scan` 与 `--help` / `--version`
  **不上锁**；`run_with_sentinel.py` 只在 **dashboard 模式**上锁。
- **「只有一个托盘图标」的证据口径** —— 断言的是
  「**第二次启动未新增任何进程**」，
  **不是**「进程数 == 1」（PyInstaller onefile 本来就是两个进程）。
- **工具优先遍历会下钻到首个命中节点的子树** —— 于是形如
  `{"role":"user","content":[{"type":"tool_use"}]}` 的行
  会从 "user" 改判为 "tool"；遍历**不再首个命中早退**
  （性能略降，深度受 `LOG_PARSE_MAX_DEPTH=6` 限制）；
  **一行内多个工具块**（Claude 并行调用）**只认第一个**。
- **思考类别的既有口径没变** —— 只有思考块的 Claude 行命中的是
  **外层 assistant 消息节点** ⇒ 类别仍是 "reply"（不是 "think"），
  但**正文已不再丢失**。
- **未实机验证的能力不写进文档** ——
  这一版声称的每一项都有对应的断言、截图或证据 JSON。
