# v4.0.0 —— 核心组件集成与上游插件进程树雷达

> 前期并行开发产出了四个**独立**零件（日志压缩、优先级队列、微统计、
> 上游对接分析报告），散落在归档区、互不相识。
> 这一版把它们**焊进主引擎**，并第一次能**看见第三方派发出去的 Agent**：
>
> - **三个核心组件接入 `src/core/engine.py`** ——
>   ① **日志压缩器**：L2 判定之前先把事件序列压成高信噪比「演进流」，
>      替换掉原本粗暴的截断尾巴；
>   ② **微统计检测器**：独立前置检测器，命中 `STATS_LOOP` 等
>      **当场打断**后续判定并生成告警；
>   ③ **优先级队列**：包裹本地 L2 请求，红线事件（P0）**插队**，
>      且**不阻塞**微统计与主循环；
> - **上游派发进程树雷达**（新模块 `src/proc_tree.py`）——
>   用 `psutil` 找桥接宿主 → 枚举**全部子孙** → 读 `cmdline` / `cwd`
>   匹配 Agent 特征 → 作为「已发现但在运行中」显示并**允许一键挂载** →
>   若 `cwd` 下生成了新日志则**自动绑定**为被监控日志；
>   ⚠️ **零侵入** —— 不需要上游改任何一行代码。
>
> ⚠️ **红线一字未改** —— R1–R9 与 v3.9.0 **完全一致**。
> 本版只改**判定之前**的输入与**调度顺序**，
> **不动** L1/L2/L3 的判定规则、阈值与告警口径。
> R6（退出只杀自己拉起的子进程）与 R7（不够确信就不动手武装守护者）
> 也**一字未改**。

## 2. 任务一：三个核心组件接入主引擎

### 2.1 为什么是「移动」而不是「复制」

三个组件原本躺在 `_备份与归档/` 里，而**归档区整体被 `.gitignore` 忽略**。
如果「复制」回主线，就会出现**两份事实来源** ——
以后改哪一份、哪一份才是真的，很快说不清。

所以本版用的是**移动**（`shutil.move`）：组件、它们的测试文件，
以及验收文档 `_管理文档/文档与报告/v3.8.1-优先级队列验收.md`
**一次性搬回主线**。归档区**故意保留** 4 个文件（不入库）。

### 2.2 A：日志压缩器（替换粗暴截断）

**改前**（`src/core/engine.py` 的 `IntentTracker.observe`）：

```python
summary = build_window_summary(window_events)
```

**改后**：

```python
summary = build_compressed_summary(window_events, self.goal)
```

两者的差别是**实测**出来的，不是猜的：

| | 旧 `build_window_summary` | 新 `build_compressed_summary` |
| --- | --- | --- |
| 长度（15 事件窗口） | 502 字符 | 558 字符 |
| 步号 | `第5步` | `[5]` |
| **命令文本** | `（无命令文本）` —— **丢了** | `pytest tests/test_auth.py -q` —— **保住了** |
| 工具参数 | `file_path=D:/proj/src/auth/token.py` | `D:/proj/src/auth/token.py` |
| 当前动作 | **无** | 末行 `[Current Action]: …` |
| 连续同类动作 | 逐条罗列 | 合并成 `[1] [连续读取] … 等 3 个文件 (3 进行中)` |

> ⚠️ **摘要第一行的 `[Task Goal]:` 会被剥掉** ——
> L2 的 Prompt 里**已经有一份**【原始目标】段，再塞一遍是浪费窗口。
> 剥离由 `_strip_compressed_goal()` 完成。
>
> ⚠️ **压缩失败或结果为空 ⇒ 自动降级**回 `build_window_summary`。
> 旧路径**没有删**，它是**兜底**而不是被淘汰。

### 2.3 B：微统计检测器（前置打断）

**位置**：`src/core/engine.py` 的 `process_event` 里，**L1 规则判定之后**。

为什么放在 L1 之后？因为 **R1–R9 一字未改**是硬约束 ——
红线必须**照常先出**，不能让微统计挡在前面。

但微统计**先喂数据、后发告警**：

1. 事件先喂给检测器（`self.micro_stats.observe(event)`）；
2. L1 规则照常判定，红线照常发；
3. **然后**才看微统计有没有命中；
4. 命中 ⇒ **发告警并 `return`**，后面的检测器**不再跑**。

> 归档组件自带的 `MicroStatsReporter.attach(engine)` 是
> monkey-patch 式挂载，**不打断、只写 ONTRACK_JSON**，
> 所以本版**没有采用它**，而是走上面这条「真打断」的路径。

**实测**（`logs/v400-demo/core_components_terminal.txt` 第 3 段）：

```text
第 1 次读同一个文件 → 上下文判定已跑 1 次
第 2 次读同一个文件 → 上下文判定已跑 2 次
第 3 次读同一个文件 → 上下文判定已跑 3 次
第 4 次读同一个文件 → 上下文判定已跑 3 次   ← 被打断

引擎产出的告警：verdict=STATS_LOOP 触发器=['micro_stats']
上下文判定一共跑了 3 次（挂检测器时第 4 次被**打断**）
对照组（不挂微统计）：上下文判定跑了 4 次
```

对照组跑 4 次、实验组跑 3 次 ⇒ **差的那一次确实是微统计打断的**，
不是碰巧。

### 2.4 C：优先级队列（P0 插队）

**难点**：`PriorityTaskQueue.submit` 是**异步**的，
而 evaluator / explainer 都是**同步阻塞**契约
（调用方要立刻拿到判定结果）。

解法是新增 `src/core/l2_scheduler.py` 的 `L2Scheduler.call()` ——
把队列包成同步调用：

```python
verdict = self.scheduler.call(task_id, fn, priority=PRIORITY_P1)
```

**优先级映射**（`engine._l2_priority_for_verdict()`）：

| 判定结果 | 档位 |
| --- | --- |
| 红线告警的解释请求 | `P0_RED_LINE` |
| 危险动作（漂移判定） | `P1_DRIFT` |
| 常规 / 无判定 | `P2_ROUTINE` |

**共享调度器**：漂移判定（`IntentTracker`）与红线解释
（`ExplanationWorker`）**共用同一个 `L2Scheduler` 实例** ——
这样红线的解释才能**越过**漂移判定的排队先跑完。
实测三处指向同一对象：

```text
engine.l2_scheduler          = L2Scheduler
intent_tracker.scheduler     = L2Scheduler
explanation_worker.scheduler = L2Scheduler
三者是**同一个对象**：True
```

**插队实测**：

```text
队列里已经排了 1 个任务（P2）
实际执行顺序：p2-running → p0 → p2-queued
P0 排在 P2 前面：True
```

> 注意顺序：`p2-running` 之所以还在最前，是因为**已经在跑的任务
> 不会被立刻掐掉** —— 抢占有 `preempt_after_seconds` 的门槛（见 §6.3）。

### 2.5 红线与判定口径：**没动**

| 项 | v3.9.0 | v4.0.0 |
| --- | --- | --- |
| R1–R9 | 九条 | **一字未改** |
| 漂移判定标准 | 见 v3.9.0 §2.2 | **一字未改** |
| 漂移阈值 | `threshold` | **一字未改** |
| 告警口径 | `verdict` / `reason` / `rule_id` | **一字未改** |
| v3.9.0 的确定性白名单 | 命中即放行 | **一字未改**（仍吃**原始事件**，不看压缩结果） |

① **输入**（原始事件 → 压缩演进流）；
② **调度顺序**（直连 → 排队）。

## 3. 任务二：上游派发进程树雷达

### 3.1 零侵入的思路

上游的 `agent_bridge` 是**别人家的工具**。
按「不要求上游改代码」这个硬约束，
唯一可行的路子是**从操作系统层面看**：

> 派发出去的 Agent 进程**必然**挂在某个桥接宿主进程下。
> 那就把宿主找出来，把它的**全部子孙**枚举出来，
> 按**命令行特征**认人。

### 3.2 扫描链路（`src/proc_tree.py`）

```text
find_bridge_hosts()          找宿主
  ├─ 命令行特征：python -m webui.server / webui/server /
  │               n.e.k.o_plugin_agent_bridge / agent_bridge
  └─ 目录特征  ：n.e.k.o / neko / agent_bridge / agent-bridge
        ↓
enumerate_descendants(pid)   枚举全部子孙（最深 6 层、最多 8 个宿主）
        ↓
match_agent(cmdline, cwd)    特征匹配 14 个 Agent
        ↓
find_log_for_process(cwd)    在 cwd 下找真实存在的 .jsonl / .log
        ↓
scan_process_tree()          一站式扫描 + summarize_tree() 出看板摘要
```

### 3.3 特征匹配与日志关联

`match_agent()` 返回 `(agent, label, confidence)`：

| 认出方式 | 置信度 | 说明 |
| --- | --- | --- |
| `cmdline_name` | 0.95 | 命令行里的进程名命中别名表 |
| `cmdline_script` | 0.90 | 命令行里的脚本名命中 |
| `cwd` | 0.60 | 工作目录命中（**兜底**，可信度低） |

**日志关联**遵守 **R7 的保守语义**：
`find_log_for_process()` 只认 **`.jsonl` / `.log`**、
必须是**真实存在的普通文件**、`os.scandir` **非递归**
（只看 `cwd` 下一层，不往子目录钻）。

**只有关联到真实日志才允许一键挂载**（`attachable=True`）。
没有日志的进程**只显示**成「已发现但在运行中」，**不能挂载** ——
这是 R7「不够确信就不动手」的延续。

### 3.4 GUI 接线与性能

- `src/gui/server.py`：`/api/discover` 响应新增 `processes` / `process_count`；
  已接入的进程额外标 `attached=True` 且 `state="attached"`；
- 扫描走 `await run_in_threadpool(...)`，**不堵事件循环**；
- **5 秒 TTL 缓存**（`CLOUD_PROC_SCAN_TTL`）+ **启动期后台预热**
  （`sentinel-proc-warm` 线程）；
- 前端新增 `.attach__procs` 进程列表区与 `renderProcesses(rows)`，
  状态文案改为「发现 N 个正在写入的会话、M 个上游派发进程。」。

**性能实测**（本机 345 个进程，Windows）：

| 场景 | 耗时 |
| --- | --- |
| 首次全量扫描（psutil 缓存冷） | **4192 ms** |
| 缓存热后的扫描 | **395 ms** |
| 单进程属性读取 | ~11 ms |
| 全量 342 个进程的 `proc.cwd()` | ~10 ms |

> 因为第一次要几秒，所以 `cwd` **惰性读取**：
> 先只读 `cmdline` 判宿主，**认不出**才单独读 `cwd`。

## 6. 已知边界与取舍（说清楚，别假装没有）

### 6.1 压缩后 L2 的输入格式变了 —— A/B 证据需要重跑

v3.9.0 的 A/B 证据（`REAL-FP-01` / `REAL-FP-02` /
`REAL-CTRL-01`）是**基于旧格式**做的。
本版换了摘要格式，**误报是否回升需要重新验证** ——
本版**没有**重跑那组 A/B，这一点**未验证**。

> 这是本版最需要盯的一条。压缩器保住了命令文本（原先丢的），
> 理论上信息**变多**了，但格式也确实变了。
> **不能**拿 v3.9.0 的 A/B 结论直接套到 v4.0.0 上。

### 6.2 压缩器会丢掉「非意图句」thinking

`_INTENT_VERBS_CN`（31 词）**没有「看 / 读 / 查」**这类浏览动词，
且首句被判 `_is_filler` 时**整条丢弃**。实测：

```text
extract_intent("我先看看目录结构")        -> ""
extract_intent("我先把旧构建产物清掉")      -> ""
```

引擎的 `[思考补充]` 兜底块会把原话捞回来，但：

- 该块**不参与编号**（所以步号与正文对不上）；
- 该块放在 `[Current Action]` 行**之前**，**时序不精确**；
- `fallback_intent("先看看目录")` 会返回**带语气词**的原句
  （`先看看目录`），因为句首的「先」不在剥离词表里。

### 6.3 优先级队列没有取消入口

- 超时后任务**仍会跑完**（只是调用方不等了）；
- 抢占会**真实丢掉一次模型调用**（**计费成本**）；
- 抢占只在「有更高档位在等」**且**「当前任务已跑过
  `preempt_after_seconds`（默认 10 秒）」时才发生；
- 队列**单并发**。

### 6.4 进程型 Agent 无日志时不可挂载

`POST /api/attach` 强制要求 `path` 是**已存在的日志文件**，
所以没有日志的进程只能显示成「已发现但在运行中」。
这是 R7「不够确信就不动手」的保守语义，**有意为之**。

### 6.5 `dispatch.jsonl` 只能做弱关联

那份记录里**没有** pid / exe / cmdline，
只能用 `agent + cwd + 时间窗` 关联；
**本次尚未实现**该关联。

### 6.6 N.E.K.O 桌面端宿主的特征只验了一种

实机确认的是 `N.E.K.O.exe` + `cwd=…\n.e.k.o`；
插件形态的**其他宿主变体未确认**。

### 6.7 派发是同步的

Agent 跑完即退，扫描间隔太长会**漏掉**短任务，
间隔太短则 `psutil` 开销上升。
进程树扫描首次约 **4.2 s**、热缓存约 **0.4 s**（Windows 实测），
已用**启动期后台预热** + **5 秒 TTL 缓存**缓解，
但用户若在预热完成前打开面板**仍可能等待**。

### 6.8 `AGENT_SPECS` 运行时是 14 条

内置 9 条 + `providers/` 5 条 = **14 条**，
而插件文档写的是 12 条 —— **以运行时为准**。

### 6.9 GUI 的「一键挂载」复用既有端点

复用 `POST /api/attach`（带 `agent` / `cwd` 提示做上下文），
**没有新增挂载端点**。
