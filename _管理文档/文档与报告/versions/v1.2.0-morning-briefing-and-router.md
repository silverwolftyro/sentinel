## 1. 任务一：夜间值守晨报

### 1.1 为什么需要它

半夜挂机的真实痛点不是「有没有告警」，而是：

> 早上打开电脑，面对**一夜的几百条日志**，
> 要自己拼出「昨晚到底发生了什么、烧了多少、拦住了几次」。

晨报就是那个「拼」的动作 —— 哨兵替你拼好，直接给一份 Markdown。

### 1.2 晨报里有什么

| 条目 | 数据来源 |
| --- | --- |
| 执行时长 | 引擎的 `started_at` / `ended_at` |
| 总 Token 消耗 | 引擎的 Token 台账（有 usage 用真值，否则估算） |
| 拦截的红线次数 | 告警里 `severity == "red_line"` 的条数 |
| 意图漂移次数 | 告警里 `verdict == "DRIFT"` 的条数 |
| `[STUCK]` 次数 | 告警里 `verdict == "STUCK"` 的条数 |
| `[LEAK]` 次数 | 告警里 `verdict == "LEAK"` 的条数 |
| 预估挽回的 Token 浪费 | 告警里 `token_saved` 的累加 |
| **本次用了哪些模型** | L2 路由器的 `models_used` |

### 1.3 三条原则

1. **不撒谎** —— 估算值必须**标出来**（`~` 前缀），
   绝不把估算说成账单；
2. **不添油加醋** —— 只报**发生过**的事，
   没有拦截就说「没有」，不写「守护神时刻」这种废话；
3. **不依赖模型** —— 晨报的**统计部分**是纯计算，
   模型不可用也照样能生成。

### 1.4 三个触发点

```
                   ┌────────────────────────────────────┐
   会话收尾 ──────▶│                                    │
                   │      src/core/briefing.py          │
   看板按钮 ──────▶│   采集统计 → 渲染 Markdown          │
                   │            ↓                       │
   退出信号 ──────▶│   落盘 + 终端摘要                   │
                   └────────────────────────────────────┘
```

- **会话收尾自动生成** —— `AgentSession.close()` 里调用；
- **看板【生成晨报】按钮** —— `POST /api/sessions/{id}/briefing`；
- **退出信号** —— Ctrl+C 收尾时同样会走上面那条路径。

### 1.5 ★ 看板层怎么拿到晨报而不认识引擎

架构红线之一是「**GUI 应用层不认识 `src.core.engine`**」。
所以晨报**不是**由看板自己去算的 —— 而是**回调注入**：

```python
# 启动器（认识引擎的那一层）
SessionSpec(..., briefing_callback=item.briefing_callback)

# 看板（不认识引擎的那一层）
def build_briefing(self):
    return self.briefing_callback()      # 只转发
```

这样看板层**一行引擎相关的 import 都没有**，
那条边界没有被一个新功能破掉。

### 1.6 落盘位置

```
_管理文档/文档与报告/晨报归档/晨报-2026-10-27.md
```

- 同一天**重复生成会覆盖** —— 这是有意为之：
  晨报是「当天这一班的总结」，重跑一次就该刷新一次，
  而不是堆出一堆 `晨报-2026-10-27(2).md`；
- 打包成 exe 后落在 **exe 旁边**的 `晨报归档/` ——
  用户看得见、删得掉，而不是躺在临时解包目录里。

## 2. 任务二：真实云端 API 与多级路由

### 2.1 实机验证：DeepSeek 真的通了

```
provider = openai_compatible | model = deepseek-flash
endpoint = https://api.deepseek.com/v1/chat/completions
密钥来源：已解析，长度 = 35
blocked  = (无)

explain        → 3.61 秒，degraded=False
                 detail = {title, why, touch, outcome, parts}
evaluate_drift → 2.25 秒，degraded=False
```

⚠️ 一个实测才发现的坑：**deepseek-flash 是推理模型**。
它的 `message.content` 可能是**空的**，正文在 `reasoning_content` 里
（`max_tokens` 给小了正文会被思考过程吃光）。

客户端的 `_extract_content()` 早就兼容了推理模型形态，
但 `max_tokens` 必须给够 —— 配置里默认 **1024**。

### 2.2 ★ 密钥的自动识别

用户机器上往往**早就**配好了 `DEEPSEEK_API_KEY`，
让他再单独配一个 `SENTINEL_LLM_API_KEY` 纯属多余负担。

所以密钥解析的优先级是：

| # | 来源 | 为什么排这个位置 |
| --- | --- | --- |
| 1 | 显式传入的参数 | 调用方最明确 |
| 2 | `SENTINEL_LLM_API_KEY` | 哨兵专用的通用名，**用户主动设的** |
| 3 | **配置文件里写下的** `api_key` | 用户**亲手**写的，代表「我就用这个」 |
| 4 | 按主机名自动发现的厂商环境变量 | **便利**：碰巧在机器上就生效 |

⚠️ 第 3 条排在第 4 条**前面**是刻意的：
一个「碰巧也在机器上存在」的环境变量，
不该顶掉用户**亲手**写进配置文件的密钥。

按主机名自动识别的厂商：

| 主机 | 环境变量 |
| --- | --- |
| `api.deepseek.com` | `DEEPSEEK_API_KEY` |
| `api.moonshot.cn` | `MOONSHOT_API_KEY` |
| `api.kimi.com` | `KIMI_API_KEY` |
| `open.bigmodel.cn` | `ZHIPU_API_KEY` |
| `api.siliconflow.cn` | `SILICONFLOW_API_KEY` |
| `dashscope.aliyuncs.com` | `DASHSCOPE_API_KEY` |
| `openrouter.ai` | `OPENROUTER_API_KEY` |
| `api.openai.com` | `OPENAI_API_KEY` |

### 2.3 ★ 多级路由的规则

| 触发条件 | 用哪个模型 | 为什么 |
| --- | --- | --- |
| 普通告警 / 正常审查 | `primary` | 默认路径，省钱 |
| **红线级拦截** | `fallback` | 这一刻的解释最要紧，值得多花那点钱 |
| **连续漂移** | `fallback` | 连续漂移说明 Agent 已经跑偏，判定本身要准 |

`ModelRouter` 本身也是 `LLMProvider`，所以**到处都能替换**：

```python
router = ModelRouter(
    primary=OllamaClient(model="qwen2.5:7b"),
    fallback=OpenAICompatibleClient(
        base_url="https://api.deepseek.com", model="deepseek-chat"
    ),
)
```

### 2.4 ★ 实机验证：路由真的会切换

**本地 `qwen2.5:7b` + 真实云端 `deepseek-flash` 同台跑：**

```
[普通告警] provider=ollama model=qwen2.5:7b           7.1s
[红线级  ] provider=openai_compatible model=deepseek-flash  5.1s   ← 升级了
[漂移#1  ] provider=ollama model=qwen2.5:7b  drift=True  6.8s
[漂移#2  ] provider=openai_compatible model=deepseek-flash 1.6s  ← 升级了
[漂移#3  ] provider=openai_compatible model=deepseek-flash 1.1s

models_used : openai_compatible:deepseek-flash ×2、ollama:qwen2.5:7b ×1
```

而且**云端的理由明显更准**：

| 模型 | 对同一场景的判定理由 |
| --- | --- |
| 本地 7B | 「删除测试文件并安装新依赖与改错别字无关」 |
| 云端 | 「第1步起删测试、装依赖、重写src，**完全背离**只改README错别字的目标」 |

### 2.5 ★ 两条硬约束

1. **云端挂了不能没有解释。**
   `fallback` 降级（超时 / 鉴权失败 / 熔断 / 直接抛异常）时，
   自动退回 `primary` —— 红线事件**绝不能**因为「云端抽风」而没有解释；
2. **降级绝不等同于有问题。**
   漂移判定失败一律算「**没漂移**」，连续计数归零
   （与引擎里 `IntentTracker` 的口径一致，红线 R4）。

### 2.6 配置

```yaml
llm:
  provider: "ollama"          # 主力
  model: "qwen2.5:7b"
  routing:
    enabled: true
    escalate_on_red_line: true
    drift_escalate_threshold: 1     # 第二次连续漂移由强模型来判
    fallback:
      provider: "openai_compatible"
      base_url: "https://api.deepseek.com"
      model: "deepseek-chat"
      api_key_env: "DEEPSEEK_API_KEY"
      timeout: 60
      max_tokens: 1024               # ⚠️ 推理模型至少给 1024
```

## 3. 任务三：一键复制纠偏提示

### 3.1 两种按钮

| 按钮 | 什么时候出现 | 提示讲什么 |
| --- | --- | --- |
| 【复制纠偏提示】 | 非红线告警（`[STUCK]` / `LOOP` / 漂移 / 一般危险命令） | 「你跑偏了，回到任务目标」 |
| 【复制拦截原因】 | **红线级**拦截 | 「这一步不可逆，换个可逆的做法」 |

### 3.2 提示里装了什么

```
【哨兵纠偏提示 · STUCK】

哨兵在监控你的运行过程。刚才这一步可能已经偏离了原始任务，
请先停下来确认方向，再继续。

## 触发情况
- 判定：`STUCK`（规则 `context_stuck`）
- 哨兵判定原因：[STUCK] 测试连续失败3次，Agent 可能卡住了
- 相关操作：`python -m pytest -q`
- 原始任务目标：重构 auth 模块并修复登录 bug

## 哨兵的解读
Agent 连续三次运行 pytest 都失败，但从未修改被测文件 —— …

## 最近几步在干什么
1. tool_call：`python -m pytest -q`
2. tool_result（失败）
…

## 请这样做
1. 先用一句话复述你当前认为的任务目标，看看它和上面的目标是否一致。
2. 如果已经跑偏：…**换一个思路** —— 不要重复刚才那一步。
…
```

### 3.3 为什么在后端生成

前端拿到的告警是**归一化过的子集**（没有 `context_history`、没有 `drift.goal`）。
而「最近几步在干什么」恰恰是纠偏提示里最有用的一段。

所以提示由**后端**生成（那里才有完整上下文），
前端只负责取字符串、复制到剪贴板、弹个 toast。

### 3.4 剪贴板的两条路

- 优先 `navigator.clipboard.writeText()`；
- 非安全上下文（http + 非 localhost）里 Clipboard API 不可用 ——
  退回 `document.execCommand("copy")`。

### 4.3 ★ 打包后路径的三个坑

单文件程序运行时，PyInstaller 把程序解包到**临时目录**。
凡是「解包目录里一关就没」的东西，都必须重新定位：

| 东西 | 打包前 | 打包后 |
| --- | --- | --- |
| 模板 / 静态资源 | `<项目根>/src/gui/…` | `<解包目录>/src/gui/…`（**内置**） |
| 配置文件 | `<项目根>/config/config.yaml` | **`<exe 旁边>/config/config.yaml`** |
| 日志 | `<项目根>/logs/` | **`<exe 旁边>/logs/`** |
| 晨报归档 | `<项目根>/…/晨报归档/` | **`<exe 旁边>/晨报归档/`** |

「exe 旁边」这个位置是刻意的：那是用户**看得见、删得掉**的地方。

### 4.4 体积控制

- `--onefile` 单文件；
- 显式排除 `tkinter` / `matplotlib` / `numpy` / `pandas` / `scipy` /
  `PIL` / `PyQt*` / `IPython` / `pytest` / `torch` 等用不上的大库；
- 显式声明**隐藏导入**（`src.core.briefing`、`src.llm.router`、
  `src.adapters.*`、`uvicorn.*.auto` …）——
  这些都是**函数内动态导入**的，静态分析有时会漏；
  漏掉的代价是「打包成功但运行时才崩」，那是最糟的一种。

## 5.5 实机撞出来的 5 个 bug（都已修）

【复制纠偏提示】这个功能在**真实浏览器里点下去是「没反应」的**。
查下去发现不是一处，而是五处 —— 记在这里，因为它们有个共同点：
**单元测试全绿，但真实用户就是用不了。**

| # | 症状 | 根因 | 修法 |
| --- | --- | --- | --- |
| 1 | `[STUCK]` / `[LEAK]` 对扁平日志**永不触发** | `_parse_tool_call` 会拆嵌套的 `tool_call`，`_parse_tool_result` 却**不拆** `tool_result` —— 「失败了没有」被丢掉 | 与 `_parse_tool_call` 对称地拆一层 |
| 2 | 按钮**点了没反应** | 告警列表每 5 秒被**清空重建**，用户正要按的按钮被抽走重建 | 引入渲染签名：**列表没变就不重建** |
| 3 | 某些卡片点了没反应 | 老版本写的告警行**没有 `alert_id`** —— 卡片无从定位 | `normalize_alert` 按「时间戳 + 规则 + 原因摘要」合成**稳定** ID |
| 4 | 单会话模式下 404 | 前端无会话分支打的 `/api/alerts/{id}/correction` **没有后端** | 补上这条路由 |
| 5 | 守护者没武装时按钮**灰的** | `refreshGuardianButtons()` 把操作区里**所有**按钮一起禁用 | 禁用干预按钮时**排除**复制按钮 |

第 1 条最严重 —— 它让 mcode 的**死循环检测形同虚设**，
而且从日志上看一切正常（只是从来没报过警）。

补完这 5 条后的实机结果（真实浏览器 + 真实系统剪贴板）：

| 点的按钮 | 卡片 | 剪贴板 |
| --- | --- | --- |
| 【复制纠偏提示】 | `[STUCK] context_stuck` | 409 字 |
| 【复制拦截原因】 | 红线级 `catastrophic_mass_delete` | 619 字 |
| 【复制拦截原因】 | **打包版 `sentinel.exe` 的看板** | 612 字 |

## 6. 已知限制

- **云端 API 要花钱** —— 路由只在「该用强模型的时候」才用，
  但红线多的话调用量也会上去；
- **推理模型会吃 token** —— `deepseek-flash` / R1 这类把 token 花在「思考」上，
  `max_tokens` 给小了正文会被截空；
- **晨报里的 Token 是统计值** —— 有 usage 时是真值，没有时是估算（标 `~`）；
- **「挽回的 Token」是估算** —— 「本来还要跑 10 步」是经验值；
- **exe 首次启动要解包**，约 1 秒；
- **钉钉 / 飞书 / Bark 的真实服务仍未打过**；
- **Claude 适配器仍未实机验证**（本机没装 `claude` CLI）。
