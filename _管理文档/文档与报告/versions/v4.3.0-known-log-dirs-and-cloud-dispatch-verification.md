# v4.3.0 —— 已知日志目录映射与上游派发实机验证

> v4.2.0 把雷达的「慢/待验证」阈值降到 10 秒，代价是**误报变多**。
> 这一版解决它，并**真刀真枪**验证了一次对上游插件的派发接管。
>
> - **已知会话日志目录**（`log_dirs`）—— Agent CLI 常常**不往自己的
>   cwd 写日志**：Claude Code 写 `~/.claude/projects/<项目slug>/`，
>   Codex 写 `~/.codex/sessions/<年>/<月>/<日>/`，
>   OpenCode 写 `~/.local/share/opencode/log/`。
>   雷达以前**只查 cwd**，找不到就把进程标成「疑似挂起」—— 假阳性。
>   现在清单里登记了已知目录，cwd 下没有就再去那里找（**递归、有界**）。
> - **实机验证上游派发接管** —— 真的起了上游的控制台
>   （`python -m webui.server`，纯标准库），通过它的 HTTP 接口派发了一个
>   **OpenCode** 任务：Agent 真跑完了（exit 0 / 6.3 秒 / 有真实输出），
>   哨兵雷达**第 1 次扫描就命中**了那个子进程 —— 名字、PID、工作目录全对，
>   日志在**工作目录之外**被找到，徽章显示「运行中 · 可接入」而不是「疑似挂起」。
> - **挂载链路实测** —— 受控挂载一个 mcode 格式的 JSONL 会话，
>   追加一行 `rm -rf /` 的工具调用，**L1 规则当场触发 DANGEROUS 告警**。
>
> ⚠️ **能力边界必须说清楚** —— 三条实测结论：
> 1. **本机只装了 opencode**（上游 14 个 Agent 里唯一 `ready=True` 的，
>    v2.0.18）。Claude / Codex **没装**，而 `codex` **根本不在**上游的
>    14 个 Agent 列表里 —— 任务书写的「Claude 或 Codex」在本机**两个都做不了**，
>    故改用 opencode，并在此如实说明。
> 2. **OpenCode 的会话存在 SQLite 里**（`opencode.db`），不落 JSONL；
>    `opencode.log` 是 **key=value 调试日志**，不是会话流。
>    所以挂上它**收不到 Agent 对话事件**（实测 `streams=[]`）——
>    「挂得上」不等于「收得到流」。会话级的 L1/L2 对 opencode **不成立**。
> 3. **L2 跑不了** —— L2/L3 需要本机推理引擎（`http://127.0.0.1:8888/v1`），
>    本机没有 → 事件被标成 `ENGINE_OFFLINE`，L2 不发起调用。
>    这是**环境缺口**，不是代码缺陷；L1（规则层）不依赖 LLM，实测正常。
>
> ⚠️ **红线一字未改** —— R1–R9 与 v4.2.0 **完全一致**。
> 本版只改「日志在哪找」与数据登记，不动 L1/L2/L3 的判定规则与阈值。

## 2. 任务一：已知会话日志目录

### 2.1 数据层

`src/agents/cloud_agents.json` 的每条 Agent 都多了一个 `log_dirs` 字段：

```json
{
  "id": "claude",
  "label": "Claude Code（Anthropic）",
  "binary": "claude",
  "mode": "flag",
  "prompt_flag": "-p",
  "model_flag": "--model",
  "json_args": ["--output-format", "json"],
  "aliases": [],
  "auth_patterns": [],
  "fail_patterns": [],
  "login_hint": "",
  "install_cmd": "",
  "install_hint": "",
  "notes": "",
  "hints": [],
  "log_dirs": ["~/.claude/projects"],
  "log_dirs_note": "已登记的已知会话日志目录。",
  "json_shape": "document",
  "json_shape_note": "stdout 整体是一个 JSON 文档"
}
```

**只有 4 条非空**，每条都有依据：

| Agent | 已知会话日志目录 | 依据来源 |
| --- | --- | --- |
| `claude` | `~/.claude/projects` | `src/radar.py` 模块文档 + 既有默认扫描根；`_构建与发布/scripts/verify_v240_exe_pid.py:164` 也用 `.claude/projects/beta` 造过夹具 |
| `codebuddy` | `~/.codebuddy/projects`、`~/.codebuddy/sessions` | **本机实况**（`~/.codebuddy/projects/<项目slug>/*.jsonl` 真实存在） |
| `dsh` | `~/.dsh/sessions` | `src/radar.py:255-256` 的默认扫描根 + 本机实况 |
| `opencode` | `~/.local/share/opencode/log` | **本机实况**（`opencode.log` 真实存在） |

其余 **10 条是空数组** —— 空数组表示「**还没查清楚**」，不是「没有日志」。
每条都带一句 `log_dirs_note` 说明这一点。
**凭印象填一个不存在的路径，只会让雷达每次扫描白跑一圈** —— 所以没填。

> `schema` 仍是 **1**：加一个可选字段属**向后兼容**，不递增版本号。
> 老清单（没有 `log_dirs`）照样能加载 —— `_require_str_list` 对缺失键返回空元组。

### 2.2 查找层

```python
def find_log_for_process(
    cwd, agent="", *, max_age_seconds=3600.0, now=None, log_dirs=(),
):
    ...
    # 1) 先看 cwd —— Agent 直接在自己工作目录里写日志的情况最常见
    root = str(cwd or "").strip()
    if root:
        found = _scan_log_dir(root, wanted, window, reference)
        if found:
            return found

    # 2) cwd 下没有，再看该 Agent 登记的 log_dirs
    for raw_dir in log_dirs or ():
        ...
        found = _scan_log_tree(expanded, wanted, window, reference)
        if found:
            return found
    return ""
```

**为什么必须递归**：Claude Code 的会话日志是
`~/.claude/projects/<项目slug>/<会话>.jsonl` —— 文件在根目录**下面一层**；
Codex 的是 `~/.codex/sessions/<年>/<月>/<日>/<会话>.jsonl` —— **四层**。
只看一层是找不到的，所以 `LOG_DIR_MAX_DEPTH = 4`。

**三个必须有界的理由**（用户家目录可能很大）：

| 约束 | 值 | 理由 |
| --- | --- | --- |
| `LOG_DIR_MAX_DEPTH` | 4 层 | 够到 Codex 的最深层，同时挡住更深的目录树 |
| `LOG_DIR_MAX_ENTRIES` | 4000 个目录项 | 装了几个月 Agent 的机器上 `~/.claude/projects` 可能有几百个项目目录。**宁可少找到一个，也不能把雷达拖慢** |
| 跳过隐藏目录 + `node_modules` | — | 那些地方没有会话日志，扫进去纯属浪费预算 |

**压缩日志一律排除**：`.zstd` 的会话日志（DeepSeek harness 用的）
**不能接入**实时审查 —— 跟读器记的是原始字节偏移，压缩流没法按字节增量读，
挂载接口本来就明确拒绝它。那就不该把徽章标成「可接入」，
否则用户点进去才吃闭门羹。压缩后缀从 `src.radar` 取（**单一事实来源**）。

## 3. 任务二：实机验证上游派发接管

### 3.1 怎么验的

1. 起了上游自己的控制台：`python -m webui.server --port 8787`
   （**纯标准库**，`from bridge.*` 导入，**没有**依赖宿主 SDK，所以能独立跑）；
2. `GET /api/agents` 确认 14 条路由，其中 **opencode 是唯一 `exists=True` / `ready=True`** 的
   （v2.0.18）；
3. 造一个**空的**工作目录（里面一个 `.jsonl` / `.log` 都没有）——
   这样 cwd 查找**必然失败**，只有 log_dirs 能救；
4. `POST /api/dispatch` 真派发一个 opencode 任务
   （上游的接口是同步阻塞的，所以放在后台线程里派）；
5. **并发**地反复跑哨兵的 `scan_process_tree()`，看雷达能不能扫到那个子进程。

### 3.2 结果

上游的派发**真的跑完了**：

```json
{
  "ok": true,
  "agent": "opencode",
  "label": "OpenCode",
  "exit_code": 0,
  "timed_out": false,
  "needs_login": false,
  "command": "D:\\OpenCode\\bin\\opencode.EXE run <task>",
  "output": "只读审计监控是一种安全实践，只对系统数据进行只读（不修改）的访问和留痕……\n\n停下了。",
  "stderr": "> build · flint-40b-free",
  "seconds": 6.3
}
```

雷达**第 1 次扫描就命中**：

```json
{
  "pid": 38620,
  "agent": "opencode",
  "label": "OpenCode",
  "cwd": "C:\\Users\\alpha\\AppData\\Local\\Temp\\v430-cloud-dispatch-9b9raw4e",
  "log_path": "C:\\Users\\alpha/.local/share/opencode/log/opencode.log",
  "attachable": true,
  "confidence": 0.95,
  "matched_by": "cmdline_name"
}
```

**决定性的 A/B**（同一个进程、同一个时刻，两种查找策略）：

| 策略 | 结果 |
| --- | --- |
| v4.2.0 行为（只查 cwd） | **(空)** → 会被标成「疑似挂起」 |
| v4.3.0 行为（cwd + log_dirs） | `C:\Users\<用户名>\.local\share\opencode\log\opencode.log` → **误报消除** |

日志的 mtime 是 `16:22:55` —— 就在派发期间，**确实是 Agent 正在写的那个文件**。

### 3.3 ⚠️ 「2 秒内扫到」的诚实口径

裸调 `scan_process_tree()` 时：

| 扫描 | 耗时 |
| --- | --- |
| 第 1 次（**冷**） | **2698 ms** |
| 第 2 次起 | **~90 ms** |

冷启动那 2.7 秒是 psutil 缓存冷 + 目录扫描。
哨兵 GUI 侧有 **v4.0.1 的预热机制**（`_warm_cloud_process_scan()`），
实测 `GET /api/discover` 的 `process_scan_elapsed_ms` 是 **111.6 ms** ——
**接上 GUI 之后不满足「裸调 2 秒内」，但满足「用户感知 2 秒内」**。
这个区分必须说清楚，不能拿裸调数字当「2 秒内扫到」。

### 3.4 挂载后的 L1/L2 边界

| 会话 | watch_path | 事件流 |
| --- | --- | --- |
| `attach-a7a8189defa0`（MCode） | `~/.minimax/v2/sessions/.../messages.jsonl` | events=29、ontrack=30、**goal 自动提取成功** |
| `attach-a7bca86091a6`（OpenCode） | `opencode.log`（key=value 调试日志） | streams=[]、tokens={} —— **收不到事件** |

**「挂得上」不等于「收得到流」。** OpenCode 把会话存在 **SQLite** 里
（`opencode.db`），`opencode.log` 是调试日志 —— 挂上它**不会**产生 Agent 对话事件。
会话级的 L1/L2 对 opencode **不成立**。

为了把「L1 能不能收流」单独验清楚，做了一次**受控测试**：
造一个临时的 mcode 格式 JSONL（不碰任何用户真实文件）→ 挂载 →
追加一行 `rm -rf /` 的工具调用：

```
挂载 ok = True  session.id = attach-c554db08a87e
>>> 追加一行高危工具调用 rm -rf / ...
追加后计数: {"DANGEROUS": 1}
alert_total = 1
  流 default: alerts=1 ontrack=0
=> L1 规则**收到了日志流**：DANGEROUS 告警已触发。
```

**L1（规则层）实测正常。**

**L2 跑不了**：L2/L3 需要本机推理引擎（`http://127.0.0.1:8888/v1`），
本机没有 → 事件被标成 `ENGINE_OFFLINE`，L2 不发起调用。
这是**环境缺口**，不是代码缺陷 —— L1 不依赖 LLM。
