## 2. 判定口径未变的机器证明

「本版不改判定规则」这句话，v3.6.1 的教训是**不能只写在文档里**——
所以这一版把它做成了**会变红的测试**。

### 2.1 逐条比对（一次性实测）

用 Python 的 `ast` 模块从 **HEAD（v3.6.1）** 的 `src/rules/basic.py` 里
精确取出 `DEFAULT_DANGEROUS_COMMANDS`（避开正则字符串里的转义误伤），
再与 v3.7.0 的 `src/rules/registry.py` 的 `BUILTIN_DANGEROUS_RULES`
**逐条、按顺序**比对：

```text
HEAD 正则条数 = 18
当前清单条数 = 18
✅ 18 条正则逐字一致（含顺序）
```

### 2.2 固化成三条守卫用例

`tests/test_v370_cascade_rules_presentation.py` 第九节：

| 用例 | 钉住什么 |
| --- | --- |
| `test_十八条高危正则逐字未动` | 清单里的 18 条正则与 v3.6.1 基线**逐字一致**（含顺序） |
| `test_判定引擎仍在用同一批正则` | 判定引擎**实际编译**的正则也一致（不只是清单显示一致） |
| `test_红线类别判定键未变` | 四个红线类别键（`root_delete` / `mass_delete` / `disk_wipe` / `remote_exec`）没变 |

⚠️ 基线是**手抄的快照**，不是「当前实现」的复制品 ——
它的作用是：一旦有人动了某条正则（哪怕只改一个 `\s`），
测试立刻失败，逼着改动者显式声明「我改了判定规则」。

**反向验证**（实测，不是推断）：把 `dangerous.sudo` 的正则从
`\bsudo\b` 改成 `\bsudo(?:\s|$)` 后重跑 ——
**三条用例同时变红**（外加原有的 `test_关键高危正则还在` 一条），
改回后全绿。

### 2.3 红线检测器本体：一个字都没动

`git diff src/rules/basic.py` 的**删除行**里，
`CatastrophicDetector` 的方法体**一条都没有** ——
只多了两处**配置层**的改动：

1. `DEFAULT_DANGEROUS_COMMANDS` 改为从 `registry` 派生
   （正则内容与顺序一字未改，见 §2.1）；
2. 新增 `_effective_categories()` ——
   生效类别 = `rules.catastrophic.categories` 白名单
   **∩** 规则清单里没被关闭的红线类别。

第 2 条在**默认配置**下等价于 v3.6.1：
四个类别全开、白名单也是四个 ⇒ 交集还是四个。

## 3. 任务一：L1 规则管理页

### 3.1 为什么要有这一页

v3.6.x 的高危规则是一张写死在 `src/rules/basic.py` 里的正则表，
用户能改的只有「整体开 / 整体关」。
这一版把**每一条**都摊开，让用户逐条决定：

- **要不要它管**（关掉）；
- **管到什么程度**（拦截 / 仅记录）。

### 3.2 规则清单长什么样

表格共 **23 条**，顺序固定为「红线 → 高危 → 死循环」：

| 来源 | 条数 | id 前缀 | 举例 |
| --- | --- | --- | --- |
| 红线级（catastrophic） | 4 | `catastrophic.` | `catastrophic.root_delete` |
| 高危命令（dangerous） | 18 | `dangerous.` | `dangerous.sudo` |
| 死循环（loop） | 1 | `loop.` | `loop.repeat_read` |

每行显示：**规则名 / 匹配内容 / 风险等级 / 动作 / 开关**。

⚠️ `rule_id` 契约**不变**：高危仍是 `"dangerous_command"`、
红线仍是 `"catastrophic_<category>"`、死循环仍是 `"repeat_read_loop"`；
清单 id 走**新增**字段 `rule_entry_id`，老逻辑照旧认老 id。

### 3.3 两种动作的区别（不是同一个开关）

| 动作 | 命中时 | 会不会挂起进程 |
| --- | --- | --- |
| **拦截**（默认） | 出告警 | 红线级**会**（`red_line_only` 策略下） |
| **仅记录** | 出告警，严重度降为 `standard` | **不会** |

「仅记录」的实现方式是把告警的 `severity` 降级，
并额外打上 `rule_action="log"` / `log_only=True` 两个字段 ——
**不是**在前端藏一行，告警照样进日志、照样能在看板看见。

⚠️ 关掉死循环规则后，**连状态都不再累积**
（不然关了规则还在偷偷记状态）。

### 3.4 导入 / 导出

- **导出**：`GET /api/rules/export?format=json|yaml`
  返回**纯规则数组**（每条自带 `enabled` 与 `action`），
  文件名 `sentinel-rules.json` / `sentinel-rules.yaml`；
- **导入**：`POST /api/rules/import`，接受上面那份文件，
  也接受**只写规则本体**的增量载荷；
- **无损**：「导出 → 不改一个字 → 导回」之后，
  每条规则的开关状态与动作**都还在**。

⚠️ **自定义规则只能是「高危命令」** —— 红线与死循环的判定是
**结构化**的（路径形状、跨事件状态机），一条正则表达不出来。
导入非 `dangerous` 的规则会**明确报错并跳过**，
而不是收下一条永远不生效的规则。

### 3.5 红线类别是唯一权威 UI

v3.6.x 的设置页里有 **8 个红线 checkbox**，
其中「提权 / 网络变更 / 清历史 / 读凭据」这四个类别
**从来就没有**对应的判定逻辑 —— 勾上也不生效。
这一版把整块死控件**移除**，规则页只列真实存在的 23 条。

红线类别的 `enabled` 必须**同时**满足三件事：

1. 不在 `rules.disabled_rules` 里；
2. 在 `rules.catastrophic.categories` 白名单里；
3. 红线总开关 `rules.catastrophic.enabled` 开着。

保存时前端把启用的红线类别**回写** `rules.catastrophic.categories`。

## 4. 任务二：级联路由控制阀

### 4.1 三个独立开关

| 开关 | 配置键 | 关掉之后 |
| --- | --- | --- |
| L1 | `rules.enabled` | 不做规则判定 |
| L2 | `llm.cascade.l2.enabled` | **L2 根本不装配**（省显存），级联通路直接由 L3 复核 |
| L3 | `llm.cascade.l3.enabled` | 级联通路退回「单层」模式 |

⚠️ 「关掉 L2」**不是**「装配了但不用」——
`build_cascade_provider()` 在 L2 关闭时**完全不创建** L2 客户端，
本地模型**一点显存都不占**。

### 4.2 L2 → L3 桥接

前置条件：**L2 关 + L3 开 + `bridge_l1_to_l3` 开**。
三个条件缺一，桥接**不成立**（`CascadeRouter.bridging` 返回 `False`），
页面上的开关会**如实显示成不可用**。

打开之后：

```text
L1 命中的事件  ──┐
                  ├──▶ 云端 L3 复核 ──▶ 结论
L1 没命中的事件 ─┘   （bridge_l1_to_l3 打开时才走上面这条）
```

### 4.3 ⚠️ 单盲边界（必须说清楚）

桥接这条路**只有 L3 一个视角**，属于**单盲**。所以：

- **永远不亮红灯** —— 「双盲一致才升级红线」这条原则没有被破坏；
- L3 说有问题 ⇒ 只出**标准级**告警（`rule_id="cascade_bridge_l3"`，
  带 `bridged=True` / `single_blind=True` 标记），**绝不挂起**；
- 只送**「工具调用」事件** —— 思考过程与纯文本**不上云**；
- `CascadeResult.bridged` 与 `status="bridged"` 把单盲路径与
  正常双盲路径**区分开**，前端不会把两者混为一谈。

### 4.4 L1 命中后的拦截策略

| 取值 | 含义 | 默认 |
| --- | --- | --- |
| `red_line_only` | 只拦红线级（高危只告警） | ✅ **默认** |
| `suspend` | 高危命令命中就**直接挂起**（死循环不挂起） | |
| `alert` | 只告警，**绝不挂起** | |
| `escalate` | 先不挂起，等 L2 / L3 双盲结论再定 | |

⚠️ 默认值 `red_line_only` **与 v3.6.1 行为等价** ——
升级到这一版，守护者的动作**一个字都没变**。

## 5. 任务三：极限摘要算法

### 5.1 两个 0-100 档位

| 滑条 | 配置键 | 管谁 |
| --- | --- | --- |
| 右侧「被监控日志」极限压缩 | `presentation.log_compression` | 右侧日志区 |
| 中间「实时审核流水」极限压缩 | `presentation.audit_compression` | 中间流水区 |

**日志档位分段**

| 档位 | 呈现 |
| --- | --- |
| 0–30 | 纯代码（原始 JSON，带高亮） |
| 31–69 | 自然语言（藏掉 arguments 与 tool_result） |
| 70–99 | 高度摘要（只留问题 + 回答 + 核心工具调用） |
| **100** | **极限摘要** —— 相邻同类动作**真的合并** |

**流水档位分段**

| 档位 | 呈现 |
| --- | --- |
| 0–39 | 完整（含思考过程） |
| 40–69 | 精简（省略思考） |
| 70–89 | 结论（只留核心上下文 + 告警 + 结果） |
| **90–100** | **极限** —— 只留结论与危险动作，**连续普通流水合并成计数行** |

### 5.2 100 档的合并示例

连续 5 次读同一个文件：

```text
[读取] core/auth.py 等 5 个文件
```

连续 3 次执行命令：

```text
[执行] npm test 等 3 条命令
```

合并规则（**三条都缺一不可**）：

1. **相邻** —— 中间夹了别的动作就断开；
2. **同动作类别** —— 读 / 写 / 执行 各自成段；
3. **挖得出目标** —— 认不出目标的那条**不合并**
   （宁可多显示一行，也不显示一句没有信息量的「[读取] 等 5 个文件」）。

单位按动作类别走：读 / 写用「个文件」，执行用「条命令」。
目标保留**尾巴**（路径）/ **开头**（命令），超过 64 字截断。

### 5.3 动作分类的匹配顺序

**写入 → 执行 → 读取**。

⚠️ 顺序不能反：`search_replace_content` 名字里有 "content"，
若先按「读取」匹配就会被误判成读文件。

### 5.4 看板不再有滑条

主看板右侧日志顶部那根滑条**整条移走**，
只留一句「渲染档位见『设置 › 流水线控制 › 呈现与摘要』」。

- 档位来自 `GET /api/presentation`（服务端配置，全局口径）；
- 看板初始化时读一次，之后每 **10 秒**轮询一次；
- ⚠️ **不再**用 `localStorage` 存档位；
  但**布局比例**（面板宽高）**仍然**存 `localStorage` ——
  那是「这台屏的偏好」，不是「全局口径」。

## 7. 实机演示揪出的三个真缺陷

⚠️ **这一节是本版最该被读的部分。**

三个缺陷**全是实机演示时真跑出来的** ——
**单测当时全绿，真机就是不对**。
它们已全部修掉，并各自补了会变红的回归用例。

### 7.1 缺陷一：配置写回器把 YAML 写坏了

| 项 | 内容 |
| --- | --- |
| 现象 | 保存规则后热重载降级；档位回落到 40/60；规则保存**看着成功了其实没生效** |
| 根因 | 老写回器把「与父键**同列**的缩进式块序列」当成「父键的值块已经结束」，于是把**已有**列表当成「不存在」→ **插入**一份新列表、旧列表留在原地 → **同一个键出现两次** → `ParserError: while parsing a block mapping` |
| 修法 | 新增 `_value_block_end()`，把「与父键同列的缩进式块序列」算进父键的值块；接入 `_rewrite_scalar()` / `_rewrite_list()` / `_locate()`；**保留原文件缩进风格** |
| 回归 | `tests/test_v370_cascade_rules_presentation.py` 第八节 4 条用例；**有效性已实证**（`git stash push -- src/config_loader.py` 还原旧版 → 独立探针脚本复现 `ParserError` → `git stash pop` 恢复 → 探针输出「✅ YAML 可解析」） |

### 7.2 缺陷二：极限摘要的 SSE 新行不合并不了

| 项 | 内容 |
| --- | --- |
| 现象 | 100 档位下，**首屏**渲染时合并是对的（`redrawLogLines()` 整块重画）；但 SSE **推来的新行**永远合不起来 |
| 根因 | SSE 推送路径**逐行 append**，合并算法只在 `redrawLogLines()`（整块重画）时才跑；而合并是「**全局相邻**」关系，新行可能并进上一组尾巴、或把上一组打断 |
| 修法 | 极限档下 SSE 每来一批 → **整块重画** `redrawLogLines()`；非极限档保持原快速路径 |
| 理由 | 极限档 DOM 本就只留几行，重画成本可接受；而「逐行 append」在数学上**永远合不起来** |
| 回归 | 夹具新增 1 条**结构守卫**（明确标注不是行为测试），守住 `appendLogLines()` 里的 `"extreme"` 分支 + `redrawLogLines()` 调用 |

### 7.3 缺陷三：看板解析器不认 mcode 的工具调用

| 项 | 内容 |
| --- | --- |
| 现象 | 看板右侧日志**识别不出** mcode 的工具调用行 |
| 根因 | `logToolName()` 的 keys 里**没有** `tool_call` / `toolCall`；`logToolArguments()` 的嵌套查找也没有 `node.tool_call \|\| node.toolCall` |
| 取向 | **不改服务端推送形态**，让前端解析器认识 mcode 的 `tool_call` / `toolCall` |
| 回归 | 夹具新增 6 条用例（mcode 旧协议 / v0.6 / Claude 风格各 2 条） |

## 12. 已知边界（说清楚，别假装没有）

- **桥接是「单盲」** —— 永远不亮红灯，只出标准级告警、绝不挂起；
- **桥接只送「工具调用」事件** —— 思考过程与纯文本不上云；
- **关掉 L2 = 失去本地过滤** —— 每个事件都要花钱问云端；
- **自定义规则只能是「高危命令」** —— 其余类型导入时明确报错跳过；
- **100 档的合并只合并「相邻 + 同动作 + 挖得出目标」的条目**；
- **看板档位是 10 秒轮询**，不是实时推送；
- **「放行给 L2 二次判断」要求级联开着** ——
  L2 关着时它等价于「只告警不挂起」；
- **Claude 风格的混合行有一个既有边界** ——
  同一行里 `thinking` 在前、`tool_use` 在后时，
  `findLogSignal` 会**先命中 thinking 节点**，
  于是这一行的工具调用**不被提取**。
  ⚠️ 这是 **v3.6.0 的既有设计**，**本版不改**（改了会牵动核心上下文判定）；
- **未实机验证的能力不写进文档** ——
  这一版声称的每一项都有对应的断言、截图或证据 JSON。
