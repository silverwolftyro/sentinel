# v4.1.0 —— 吸收上游资产与 Agent 配置数据化

> 《第三方 Agent Bridge 资产盘点》报告建议：先做成本最低、收益最高的
> 「阶段 A（数据层）」与「阶段 B（派发层）」，把哨兵的 Agent 扩展机制
> 彻底**数据化**，暂不做高成本的多格式解析器，也**不去改上游的代码**。
> 这一版就是那两步的落地。
>
> - **Agent 配置数据化** —— 新增 `src/agents/` 包。
>   14 个上游 Agent 的可执行名、启动形态、参数模板、鉴权措辞、
>   登录指引全部登记在 `src/agents/cloud_agents.json` 里。
>   **新增一个 Agent = 加一条 JSON，不用改一行 Python。**
> - **别名补齐 8 条** —— 此前雷达只认得出内置 9 个 Agent 的 8 条别名，
>   `gemini`（`gcli`）、`command-code`（`cmdc`）、`step`（`stepcode`）、
>   `pi`（`pi-coding-agent`）等**一概认不出**。
>   现在别名表从 8 条变成 **16 条**。
> - **派发层加固** —— 吸收上游 `bridge/runner.py` 的四条避坑经验：
>   stdin 一律 DEVNULL、超时连**进程树**一起清、输出管道持续读取但**限幅**、
>   **不靠退出码**判成败。
> - **鉴权识别两层机制** —— 这些 CLI 未登录时**退出码往往是 0**
>   （gemini 是 41、command-code 是 3、claude 是 0），
>   以前会被当成「任务完成」。现在按**措辞**认出来。
> - **前端两处改进** —— 雷达面板新增「**慢/待验证**」状态；
>   会话列表与实时流水区改成「**签名没变就不重建**」。
>
> ⚠️ **红线一字未改** —— R1–R9 与 v4.0.1 **完全一致**。
> 本版只改**扩展机制**与**界面反馈**，不动 L1/L2/L3 的判定规则与阈值。

## 2. 任务一：Agent 配置数据化

### 2.1 数据文件：`src/agents/cloud_agents.json`

**14 条 Agent**，每条登记 18 个字段：

```json
{
  "id": "command-code",
  "label": "Command Code",
  "source_label": "Command Code",
  "binary": "command-code",
  "mode": "switch",
  "fixed_args": [],
  "prompt_flag": "-p",
  "model_flag": "--model",
  "json_args": ["--output-format", "json"],
  "json_shape": "document",
  "json_shape_note": "stdout 整体是一个 JSON 文档",
  "version_args": ["--version"],
  "aliases": ["cmdc", "commandcode"],
  "auth_patterns": [
    "authentication failed",
    "please run .{0,12}login.{0,4} first"
  ],
  "fail_patterns": [],
  "login_hint": "需要先登录：cmdc login（等价于 command-code login）",
  "install_cmd": "bun add -g command-code",
  "install_hint": "",
  "notes": "官方横幅自称 cmd，但 cmd 在 Windows 上是 cmd.exe，故不登记为别名。",
  "hints": ["……"]
}
```

> ⚠️ `label` 用的是**哨兵本地的中文译名**，`source_label` 保留上游原文 ——
> 面板上显示的一直是中文，没必要为了「忠于上游」把英文换回去。
>
> ⚠️ `notes` / `hints` 是**上游作者在其自有机器上的观察**，
> 本机**未复验**。迁移到别的机器必须逐条重测
> （详见 §4.3「不能照抄的东西」）。

### 2.2 `json_shape`：本版新增的一个维度

盘点时发现一个坑：**`json_args` 只声明了「开关」，没声明「输出长什么样」**。

| 形态 | Agent | 处置 |
| --- | --- | --- |
| `document` | claude / codebuddy / command-code / gemini / openclaw / opencode | ✅ 打开开关，正文能抠出来 |
| `jsonl` | atomcode | ✅ 打开开关，逐行解析 |
| `stream` | omp / pi | ⚠️ **不开** —— 事件流按文档解析必然失败，作者也建议「默认别开」 |
| `none` | dsh / evox / hermes / qwenpaw / step | 没有开关，纯文本 |

所以清单里 `json_args` 与 `json_shape` **必须同时声明**，
校验器会拦下「只给一个」的错配。

### 2.3 `src/agents/__init__.py` 的加载与校验

`load_agents()` 会拦住这些错：

| 错 | 表现 |
| --- | --- |
| `schema` 不是 1 | `AgentConfigError` |
| `id` 不匹配 `^[a-z][a-z0-9-]{1,31}$` | `AgentConfigError` |
| `id` 重复 | `AgentConfigError` |
| **同一个别名挂在两个 Agent 上** | `AgentConfigError` |
| `mode` 不在三种里 | `AgentConfigError` |
| `flag` / `switch` 缺 `prompt_flag` | `AgentConfigError` |
| `positional` 却有 `prompt_flag` | `AgentConfigError` |
| `json_args` 与 `json_shape` 只给一个 | `AgentConfigError` |

**未知字段一律忽略**（前向兼容比严格校验更重要 —— 这也是上游的做法）。

⚠️ `strict=False` 时清单缺失只**降级成空表**并记一条 warning ——
打包成 exe 后万一漏带清单，哨兵要能**降级**而不是起不来。

### 2.4 `build_argv()`：正文的位置不固定

上游的 `mode` 有三态，拼出来的 argv **只有两种形态**：

```
[可执行名] + fixed_args + ([prompt_flag, 正文] | [正文])
           + json_args（仅当 json_output）
           + ([model_flag, 模型]（仅当给了 model）)
           + extra_args
```

| Agent | mode | argv |
| --- | --- | --- |
| claude | flag | `claude -p <正文>` |
| command-code | switch | `command-code -p <正文>` |
| dsh | positional | `dsh --profile headless <正文>` |
| opencode | positional | `opencode run <正文>` |
| openclaw | positional | `openclaw agent exec <正文>` |
| gemini | flag | `gemini -p <正文> [-m 模型] [-o json]` |

⚠️ **`flag` 与 `switch` 拼出来一模一样** —— 区别只在登记时的自我约束
（把不吃值的布尔开关误写成取值开关，到真机上才会发现）。
所以 argv 构造器可以合并成一个分支，但**登记时要分开写**。

⚠️ 哨兵自己的 `mcode` / `claude` / `codex` 约定把正文放**最后**，
两者**不能混用** —— 所以 `AgentProfile` 新增了 `build_full_args` 钩子，
让数据驱动的 Agent 走「完整命令行」路径。

### 2.5 雷达别名表：8 条 → 16 条

`src/proc_tree.py` 的三张表改成动态加载：

```python
_CLOUD_AGENTS = load_agents(strict=False)
CLOUD_AGENT_BINARIES = binary_table(_CLOUD_AGENTS)
CLOUD_AGENT_LABELS = label_table(_CLOUD_AGENTS)
CLOUD_AGENT_ALIASES = alias_table(_CLOUD_AGENTS)
```

**此前认不出、现在能认出的 8 条别名**：

| 别名 | 归一到 | 此前 |
| --- | --- | --- |
| `cmdc` | command-code | ❌ 认不出 |
| `commandcode` | command-code | ❌ 认不出 |
| `gcli` | gemini | ❌ 认不出 |
| `geminicli` | gemini | ❌ 认不出 |
| `hermes-agent` | hermes | ❌ 认不出 |
| `pi-coding-agent` | pi | ❌ 认不出 |
| `earendil-pi` | pi | ❌ 认不出 |
| `stepcode` | step | ❌ 认不出 |

## 3. 任务二：派发层加固

### 3.1 吸收的四条避坑经验

| 坑 | 上游的做法 | 哨兵本版的落地 |
| --- | --- | --- |
| **stdin 被抢** | 一律 DEVNULL | `spawn_agent()` 里 `stdin=subprocess.DEVNULL`；接管链路的 `_spawn()` 原本就分两档，v4.1.0 保留 |
| **孤儿进程** | 超时连进程树一起清 | `kill_process_tree()`：Windows 走 `taskkill /F /T /PID`，POSIX 走 `killpg` |
| **管道写满死锁** | 后台线程一直读 + 限幅缓冲 | `_drain()` 后台线程 + `BoundedBuffer`（默认 256 KB 尾部） |
| **退出码不可信** | 另做措辞识别 | `src/agents/auth.py` 的两层机制 |

### 3.2 输出限幅：留尾部，丢头部

Agent 输出里最有价值的是**最后**几句（结论、报错摘要），
前面的启动噪声可以丢。所以 `BoundedBuffer` 超限时从**头部**裁。

⚠️ 限幅但**不能停止读取** —— 停止读取会让管道写满、
子进程**永久阻塞**。这两件事必须分开做：
「一直读」是必须的，「只留尾巴」是限流。

### 3.3 鉴权识别的两层结构

```
第一层：GLOBAL_AUTH_PATTERNS（8 条全局兜底）
        authentication required / unauthenticated / not logged in /
        use /login / run /login / invalid api key /
        credentials expired|invalid|not found|missing / 中文四种

第二层：每条 Agent 档案里的 auth_patterns
        command-code → authentication failed / please run …login… first
        gemini      → please set an auth method / specify one of the
                       following environment variables
        pi          → pi auth
```

**三条门槛**（缺一不可）：

1. stderr 必须**短**（≤ 800 字符）—— 真跑完任务的 Agent 一定把结果写进 stdout；
2. 只看 stderr **开头** 400 字符；
3. stdout 里**没有实质内容** —— 滤掉警告 / 空行 / 纯符号行后，
   剩余任一行长度 ≥ 8 即视为有正文。

⚠️ **不能要求 stdout 为空** —— 启动期真出问题时 CLI 往往先往 stdout
打几行噪声（codebuddy 的 PowerShell 警告就是），
用「stdout 非空就不判」当闸门，这类失败会被报成 `ok=True`。

**「运行期失败」与「没登录」是分开的**（`fail_patterns`）：
hermes 的 gateway 没跑时退出码**也是 0**，只打一行
`Error: Gateway inaccessible: service_manager_unavailable` ——
处置动作是「去起服务」，不是「去登录」。

### 3.4 接管链路怎么用上这两层

`_drain_stderr()` 现在**边转发边收集**进限幅缓冲；
主循环同时收集 stdout；`run()` 收尾时调 `_judge_auth_failure()`：

- 命中鉴权 → 记一条 `agent_auth` 事件，终端明确提示
  「⚠️ XX 疑似**未登录**（退出码不代表成功）」；
- 命中运行期失败 → 记一条 `agent_runtime_error` 事件。

### 3.5 14 个 Agent 接进派发档案表

`AGENT_PROFILES` 从 **3 条**扩到 **16 条**
（14 个上游 + mcode + codex；claude 两边都有，**保留哨兵自己那份**
—— 它用 `--output-format stream-json`，比上游登记的 `json` 更适合流式审查）。

⚠️ **一律用通用 text 适配器** —— v4.1.0 明确不做多格式解析器。
只有 `json_shape` 是 `document` / `jsonl` 的那几个会打开机器可读输出开关。

### 3.6 通用纯文本适配器的能力边界

| 能力 | 有没有 |
| --- | --- |
| 规则层对正文做正则匹配（危险命令、密钥泄漏） | ✅ |
| 引擎统计行数与事件数 | ✅ |
| **L2 流式漂移判定** | ❌ —— 漂移判定依赖结构化事件语义 |
| **「本轮结束」判定** | ❌ —— 没有 `done_markers`，只能靠进程退出 |

⇒ 这 6 个 Agent 在哨兵里属于「**能看、不能审**」的一档。

## 4. 任务三：前端「偷师」

### 4.1 「慢/待验证」状态

上游面板有个 `slow` 档：有的 CLI 未登录时**静默挂起**（step 实测 40 秒以上、
stdout/stderr 全空），面板看着像「在干活」。
作者把它单列一档，注释写得很直白：
「别让用户以为它能正常干活」。

哨兵侧的数据来源：进程创建时刻 `started_at`
（v4.1.0 新增到 `DiscoveredAgentProcess`）。

判据：**进程还活着，但一直没找到它写出的日志，且已超过 60 秒**。

| 情况 | 徽章 |
| --- | --- |
| 已接入 | 已接入 |
| 有可接入的日志 | 运行中 · 可接入 |
| 没日志，但存活 < 60 秒 | 运行中 · 暂无日志可接入 |
| 没日志，且存活 ≥ 60 秒 | **慢/待验证 · 已运行 N 秒未见输出**（橘黄） |

⚠️ 阈值取 60 秒 —— 上游实测的最短挂起案例是 step 的 40 秒以上，
留了点余量。

### 4.2 列表不再被轮询抽走

**实测发现**：哨兵前端**告警列表**早就有「集合没变就不重建」的机制
（`renderAlerts`），但**会话列表**（每 **5 秒**轮询）与
**实时流水区**（每 **15 秒**回放）还是「清空 → 重建」——
用户正在滚动或正要点的条目会被**抽走重建**。

v4.1.0 复刻上游的 `refreshLastCells` 思路，改成**签名机制**：

| 列表 | 签名函数 | 判据 |
| --- | --- | --- |
| 会话列表 | `sessionListSignature()` | id / state / workspace / agent / 告警数 / pid / 绑定状态 / 目标 / 流筛选 / 各线程流计数 |
| 实时流水区 | `liveAuditSignature()` | 整段条目的 JSON 序列化 |

签名没变就**一个 DOM 都不动**。

⚠️ 会话列表的签名**必须带上流筛选条件** ——
流筛选会改变条目里那些「默认流 / 线程 X」小标签的高亮状态，
不带的话改了筛选界面不会重绘。

## 7. 诚实边界

1. **没有在本机跑过那 14 个 Agent CLI** —— 本机没装它们。
   清单里的 `notes` / `hints` 是**上游作者的自述**，不是本次的观测结果。
2. **`json_shape` 的判断依据是格式分析**，不是逐个 CLI 实跑验证。
3. **通用纯文本适配器没有做 L2 漂移判定** —— 这是**明确的能力缺口**，
   不是「还没做」，是这一版**决定不做**（成本过高）。
4. **6 个 Agent 只能事后判定** —— 纯文本没有「本轮结束」标记。
5. **`failure_mode = "timeout"` 没有实现** —— 上游的 `providers/step/provider.toml`
   里有这个字段，但**它的运行时 schema 根本不读**（只有测试读）。
   step「静默挂起只能靠超时判定」这条语义，哨兵要自己实现。
