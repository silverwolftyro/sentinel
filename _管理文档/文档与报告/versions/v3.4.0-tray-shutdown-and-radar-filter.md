# v3.4.0 —— 托盘化彻底退出 · 挂载清理与状态纠偏 · 雷达排除自身

> 这一版做四组事，全部来自**用户实测反馈**：
>
> 1. **后台幽灵** ——
>    「找不到『退出系统』的按钮，关掉黑框后后台变成无法杀死的幽灵，
>    只能去任务管理器杀。」；
> 2. **挂载删不掉** —— 选错 / 失效的会话只能干瞪眼；
> 3. **状态是假的** ——
>    「进程已死，但因日志文件还在，状态依然显示『运行中』」；
> 4. **雷达抓错东西** ——
>    「哨兵去抓自己压测产生的残留日志，
>    却漏掉了用户真实在跑的 N.E.K.O 任务。」；
> 5. **看不到流式滚动** —— 中间面板空空如也，「感官上像个死系统」。
>
> ⚠️ **红线一字未改** —— R1–R9 与 v2.1.0 **完全一致**。
> 这一版**唯一**新增的进程相关行为是：
> 退出时**只结束哨兵自己拉起的子进程**；
> 雷达挂载进来的、属于用户的 Agent，**绝不**去动（R6）。
> 哨兵依然只读，不碰别人的进程，不自动接管任何东西。

## 1. 红线：这一版一个字都没改

| 红线 | 这一版怎么守的 |
| --- | --- |
| R1 只读监听 | 被监控的 Agent 日志**一个字节都没动**；这一版只新增了「读进程表判死活」 |
| R2 不干预代码 | 新增的全是**界面元素**与**配置项**，不含任何写文件的动作 |
| R3 不注入进程 | 托盘、卸载、状态纠偏**都不给任何进程发信号** |
| R4 本地闭环 | 托盘、进程存活判定、雷达过滤**全部在本机**完成，不外发任何数据 |
| R5 旁路失败 | pystray / Pillow 缺失 → **不出图标**，哨兵照跑；psutil 缺失 → 存活判定一律「不知道」，**不改状态** |
| R6 不终止进程 | 退出时**只**结束哨兵**自己拉起**的子进程（`run_with_sentinel.py` 的 `_terminate_agent_trees`）；雷达挂载进来的用户 Agent **绝不**去动 |
| R7 不悄悄改系统设置 | 托盘图标是**哨兵进程自己的**窗口；不写任何系统设置、不加开机自启 |
| R8–R9 | 与 v2.1.0 一致 |

⚠️ 特别说明两条容易紧张的：

- **「关掉黑框」现在会真的退出** ——
  这是**哨兵自己的**进程响应**它自己的**控制台关闭事件，
  不是哨兵去关别人的窗口。
- **「状态纠偏」会结束进程吗** —— **不会**。
  它只是**停止读那份日志**并把状态改成「已退出（静默）」，
  进程是用户自己的，哨兵**一个信号都不发**。

## 2. 任务一：彻底解决后台幽灵与托盘化

### 2.1 问题出在哪

「关掉黑框后后台变成无法杀死的幽灵」这句话背后是三件事：

| # | 事实 | 后果 |
| --- | --- | --- |
| 1 | Windows 上**双击关闭控制台窗口不会**杀掉控制台程序 | 进程继续在后台跑 |
| 2 | 看板是**网页**，没有「关闭自己」的能力 | 找不到任何「退出」入口 |
| 3 | 终端黑框**不是按钮** | 用户不会想到去那儿找 |

结果是用户只剩一个办法：打开任务管理器，手动找进程，杀掉。
—— 而这恰恰是「找不到出口」的最终形态。

### 2.2 这一版怎么做的：**三条路，一个出口**

```
托盘【彻底退出】 ─┐
看板【关闭哨兵】 ─┼─→  ShutdownCoordinator.request()  ─→  收尾钩子（按序）
关掉黑框        ─┘        （幂等：只生效一次）
```

| 入口 | 实现 | 说明 |
| --- | --- | --- |
| 托盘右键菜单 | `src/gui/tray.py` | 菜单**只有两项**：【打开看板】、【彻底退出】 |
| 看板右上角按钮 | `POST /api/shutdown` | 红色【关闭哨兵】，点一下**先弹确认框** |
| 关掉黑框 | `SetConsoleCtrlHandler` | 处理 `CTRL_CLOSE_EVENT` / `CTRL_LOGOFF_EVENT` / `CTRL_SHUTDOWN_EVENT` |

**收敛到同一个出口**是有意为之：
如果三条路各写一套收尾逻辑，
就会出现「这条路干净、那条路留残留」—— 那正是要消灭的东西。

### 2.3 收尾都做了什么

按**注册顺序**执行，每个钩子**单独 try**（一个炸了不挡后面的）：

1. `server.should_exit = True` —— 让 uvicorn 走它自己的正规停机路径；
2. 停掉托盘图标（`icon.stop()`）—— 不然系统里会留一个点不动的图标；
3. 结束哨兵**自己拉起**的子进程（R6）；
4. 全部做完、输出刷干净之后 → `os._exit(0)`。

### 2.4 关键决定一：托盘线程必须是**守护线程**

`pystray` 自带的 `Icon.run_detached()` 起的是**非守护**线程 ——
进程会因此**赖着不走**。

那就等于用**一个新的「幽灵」替换掉旧的「幽灵」**。
所以这里自己起 `threading.Thread(target=icon.run, daemon=True)`，
并在退出钩子里 `icon.stop()`。

### 2.5 关键决定二：退出后直接 `os._exit(0)`

正常的 `return` 会等所有**非守护线程**结束 ——
而托盘、尾巴线程都可能还在那儿，进程就赖着不走。

所以「彻底退出」这条路在收尾做完之后**直接走 `os._exit`**：
缓冲先刷出去，然后立刻消失，不给任何线程留机会。

⚠️ `os._exit` **不跑** `atexit`、**不跑** `finally` ——
所以它必须放在**所有收尾都做完之后**调用。

### 2.6 关键决定三：图标自己画，不带 `.ico`

用 Pillow **自绘**：青底圆角方块 + 白色「哨」字。

- 不引入二进制资源文件 → 打包时少一个依赖，
  也不用管图标路径在「源码形态」与「打包形态」下到底指向哪儿；
- 找不到中文字体时**画一只几何的眼睛**兜底 ——
  两种都至少是**认得出来**的图标。

### 2.7 关键决定四：托盘是**可选依赖**

`pystray` / `Pillow` 没装 → **不出图标**，但哨兵的其它功能
**一点不受影响**（与 `psutil` 同一个待遇，红线 R5）。

终端会明确打一行：`托盘不可用（缺少 pystray / Pillow）—— 不出图标。`
—— 不静默假装有。

### 2.8 关键决定五：看板按钮**先确认**再执行

网页不能自己关掉自己，但它**可以**让后台那个进程把自己收干净。

所以【关闭哨兵】点下去先弹确认框，把三条后果列清楚：

1. 看板服务会停，托盘图标会一起消失；
2. 哨兵**自己拉起**的子进程会被结束；
3. **雷达挂载进来的 Agent 不受影响**。

确认之后才发 `POST /api/shutdown`。

### 2.9 一个打包时踩到的坑（很值得记）

第一次打包出来，**打包版的托盘图标不出现** ——
终端只有一行「托盘不可用（缺少 pystray / Pillow）」。

根因在 `build_exe.py`：

```
--hidden-import pystray --hidden-import PIL ... --exclude-module PIL
```

`--exclude-module` 的优先级**高于** `--hidden-import` ——
而 `PIL` 还在 `EXCLUDED_MODULES` 里（当初为了压体积顺手排掉的）。

结果就是：打包出来的 exe **没有 Pillow**，
托盘图标**静默地不出现**。

现在 `PIL` 从排除清单里拿掉，`pystray` / `PIL` / `pystray._win32`
作为**可选依赖**点名进去。
（代价：exe 从 16.1 MB 涨到 23.3 MB —— 那是 Pillow。）

⚠️ 这类「打包成功但运行时才缺东西」是最糟的一种 ——
所以托盘演示脚本必须**跑打包版**才算数。

## 3. 任务二：挂载列表的清理与状态纠偏

### 3.1 卸载按钮

左侧每个会话卡片（**除雷达自己那个占位会话**）加一个 `[×]`：

- 点它 → `DELETE /api/sessions/{id}`；
- **立刻**从 `state.sessions` 里移除并重渲染 —— 不等下一次轮询；
- 后端停止对那份日志的跟随。

「占位会话不给按钮」这件事由**后端字段**说了算
（`SessionSpec.placeholder` → 快照里的 `placeholder`），
**不靠字符串比对** —— 名字改了也不会出错。

### 3.2 状态纠偏：为什么是「三态」

用户说：「进程已死，但因日志文件还在，状态依然显示运行中。」

根因是：哨兵判断「会话还在跑」本来只看**日志文件还在被写**，
而 Agent 跑完之后那个文件**仍然躺在磁盘上**。
于是状态永远停在「运行中」，右侧还在**一遍遍重放**同样的旧行。

修法是**独立地看进程**。但这里有个坑：
「查不到」与「死了」是**两回事**。

| 情况 | `pid_alive()` 返回 | 该不该改状态 |
| --- | --- | --- |
| 进程在 | `True` | 不改 |
| **确实死了** | `False` | **改成「已退出（静默）」** |
| 查不到（没绑定 / 无 psutil / 非法 PID） | `None` | **绝不改** |

⚠️ `None` 绝不能当成 `False` ——
那正是 v3.3.1 刚放宽过的宽容度，不能又收回去。

只有**确实绑定**了进程的会话才判（`bound_pid()` 只认 `bindable` 的绑定），
「按工作目录猜到了个什么」的那种绑定**不能**拿它的 PID 去判死活。

### 3.3 巡检节奏

**每 10 秒**看一眼。再快没有意义（进程不会秒死），
再慢用户会觉得「状态卡住了」。

### 3.4 新状态为什么是灰色的

新状态叫「**已退出（静默）**」，用**灰色**，不用红色。

理由很简单：**Agent 跑完是正常结束，不是出事了。**
红色在哨兵的语言里是「出事了」—— 用在这里会制造假警报。

而且进程一死就把跟随线程收掉：
状态变「已退出（静默）」，右侧**不再刷**那份不会再变动的旧日志。

## 4. 任务三：雷达的「排除自身」与「自定义特征」

### 4.1 问题出在哪

「哨兵去抓自己压测产生的残留日志，却漏掉了用户真实在跑的 N.E.K.O 任务。」

两件事叠在一起：

1. 哨兵自己压测留下的日志**混进了**雷达列表 → 列表里全是噪音；
2. 用户真实在跑的那个 Agent，**雷达认不出来** → 真的那个反而被挤掉。

### 4.2 排除关键词

配置新增：

```yaml
radar:
  exclude_keywords:
    - sentinel
    - stress
    - test
```

路径命中这些词的日志**一律不显示** ——
而且是在**读文件之前**就跳过（不合格的候选连读都不用读）。

⚠️ **匹配是子串匹配**（不区分大小写）——
所以 `contest` 这种目录也会被 `test` 命中。

这一点在**三处**都明说了：代码注释、设置页说明、示例配置。
被误伤就把那一条从配置清单里删掉。

### 4.3 关键决定：默认清单由**调用方**决定

`scan_agent_sessions()` 原来把「没传排除清单」理解成「用内置默认清单」。

问题来了：路径里带 `test` 的**正常**目录
（例如 `D:\projects\test-suite`）会被悄悄挡掉。
pytest 的临时目录名里就带 `test` —— 这让 13 条老测试当场挂掉，
但那只是症状：**根因是库函数替用户做了主**。

所以现在：

| 层 | 职责 |
| --- | --- |
| `scan_agent_sessions(exclude_keywords=None)` | **不过滤** —— 库函数不替用户做主 |
| `src/gui/server.py` 的 `_effective_exclude_keywords()` | 解析出**当前实际生效**的清单：配置没写就用内置默认，配了空列表就真的什么都不排除 |

**产品决定留在产品层。**

### 4.4 自定义特征

配置新增：

```yaml
radar:
  custom_process_features:
    - neko
```

内置特征只认得 `mcode` / `codex` / `claude` 三家。
用户自己写的 Agent（或改了包名的 fork）就**认不出来** ——
雷达于是「明明有任务在跑，却一个都没提示」。

两个关键决定：

**① 匹配的是「命令行」或「工作目录」。**

用户写的是命令行，但 N.E.K.O 的关键字在**项目路径**里
（`D:\项目\N.E.K.O`），只看命令行会漏 —— 两者都匹配才真正解决问题。

**② 匹配时会「去掉分隔符」再比一次。**

用户写的是 `neko`，目录叫 `N.E.K.O` ——
中间隔着三个点，**纯子串匹配对不上**。

这正是这个功能最该管住的真实场景，不能让它失效。
所以除了普通子串匹配，还会把 `.` `-` `_` `\` `/` `:` 与空白去掉再比一次
（⚠️ 只去分隔符，**不去中文** —— 中文是项目名的一部分）。

**③ 少于 3 个字符的特征直接忽略。**

一个字母的关键词能命中满机的 Node 进程 ——
「检测到活跃 Agent 进程」的提示会彻底失去意义
（狼来了：用户点进来发现是假的，就再也不信了）。

### 4.5 实机验证

本机 `D:\项目\N.E.K.O` 那个进程：

| 特征 | 认得出来吗 |
| --- | --- |
| 内置特征 | ✗（`@minimax-ai/code` 那个认得，另一个认不出） |
| 自定义特征 `neko` | **✓** —— pid 25892，cwd `D:\项目\N.E.K.O` |

## 5. 任务四：澄清流式与 Hook 机制

### 5.1 「实时审核流水」初始状态

中间面板空空如也，是因为**没命中告警**。

现在初始状态写清楚：

> 正在实时读取日志流，若无告警，此处将滚动显示正常操作。

做法上有个小讲究：这条提示是**常驻 DOM 节点**，不是 CSS 伪元素 ——
第一条真实流水进来时把它移除，清空后又放回去。

### 5.2 设置页的「旁路」说明

用户以为哨兵是「Hook 进 Agent 内部」的，
于是「没看到 Hook 的痕迹」就等于「它没在工作」。

实际不是 —— 哨兵是**旁路**：读 Agent 自己写出来的日志文件。
所以「Agent 必须开启 JSON 日志输出」才是前提。

设置页现在明确写着：

> 哨兵当前采用【旁路日志跟随】模式，不是侵入式 Hook。
> 请确保 Agent 开启了 JSON 日志输出。

## 7. 给用户看的用法

### 7.1 怎么退出哨兵

三条路，随便挑一条：

1. **托盘图标右键 →【彻底退出】** —— 最快；
2. **看板右上角的红色【关闭哨兵】** —— 会先弹确认框；
3. **关掉黑框** —— 现在**真的会**退出（以前会留下幽灵）。

三条路走的是**同一套**收尾逻辑，所以**效果完全一样**：
看板服务停、托盘图标消失、哨兵自己拉起的子进程被结束。

⚠️ **雷达挂载进来的、你自己启动的 Agent，不受影响** ——
哨兵不会去动别人的进程。

### 7.2 那个 `[×]` 是干什么的

点它就把这个会话**从哨兵这儿卸载**：
哨兵不再跟着那份日志，列表里立刻消失。

选错了、失效了、不想看了 —— 点一下就行。
⚠️ 它**只影响哨兵**，不会删你的日志文件，也不会停你的 Agent。

### 7.3 「已退出（静默）」是什么意思

意思是：**那个 Agent 进程已经结束了**，但它的日志文件还躺在磁盘上。

所以哨兵不再跟着刷那份日志了（它不会再变），
把状态如实改成「已退出（静默）」。

**这不是故障，也不是告警** —— Agent 跑完了而已。
灰色显示，不惊动你。

### 7.4 「检测到活跃进程」时怎么把 N.E.K.O 也认出来

设置页【挂载管理】里多了一块「雷达排除关键词与自定义特征」：

- **排除关键词**：默认 `sentinel` / `stress` / `test` ——
  哨兵自己的压测残留不再出现在列表里。
  ⚠️ 是**子串**匹配，所以 `contest` 也会被 `test` 命中；
  被误伤就把那一条删掉。
- **自定义特征**：填 `neko` 之类的关键字 ——
  **命令行或工作目录**里命中它的进程，雷达也会认出来并提示。

一行一条，保存即生效。

### 7.5 「实时审核流水」空着是不是坏了

**不是。** 那块面板初始就写着：
「正在实时读取日志流，若无告警，此处将滚动显示正常操作。」

哨兵是**旁路日志跟随**——它读 Agent 自己写出来的日志文件，
**不是**往 Agent 进程里插代码。所以前提是：
**请确保 Agent 开启了 JSON 日志输出**
（`--output-format stream-json` / `--json`）。
