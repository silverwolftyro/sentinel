# v2.4.0 —— 雷达进阶：挂载会话的守护者武装与意图锚定

> v2.3.0 让哨兵能**发现**并**挂载**你正在跑的 Agent，
> 但挂载进来的会话是**只读**的 —— 两个残缺：
>
> 1. **找不到对应的进程 PID** —— 守护者要挂起进程，得先知道**是谁**；
> 2. **没有目标锚点** —— 旁路日志往往没有最初的 Prompt，
>    没有锚点就做不了意图漂移（DRIFT）检测。
>
> 这一版把挂载会话从「只读」升级为「全功能」，
> **但没有扩大哨兵的动作边界**：
> 守护者只在**用户手动打开开关**之后才接管。

## 1. 红线：这一版一个字都没改

**本版未新增任何红线修订。** R1–R9 与 v2.1.0 **完全一致**，**一字未改**。

v2.3.0 的时候，挂载进来的会话**不带**守护者 ——
理由是「没弄清对象不动别人的进程」。
v2.4.0 把这条**补完**了，而不是**推翻**它：

* 哨兵**依然只读** —— 挂载进来的日志一个字节都不会被改；
  挂载会话的告警日志落在哨兵自己的 `logs/attached/` 下，
  **绝不**写进用户正在跑 Agent 的那个项目目录；
* 守护者**依旧要用户亲手武装** —— 反查得到 PID 只是**把选项摆出来**，
  开关**默认关着**；在用户手动打开之前，挂载会话**只读、只报告**；
* 反查**只敢认置信度达标**的结果 —— 置信度不够就显示「[未绑定进程]」
  并**禁用**开关，绝不拿一个「大概是某个进程」去挂起；
* **没有**新增任何写文件 / 改代码 / 终止进程的路径
  —— 「武装」这条路径只是把**已有的**守护者接到一个**用户指定的** PID 上。

## 2. 任务一：反查挂载会话的 PID

### 2.1 为什么要反查

守护者要挂起进程，得先知道**该挂谁**。

v2.3.0 的 `Guardian.detect_pid(hint)` 已经在做「按命令行里包含日志路径
反查 PID」，但那条路径**对旁路监听无效**：
挂载进来的日志路径通常**不在**任何进程的命令行里
（`mcode … > session.jsonl` 的重定向**不体现为 cmdline**），
自动探测必然落空。

所以 v2.4.0 加了**独立的反查器**，而且它是**多策略**的 ——
「写这个文件的进程」在不同平台、不同 Agent、不同启动方式下，
信号完全不一样。

### 2.2 `src/procscan.py`（新叶子模块，纯标准库 + 可选 psutil）

| 策略 | 命中条件 | 置信度 | 可否武装 |
| --- | --- | --- | --- |
| `cmdline_path` | 进程命令行里带着这个日志的路径 | 0.95 | ✅ |
| `open_files` | 进程**打开着**这个文件（文件句柄） | 0.95 | ✅ |
| `cmdline_cwd` | 命令行里有 Agent 特征，工作目录也对得上 | 0.85 | ✅ |
| `cwd_only` | 只有工作目录对得上 | 0.60 | ❌ **不够** |

只有置信度达到 `BINDABLE_CONFIDENCE`（**0.75**）的结果才允许武装。
`cwd_only` 之所以不够：同一个工作目录下可能有好几个进程
（编辑器、终端、构建脚本），**挂错一个的代价远大于少一个能力**。

主要接口：

| 函数 | 职责 |
| --- | --- |
| `scan_processes(...)` | 扫描系统进程，返回按置信度**倒序**的候选 |
| `find_process(..., require_bindable=True)` | 取**一个**敢认的结果 |
| `describe_process(pid)` | 描述指定进程（不看匹配规则） |
| `protected_pids()` | **绝不能**当成被监控进程的那几个 PID |
| `psutil_available()` | 反查能力当前可不可用 |

### 2.3 打包版的自我保护（PyInstaller 陷阱）

PyInstaller 的**单文件模式**会再起一个同名子进程。
如果不做保护，哨兵会**把自己**当成用户那个 Agent ——
然后武装守护者时**把自己挂起**。

`protected_pids()` 的处理：

* 源码运行（`sys.executable` 是 `python.exe`）——
  只排除**自身**与**父进程**；
  ⚠️ 绝不能把所有 `python.exe` 都排除掉，那会误伤用户的 Python Agent；
* 打包运行（`sys.frozen` 为真）——
  额外排除与哨兵**同名**的所有进程（启动器 + 子进程，两个都得排除）。

### 2.4 现实限制（如实说明）

* **重定向输出时反查不到**：`mcode … > session.jsonl` 的路径
  **不在** cmdline 里，`cmdline_path` 必然落空；
* **Windows 上文件句柄多半读不到**：`open_files()` 需要更高权限，
  绝大多数进程抛 `AccessDenied`；
* 因此**最稳**的信号其实是「Agent 特征 + 工作目录」；
* 查不到就是查不到 —— 界面显示「**[未绑定进程]**」，
  武装开关**禁用**并说清楚原因。**绝不假装成功。**

### 2.5 界面状态

```
反查成功：  [Codex] D:\work\project_alpha        ← 会话名
            PID 54372                [武装]      ← 开关可用（橙色）

反查失败：  [Claude] D:\work\project_beta        ← 会话名
            [未绑定进程]             [武装]      ← 开关禁用（灰色）
```

实拍见
[`assets/dashboard-v2.4.0-pid-bound.png`](../assets/dashboard-v2.4.0-pid-bound.png)。

### 2.6 武装通道

新增 `POST /api/sessions/{id}/arm`，body `{"armed": true|false}`。

* 武装 → 用 `Guardian.set_target_pid(pid)` 把守护者接到那个 PID 上，
  并挂到该挂载会话的引擎里；
* 解除武装 → 把守护者从引擎上摘掉，恢复纯只读；
* **没绑定进程** → 拒绝，并说明「尚未绑定进程，无法武装守护者」；
* **配置里守护者是关的** → 拒绝，并说明「请先到设置页开启」。

会话快照新增字段：`pid` / `process_bound` / `process_info` / `armed` /
`arm_available` / `attached`。

## 3. 任务二：挂载会话的意图锚定

### 3.1 为什么必须手动注入

旁路日志**没有最初的 Prompt**：
哨兵是从文件**尾部**开始跟随的，用户那句「我要重构 auth 模块」
根本不在日志里。

没有锚点 → 没有滑窗 → 没有意图漂移判定。
所以挂载会话必须有一个**手动注入目标**的地方。

### 3.2 实现

* 顶部「任务目标」输入框在选中挂载会话时**照常可用**；
* 设定之后 → `TaskGoal` 触发回调 → `TailRunner.apply_goal()`
  → 引擎里**立刻**装上意图追踪器 → **立刻**开始盯 DRIFT；
* 每个挂载会话有**独立**的 `TaskGoal`，互不干扰；
* 「当前监控目标」面板会**同步**（`goal_source = "explicit"`），
  不然用户会以为没生效；
* 挂载会话**不继承**配置文件里的全局 `task_goal`
  （`inherit_config_goal=False`）——
  它干的活跟哨兵自己那份任务多半不是一回事，
  硬套只会凭空造出一堆**假的**漂移告警。

### 3.3 ⚠️ 顺带修掉的一个真 bug

**症状**：挂载会话手动设定目标后，界面显示「已锚定」，
但 DRIFT 告警**永远发不出来**。

**根子**：`SentinelEngine.__init__` 只在**构造时**给意图追踪器挂
异步回调（`attach_async`）。而挂载会话的追踪器是**运行中补建**的 ——
没挂上。而在流式模式下 `IntentTracker.observe()` 的**返回值没人看**，
漂移结论全靠那个回调回到引擎。

**修法**：新增 `SentinelEngine.set_intent_tracker(tracker)` ——
装追踪器就**一定**把回调接上。

**另一个相关 bug**：清空任务目标时，`IntentTracker.set_goal("")`
是个**空操作**（不清锚点）—— 界面提示「意图漂移检测停用」，
引擎却还在拿旧目标判漂移。现在目标被清空会**直接把追踪器摘掉**。

### 3.4 实机演示

设定目标「重构 auth 模块并修复登录 bug」，
挂载会话里写入一串明显跑偏的操作
（`rm -rf ./src`、`curl … | sh`、`del /f /q …`），
两窗（window=5、threshold=2）之后挂载会话**真的**报出 DRIFT。

实拍见
[`assets/dashboard-v2.4.0-drift.png`](../assets/dashboard-v2.4.0-drift.png)。

> ⚠️ 演示环境说明：本机默认 `llm.provider` 是 Ollama，
> 没起服务时漂移判定会**降级**成「未漂移」（这是红线 R5 的设计）。
> 验收脚本会**临时**生成一份配置把 L2 指向云端模型
> （密钥走环境变量，**不落盘**），**绝不改动**用户自己的 `config/config.yaml`。

## 4. 任务三：雷达性能优化与稳定性

### 4.1 雷达跳过已挂载文件

`scan_agent_sessions()` 新增 `exclude_paths` 关键字参数；
`/api/discover` 把**已挂载**路径传进去 —— 同一份日志不必读两遍。
比较按平台规则归一化（Windows 忽略大小写）。

### 4.2 SSE 微批处理

**问题**：Agent 跑得飞起时一秒能写几百行。
逐行发 SSE 意味着一秒几百个事件：
订阅队列（默认 500 条）会被瞬间灌满、开始丢事件，
前端也被几百次 DOM 操作淹没。

**做法**：

* 服务端把日志行**攒**起来，一批一条事件发出去：
  `{"type": "lines", "texts": [...]}`，单批最多 200 行；
* 前端用 `DocumentFragment` **一次性**插入 DOM；
* ⚠️ 旧的单行事件 `{"type": "line"}` 前端**仍然认**
  （兼容旧页面 / 旧脚本），只是服务端不再逐行发。

### 4.3 实测吞吐

| 指标 | 数值 |
| --- | --- |
| 写入量 | 3000 行（0.007 秒写完） |
| SSE 收到 | **3000 / 3000 行，一行不丢** |
| 帧数 | **15 帧**（逐行发会是 3000 帧） |
| 帧数压缩比 | **200 ×** |
| 吞吐 | **8535 行/秒**（42.7 帧/秒） |

原始数据见
[`v2.4.0-实机验证.json`](../v2.4.0-实机验证.json)。
