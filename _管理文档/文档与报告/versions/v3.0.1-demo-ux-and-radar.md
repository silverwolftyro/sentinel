# v3.0.1 —— 修复演示模式误导、设置页重构与雷达增强

> 用户实测 v3.0.0，反馈了三条**要命**的问题：
>
> 1. 双击 exe 直接进了演示模式 —— 用户以为「雷达扫不到真实的进程」；
> 2. 设置页被挤压成极窄的卡片，**完全不可用**；
> 3. 雷达扫出来的全是 C 盘 `.codex` 下的文件，全显示「未知工作区」，
>    而且没覆盖用户正在用的 MiniMax Code 会话目录。
>
> 这一版**不新增任何动作能力**，只修这三件事，
> 并把「演示模式」从「一个说明」变成「一条能立刻走通的真路径」。

## 1. 红线：这一版一个字都没改

**本版未新增任何红线修订。** R1–R9 与 v2.1.0 **完全一致**，**一字未改**。

v3.0.1 做的是**修复**，不是**扩张**。逐条对照：

* 哨兵**依然只读** —— 雷达新增的扫描根目录只是**多读几个目录**，
  读的还是用户**自己**的 Agent 会话日志；
* 守护者**依旧要用户亲手武装** —— 本版**完全没碰**武装逻辑；
* **没有**新增任何写用户文件 / 改用户代码 / 终止用户进程的路径；
* 唯一一处「看起来像终止进程」的地方 —— 【退出演示】——
  停掉的是**哨兵自己**的 uvicorn，**不碰任何被监控进程**；
* 配置写回仍然只用 `config_loader.save_config()`（外科手术式，保留注释，写前备份）；
* 代码卫生只动哨兵**自己**的代码，**不碰**用户项目。

> ⚠️ 演示退出的「停服」用的是 `uvicorn.Server.should_exit = True`
> —— uvicorn 文档里的正规做法，主循环下一轮**干净退出**，
> 不是 `os.kill`、不是 `GenerateConsoleCtrlEvent`。

## 2. 任务一：修复演示模式的误导

### 2.1 问题出在哪

v3.0.0 的演示模式在横幅上写清楚了「这是模拟数据」。
但用户实测的反馈是：**「双击 exe 直接进入演示模式，
导致我以为雷达扫不到真实的进程。」**

问题不在于**没说**，而在于**只说了「这是假的」，没给「那怎么用真的」**。
一个写「这是模拟数据」的红色横幅，用户看完仍然只能自己猜命令行怎么写 ——
于是演示模式**成功地把他带偏了**。

### 2.2 做了什么

| 动作 | 说明 |
| --- | --- |
| 横幅右侧加大按钮 | 【退出演示，开始真实扫描 →】，CSS Grid 三列布局，按钮靠右 |
| 点它**真的**停服 | `POST /api/demo/exit` → 后台线程延迟 1.2 秒 → `Server.should_exit = True` |
| 页面留下**能抄**的命令 | 三条真命令：接管 Agent / `--scan` 审已有日志 / `--no-gui` 只看终端 |
| 终端反复喊「别关窗口」 | 醒目块一次 + 后台线程每 8 秒重复一次、共 8 次（≈64 秒） |

**为什么延迟 1.2 秒**：立刻停的话，浏览器先收到的是「连接被重置」而不是那句引导，
用户看到的是一个**报错页** —— 那比演示模式更糟。

**为什么引导页是静态存在的**（`#demo-exit-panel` 直接写在 HTML 里，
JS 只负责把命令填进去）：服务端一停，浏览器就**再也拿不到任何数据**。
引导内容要是等 JS 去 fetch，就永远显示不出来。

### 2.3 新增的接口

```
POST /api/demo/exit
  → {"ok": true, "instructions": [...], "stopped": true, "message": "…"}
```

非演示模式下返回 `{"ok": false, "error": "当前不是演示模式 —— 没有需要退出的东西。"}`
—— **不假装成功**。

## 3. 任务二：设置界面彻底重构（左右分栏）

### 3.1 问题出在哪

v3.0.0 的设置页是**一栏到底**：四个分区从上到下堆在一起，整页要滚两千多像素。
用户反馈「被挤压成极窄的卡片，无法展开」。

真正的毛病有两条：

1. **没有分区入口** —— 想改「通知通道」得先滚过整个「模型路由」；
2. **卡片自带内层滚动** —— `.panel__body` 有 `overflow-y: auto`，
   页面外层滚一层、卡片里再滚一层，内容被**藏在**小框里，
   看上去就是「挤成一条、打不开」。

### 3.2 现在的结构

```html
<main class="settings-main">
  <div class="settings-layout">
    <nav class="settings-nav" id="settings-nav" aria-label="设置分区">
      <p class="settings-nav__title">设置分区</p>
      <button class="settings-nav__item settings-nav__item--active"
              data-target="llm"      role="tab" aria-selected="true"
              aria-controls="section-llm">
        <span class="settings-nav__num">①</span>
        <span class="settings-nav__label">模型路由（L2）</span>
      </button>
      <button class="settings-nav__item" data-target="channels" ...>
        <span class="settings-nav__num">②</span>
        <span class="settings-nav__label">通知通道</span>
      </button>
      <button class="settings-nav__item" data-target="rules" ...>
        <span class="settings-nav__num">③</span>
        <span class="settings-nav__label">L1 规则</span>
      </button>
      <button class="settings-nav__item" data-target="sessions" ...>
        <span class="settings-nav__num">④</span>
        <span class="settings-nav__label">挂载管理</span>
      </button>
    </nav>

    <div class="settings-content" id="settings-content">
      <section class="panel settings-section settings-section--active"
               id="section-llm" data-section="llm" role="tabpanel">…</section>
      <section class="panel settings-section"
               id="section-channels" data-section="channels" role="tabpanel">…</section>
      <section class="panel settings-section"
               id="section-rules" data-section="rules" role="tabpanel">…</section>
      <section class="panel settings-section"
               id="section-sessions" data-section="sessions" role="tabpanel">…</section>
    </div>
  </div>
</main>
```

### 3.3 关键的那几行 CSS

```css
.settings-layout {
  display: grid;
  grid-template-columns: 240px minmax(0, 1fr);
  align-items: start;
  gap: 18px;
}

/* ⚠️ **关键的一条** —— 覆盖看板的 .panel__body { flex:1; overflow-y:auto } */
.settings-section > .panel__body {
  flex: none;
  min-height: 0;
  overflow: visible;
}
```

| 决策 | 理由 |
| --- | --- |
| `240px` + `minmax(0, 1fr)` | 右边那列写 `minmax(0, …)` 而不是 `1fr`：网格子项默认 `min-width: auto`，下限是**内容的 min-content**。右边那些卡片里有长路径、长正则，min-content 一大整列就会被撑得比屏幕还宽。`minmax(0, 1fr)` 等价于任务书说的 `flex: 1`，但顺手掐掉了溢出。 |
| 覆盖 `.panel__body` | 不覆盖的话卡片里会藏一个小滚动条，内容被框在里头。 |
| 分区切换**不重读配置** | 只切显示。重新读会把用户**还没保存**的改动冲掉。切换后滚回顶部，否则从长长的「模型路由」切到「挂载管理」，右边还停在几千像素以下，用户会以为没切。 |
| 窄屏（<760px）横向 Tab | 竖排导航在 390px 宽里会把内容挤出屏幕。横向排一行、可以左右滑，才是真的「点一下就切」。 |

### 3.4 实测

| 视口 | 检查项 | 结果 |
| --- | --- | --- |
| 1440×900 | 导航宽度 | `navW = 240` |
| 1440×900 | 内容区宽度 / 起点 | `contentW = 1146` / `contentX = 276` |
| 1440×900 | 卡片内层滚动 | `bodyOverflowY = visible`、`bodyFlex = 0 0 auto` |
| 1440×900 | 横向溢出 | `docScrollW = 1440 = vw`（无溢出） |
| 1440×900 | 切到「挂载管理」 | `active = section-sessions`、`visibleSections = 1` |
| 390×844 | 导航变成横向 | `navDisplay = flex` |
| 390×844 | 横向可滑 | `navScroll = 489 > navClient = 340` |
| 390×844 | 横向溢出 | `scrollW = 390 = vw` |

## 4. 任务三：雷达增强与工作区提取

### 4.1 最关键的一个 bug

> 用户的原话：「雷达扫描出的全是 C 盘 `.codex` 下的文件，全显示『未知工作区』。」

**根因不是「雷达没找到」，而是「找到了却读不出来」**：

新版 codex（v0.16x）的 rollout 首行长这样：

```json
{"timestamp":"2026-10-27T08:49:47.571Z","ordinal":0,"type":"session_meta",
 "payload":{"session_id":"01a17c8d-…","cwd":"C:\\Users\\alpha\\work\\project",
            "runtime_workspace_roots":["C:\\Users\\alpha\\work\\project"], …}}
```

`cwd` 在 **`payload.cwd`** 里 —— 而旧代码只找**顶层**和 `item`。
所以**每一行**都显示「未知工作区」。

修法：按 `顶层 → item → payload → message → data` **挨个找**，
还能从 `runtime_workspace_roots`（工作区根目录列表）里取。
顺带认了新协议的事件类型：`session_meta` / `response_item` /
`event_msg` / `turn_context`。

### 4.2 工作区提取回退链

| 档位 | 来源 | 怎么取 |
| --- | --- | --- |
| 1 | **日志字段** | `cwd` / `workspace` / `runtime_workspace_roots` |
| 2 | **启动参数** | `args` / `command` 里的参数 —— 但**必须确实是目录** |
| 3 | **系统进程的工作目录** | 反查「正在写这份日志的进程」的 cwd |
| 4 | **父目录名 + 文件名** | 例：`27\rollout-xxx.jsonl` |

| 决策 | 理由 |
| --- | --- |
| 第 2 档只认**确实是目录**的路径 | 命令行里到处是路径 —— 可执行文件、配置文件、目标文件。只有**真的是目录**的那个才可能是工作区。 |
| 第 3 档**只在前面都失败时**才调用 | 反查进程要枚举系统进程，不能对每个候选文件都做一遍。 |
| 第 4 档是**硬性兜底** | 宁可显示「这是哪个文件」，也**不再显示「未知工作区」** —— 后者会让用户以为雷达坏了。而 mcode 的会话目录名**本身就是会话 ID**，这个兜底反而很有用。 |
| 第 4 档**不写进 `cwd`** | 「父目录名 + 文件名」只是**标识**，不是真的工作目录。写进 `cwd` 会被挂载会话时当成真工作区用。 |
| 进程索引**只枚举一次** | `procscan.build_process_cwd_index()` 枚举一次系统进程，之后全是字符串匹配。否则几十个候选文件就是几十次全量枚举，慢到不能用。 |

### 4.3 扫描根目录 `radar.scan_roots`

```yaml
radar:
  scan_roots:
    - ".codex"                   # Codex
    - ".mcode"                   # MiniMax Code（社区习惯叫法）
    - ".claude"                  # Claude Code
    - ".minimax/v2/sessions"     # MiniMax Code 真正落日志的地方
```

* **相对路径按家目录解析**（`.codex` = `C:\Users\你\.codex`），
  **绝对路径原样使用**（`D:\项目`）；
* ⚠️ 第四项是**实地核对**后加的 —— Windows 版 MiniMax Code 的会话
  其实落在 `~/.minimax/v2/sessions`，只写 `.mcode` 扫不到任何东西；
* ⚠️ 雷达最多下探 **4 层**，所以要指向**会话目录本身**，
  别指向它的上级；
* 设置页「④ 挂载管理」里能直接改，改完写回 `config.yaml`。

### 4.4 默认只展示活跃文件

| 概念 | 判定 |
| --- | --- |
| **正在写入** | 距今 ≤ 5 分钟还有写入 |
| **会话主日志** | `messages.jsonl` / `history.jsonl` / `rollout-*` / claude 的 `*.jsonl` |

界面默认只显示「**正在写入**的**会话主日志**」，
其余（已静默的、附属的）收在一个复选框「显示其余 N 个文件」后面。

> 为什么要有「主日志」这一档：一个 mcode 会话目录下躺着 **4 个文件**
> （`messages.jsonl` / `llm-call.json` / `history-catalog.json` /
> `user-message-locators.jsonl`），再加上几十个早就跑完的历史会话 ——
> 全列出来就是「满屏垃圾」，用户根本找不到自己刚才跑的那个。

### 4.5 会话 ID 与首条消息时间

| 字段 | 从哪来 |
| --- | --- |
| `session_id` | 内容里的 `session_id` / `thread_id` …；找不到就从**路径**里找（mcode 的 `…-session_<id>` 目录名、codex 的 rollout 文件名 UUID） |
| `first_time` | 内容里的 `timestamp` / `time` / `started_at` …；支持 ISO 8601、epoch 秒、epoch **毫秒**（mcode 用毫秒） |
| `workspace_source` | `cwd` / `args` / `process` / `file` —— 界面上据此说明「这个路径是怎么来的」 |
