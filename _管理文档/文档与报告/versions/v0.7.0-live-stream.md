## 1. 本次目标

1. **实时流式日志监听（Tail -f）** —— 不再用 `read()` 一次性读完；
   引擎持续阻塞监听文件变化，新事件到达即刻审查；
   文件轮转 / 截断的边界情况不能崩。
2. **意图锚定与漂移检测** —— 知道 Agent 是否偏离了原始目标：
   每 5 个事件提取一次摘要，**连续 2 次**判定漂移才告警；
   告警走 Notifier 弹窗，**不触发 Guardian 挂起**。
3. **GUI 实时对接与多目标支持** —— SSE 接上流式数据；
   顶栏输入框随时设定 `task_goal`；漂移告警用橘黄色卡片。
4. **测试与文档** —— 实时性测试 + Mock 模型连续触发测试；
   `CHANGELOG`、版本文档、Git 标签三处一致。

## 2. 实时流式监听

### 2.1 接口

```python
# src/adapters/base.py
def tail_stream(
    self,
    file_path: Any,
    *,
    interval: float = 0.5,
    from_end: bool = True,
    stop_event: Optional[threading.Event] = None,
) -> Iterator[Event]:
```

`SentinelEngine.run(log_file_path, tail=True)` 进入流式模式，
CLI 对应 `--tail`。

### 2.2 三个关键设计（都是踩坑换来的）

#### ① 必须是「普通函数返回生成器」，不是「生成器函数」

```python
# ✅ 正确：起点在**调用时**锁定
def tail_stream(self, file_path, *, from_end=True, stop_event=None):
    offset = self._end_offset(file_path) if from_end else 0
    return self._follow(file_path, offset, interval, stop_event)

# ❌ 错误：起点在**首次迭代时**才锁定
def tail_stream(self, file_path, *, from_end=True, stop_event=None):
    if from_end:
        offset = self._end_offset(file_path)      # 第一次 next() 才执行
    yield ...
```

生成器函数的函数体**要到第一次 `next()` 才会执行**。
如果调用方拿到生成器之后、开始迭代之前，文件被追加了新内容，
那么这段内容会被**静默跳过** —— 监听「接上了」却漏掉了最关键的那几行。

#### ② 轮转后必须**无条件**更新 `self.identity`

`FileTailer` 靠文件身份（inode / 设备号）识别轮转。
原先只在「身份变了」时才更新保存值，于是轮转之后
**每次轮询都误判「又轮转了」** → 整个文件被反复重读 →
告警**无限重复**。

这条 bug 是**测试抓出来的**，不是想出来的 —— 表现是告警条数随时间线性爆炸。

#### ③ 半行处理

日志写到一半时不能读。`FileTailer` 保留缓冲区里不完整的尾巴，
等下一批字节补齐再吐出来。直接 `splitlines()` 会把半行当成完整行
交给解析器，然后被当成「坏行」跳过 —— 那一行就永远丢了。

### 2.3 边界情况一览

| 情况 | 行为 |
| --- | --- |
| 文件不存在 | 等待它出现（不报错、不退出） |
| 文件被截断（`> file`） | 检测到 inode 相同但大小变小 → 重新从头跟 |
| 文件被轮转（`mv` + 新建） | 检测到身份变化 → 重新定位到新文件末尾 |
| 读到半行 | 缓存，等补齐 |
| 某一行 JSON 非法 | 跳过该行，**不中断**整个流 |
| 收到停止信号 | 干净退出 |

### 2.4 终端可见性

流式模式的价值是「**看得见它在动**」，所以：

- 每条事件打一行 `[TAIL] #12 tool_call/Bash | pytest tests/test_auth.py -q`；
- stdout 在**重定向**场景下强制 UTF-8 + **行缓冲** ——
  否则输出被重定向到文件后还攒着 8KB 才落盘，实时性直接没了。

## 3. 意图锚定与漂移检测

### 3.1 概念

哨兵之前只能回答「这一步危不危险」。本轮多问一句：
「**Agent 还在做用户交代的事吗？**」

- **原始目标**（`task_goal`）= 锚点；
- 每收集 5 个 `tool_call` + `thinking` 事件 → 做一次判定；
- **连续 2 次**判定为漂移（= 10 步）才告警。

### 3.2 5 个事件的窗口里，摘要是怎么提取的

这是本版最需要解释的一环。

#### 输入进窗口的只有两类事件

```python
DRIFT_WINDOW_EVENTS = ("tool_call", "thinking")
```

`text` / `tool_result` **不参与** —— 它们是**结果**不是**意图**。
把结果混进去只会稀释窗口的信号密度（5 步里塞进 3 条结果，
真正表达意图的只剩 2 条）。

#### 摘要用「结构化确定性压缩」，**不是**「模型摘要」

```
第1步 [思考] 先看一下 auth 模块的登录逻辑，定位 session 校验失败的原因。
第2步 [Read] file_path=src/auth/login.py
第3步 [Edit] file_path=src/auth/login.py
第4步 [Bash] pytest tests/test_auth.py -q
第5步 [思考] 登录 bug 的根因是 token 过期时间没校验，已经改好并跑通了测试。
```

每一步的格式是 **`第N步 [类型] 内容`**：

| 步骤类型 | 内容来源 |
| --- | --- |
| `[思考]` | `thinking` 事件的正文 |
| `[工具名]` | 工具的**命令文本**（`Bash` → `rm -rf /tmp/build`） |
| `[工具名]` | 没有命令文本时退到**关键参数**（`Read` → `file_path=src/auth/login.py`） |

**为什么不让模型先做摘要？** 一个模型同时做「摘要」和「判断」两件事，
输出格式会明显不稳定 —— 旧项目 `dsh-plain-approval` 的 98 行 prompt +
8 个 JSON 字段，实测失败率 **44.9%**。
本项目让模型**只做判断**，输出契约只有 2 个字段：

```json
{"drift": true, "reason": "第2步起偏离，与重构auth模块无关"}
```

确定性压缩还**不丢信息**：每一步都保留了「类型 + 工具名 + 命令 / 路径」，
这些恰恰是判断漂移最关键的信号 ——
「一直在读同一个文件」= 在推进目标；「工具类型突然变了」= 可能跑偏。

#### 单步硬截断 180 字

```python
SUMMARY_STEP_LIMIT = 180   # 5 步 ≈ 900 字，7B 吃得下
```

不截断的话，一条超长的 `Bash` 输出能把整个窗口撑爆。

#### 窗口**不重叠**

5 步一窗 → 判定 → **清空缓冲** → 下一窗重新数。

这样「连续 2 次」= 恰好 10 步，与任务书要求一致；
窗口若重叠，同样两步会落在两个窗里，「连续」的语义就废了。

### 3.3 判定链路

```
5 个事件 ──> build_window_summary() ──> DRIFT_EVALUATE_TEMPLATE
                                              │
                    ┌─────────────────────────┴────────────────────┐
                    │ 7B 模型：{"drift": true/false, "reason": "..."} │
                    └─────────────────────────┬────────────────────┘
                                              │
                                   parse_drift_payload()
                                              │
                              ┌───────────────┴───────────────┐
                              │ drift=true  → 连续计数 +1     │
                              │ drift=false → 连续计数归零    │
                              │ 降级        → 视为「没漂移」   │
                              └───────────────┬───────────────┘
                                              │
                          连续计数 >= 2 ──> 触发 [WARNING] 意图漂移
```

### 3.4 三条「绝不误报」的底线

| 情形 | 行为 | 理由 |
| --- | --- | --- |
| 模型不可用 / 超时 / 熔断 | `drift=False, degraded=True`，**连续计数归零** | 「缺失绝不等同于有问题」 |
| 模型输出里**没有** `drift` 字段 | 判定**失败** → 降级 → 同上 | 宁可漏报不可误报 |
| `task_goal` 为空 | **完全不做判定**，不打扰模型 | 没有目标就没有「偏离」可言 |

### 3.5 漂移**不是红线**

漂移告警的 `severity` 是 `standard`（不是 `red_line`），
所以 `_maybe_intervene` 天然不碰它 —— **守护者不会挂起进程**。
跑偏是「可能做错事」，不是「马上要毁掉东西」。

它只做两件事：写进告警日志 + 走 Notifier 弹窗。

## 4. 看板实时对接

### 4.1 SSE 链路

```
引擎(tail 常驻) ──▶ 告警日志 ──▶ 看板 FileTailer ──▶ hub.publish ──▶ SSE ──▶ 浏览器
```

这条链路 v0.4.0 就有；v0.7.0 补上的是**引擎以常驻 tail 模式运行**，
于是链路里真的有了流式数据。

### 4.2 `TaskGoal`（多目标支持）

```python
class TaskGoal:
    def get(self) -> str: ...
    def set(self, goal: str) -> str: ...     # 变了就通知监听器
    def on_change(self, callback) -> None: ...
```

- `GET /api/task_goal` → 当前目标；
- `POST /api/task_goal` → 设定目标，并 `hub.publish({"type": "task_goal", ...})`；
- 监听器把新目标推给**正在运行**的引擎：
  `IntentTracker.set_goal()` 换锚点并**清零连续计数** ——
  换了目标，之前的判定就不作数了。

### 4.3 橘黄 vs 红色

| 语义 | 颜色变量 | 用途 |
| --- | --- | --- |
| 红线级 | `--danger` | 不可逆操作，守护者可能挂起 |
| 死循环 | `--warn: #ffb547` | 上下文模式告警 |
| **意图漂移** | **`--drift: #ff8c42`** | 语义级提醒，**只警告不干预** |

两者刻意拉开 —— 漂移卡片用**橘黄**，一眼能看出「它跟红线不是一回事」。

**几个能说明问题的细节**：

- 事件是**边写边审**的 —— 投喂脚本每 1 秒写一行，终端每 1 秒多一行；
- 第 1 个窗口（在干活）**没有**告警 —— 检测器**不乱报**；
- 第 2、3 个窗口（都在跑偏）连着判漂移 → 第 15 步后触发告警，
  正好是「连续 2 次 = 10 步」；
- 漂移告警带**真实 7B 解释**（`explanation_degraded: false`），
  不是兜底文案；
- `chmod 777` 的告警同样带真实解释，且 `severity=standard` ——
  没有触发守护者挂起。

## 7. 已知限制

1. **漂移判定要花模型时间** —— 每 5 步一次 7B 调用；
   流式模式下判定是**同步阻塞**的，慢模型会拖慢事件吞吐。
2. **降级即沉默** —— 模型不可用时漂移检测静默停摆，
   不会误报，但也不会提醒。
3. **`task_goal` 要人来填** —— 哨兵不会自动推断「用户本来想干什么」。
4. **漂移只警告** —— 不挂起进程；真要拦，得靠红线级判定。
