## 1. 本次迭代目标

把 v0.1.0 只有骨架的工程，变成**能真正跑起来**的两段式流水线：

```
JSONL 日志 ──▶ ① 采集层 Adapter ──▶ 统一事件 ──▶ ② 规则层 RuleEngine ──▶ 告警
```

明确**不做**的事：

- ❌ 不接入本地大模型（LLM 层留到 v0.4.0）
- ❌ 不做实时 tail / 断点续传（留到 v0.3.0）
- ❌ 不做多通道告警分发（留到 v0.5.0）

本版本的原则仍然是：**宁可漏报，不可误杀；确定性优先；只读旁观**。

## 2. 采集层（Adapters）接口设计

### 2.1 抽象基类 `BaseAdapter`

文件：`src/adapters/base.py`

```python
class BaseAdapter(abc.ABC):
    name: str = "base"

    @abc.abstractmethod
    def parse_payload(self, payload: dict) -> list[Event]:
        """把一个已解析的 JSON 对象拆成 0..N 个统一事件。"""

    def parse_line(self, line: str) -> list[Event]:
        """解析一行原始文本；非法 JSON 返回空列表。"""

    def read_stream(self, file_path_or_pipe: Source) -> Iterator[Event]:
        """逐行读取并 yield 解析后的事件。"""

    def iter_raw_lines(self, file_path_or_pipe: Source) -> Iterator[str]:
        """把「路径」或「已打开的流」统一成逐行文本迭代器。"""
```

**为什么这样切分职责**：

| 决策 | 理由 |
| --- | --- |
| 子类只实现 `parse_payload` | 读文件、跳坏行、跳空行是所有适配器共有的行为，不该让每个子类重写 |
| `parse_line` 负责 JSON 反序列化 | 非法 JSON 是**常态**（日志可能被截断），不能抛异常 |
| `read_stream` 是生成器 | 内存占用与日志长度无关，可以直接接管道做流式审查 |
| `file_path_or_pipe` 二合一 | 同一份代码既能审「落盘的历史日志」，也能审「正在产生的实时流」 |
| 只读打开文件 | 红线 R1：绝不写入被监控文件 |

**输入的三种形态**都支持：

```python
adapter.read_stream("logs/agent.jsonl")       # 文件路径（str / Path）
adapter.read_stream(sys.stdin)                # 管道
adapter.read_stream(io.StringIO(text))        # 内存流（测试用）
```

### 2.2 统一事件结构

事件是**普通 `dict`**（而不是 dataclass），理由：直接可 JSON 序列化落盘、
可直接进日志、直接跨进程传递。

```python
{
  "source":     "mcode",        # 归一化来源
  "type":       "tool_call",    # thinking / tool_call / text / result / unknown
  "session_id": None,           # 会话 ID，可能缺失
  "timestamp":  1750000000.0,   # 事件自带时间戳；没有就是 None（绝不伪造）
  "tool": {                     # 仅 tool_call 事件有值
      "name":      "Bash",
      "arguments": {"command": "rm -rf /"},
      "command":   "rm -rf /",  # 从参数中尽力提取的命令文本
  },
  "text":       "",             # thinking / text 事件的正文
  "raw":        {},             # 原始 JSON 载荷（便于回溯）
}
```

### 2.3 `McodeAdapter`

文件：`src/adapters/mcode.py`，针对 `mcode exec --output-format stream-json`。

**已知行形态**：

```jsonc
{"type": "thinking",  "thinking": "我需要先确认配置文件……"}
{"type": "tool_call", "tool_call": {"name": "Bash", "arguments": {"command": "ls -la"}}}
{"type": "text",      "text": "好的，已经列出了目录内容。"}
{"type": "result",    "result": {"status": "ok"}}
```

**兼容的变体**（不同版本 mcode 的字段命名并不统一，适配器在此归一化）：

| 变体 | 写法 |
| --- | --- |
| 扁平 + `arguments` | `{"type":"tool_call","name":"Bash","arguments":{...}}` |
| 扁平 + `args` | `{"type":"tool_call","name":"Bash","args":{...}}` |
| Claude 风格消息 | `{"type":"assistant","message":{"content":[{"type":"thinking",...},{"type":"tool_use","name":...,"input":{...}}]}}` |

> **为什么兼容这么多形态**：适配器的职责就是**收敛差异**，规则层只认
> 「工具名 + 参数」这一个契约。若让规则层去猜字段名，每加一个 CLI 工具
> 就要改一次规则层 —— 这正是架构文档里「单向依赖、可插拔」要避免的。

**抽取重点**（任务书指定）：

- `thinking` → 事件 `type="thinking"`，正文落在 `text`；
- `tool_call` → 事件 `type="tool_call"`，工具名与参数落在 `tool`，
  并从参数中提取 `tool["command"]`（规则层的正则直接作用在它上面）。

### 2.4 新增一个适配器的步骤

1. 在 `src/adapters/` 新建 `<cli>.py`，继承 `BaseAdapter`；
2. 实现 `parse_payload()`，返回 0..N 个统一事件；
3. 在 `tests/` 补一条**真实日志样本**（脱敏后）的解析用例；
4. 更新 `docs/ARCHITECTURE.md` 的模块映射。

## 3. 规则层（L1，Rules）接口设计

文件：`src/rules/basic.py`

### 3.1 对外接口

```python
class RuleEngine:
    def __init__(self, config: dict | None = None, *, config_path: str | None = None): ...
    def check_event(self, event: dict) -> dict: ...
    def reset(self) -> None: ...
```

`check_event()` 的返回值**必定包含** `verdict` 与 `reason` 两个键：

| `verdict` | 含义 | 触发条件 |
| --- | --- | --- |
| `ON_TRACK` | 未发现异常 | 默认返回 |
| `DANGEROUS` | 命中高危命令 | `tool_call` 的命令 / 参数匹配到高危正则 |
| `LOOP` | 疑似死循环 | 连续 N 次读取同一个文件 |

完整返回结构：

```python
{
  "verdict":    "DANGEROUS",
  "reason":     "匹配到高危命令: rm -rf",
  "rule_id":    "dangerous_command",   # 或 "repeat_read_loop" / None
  "evidence":   "rm -rf",              # 触发判定的片段
  "level":      "critical",            # info / warn / critical
  "confidence": 1.0,
  "pattern":    r"\brm\s+(?:...)",      # 命中的正则原文
}
```

### 3.2 规则层的三条硬约束

1. **绝对不调用任何模型** —— 本模块不 import `requests`，不 import Ollama 客户端。
   纯正则 + 纯逻辑，相同输入必然得到相同输出。
2. **纯函数式判定** —— `check_event()` 不做 IO、不打印、不抛异常；
   状态只保留在 `LoopDetector` 里，且可用 `reset()` 复位。
3. **判定与解释分离** —— 规则层只回答「是不是危险」，不回答「为什么危险」。
   后者留给 L2 模型层（v0.4.0）。

### 3.3 高危命令检测

- **内置表**（`DEFAULT_DANGEROUS_COMMANDS`，17 条）覆盖：
  `rm -rf` / `sudo` / `chmod 777` / `git push -f` 这四类是任务书点名要求的，
  其余是同等级、同样会造成不可逆损失的操作：
  `rmdir /s`、`del /f`、`Remove-Item -Recurse`、`format X:`、`mkfs`、
  `dd of=/dev/`、`Invoke-Expression`、`Set-ExecutionPolicy Unrestricted`、
  `chown -R root`、`curl|sh`、`wget|sh`、`history -c`、`shutdown/reboot/halt`。
- **配置增量**：`config/config.yaml` 的 `rules.dangerous_commands`
  默认**追加**到内置表之后；置 `rules.dangerous_commands_replace: true`
  可改为整体替换。
- **匹配范围**：命令文本 **加上** 序列化后的工具参数 ——
  命令藏在 `cmd` / `script` 等字段里时同样能命中。
- **正则细节**：`git push --force-with-lease` **不会**被误判为强推
  （用 `(?![-\w])` 收敛边界）；`rm -f` 不会误判（需要出现 r/R）。

### 3.4 死循环检测（状态机）

```python
class LoopDetector:
    def observe(self, event: dict) -> Optional[str]: ...
```

状态迁移：

```
IDLE ──读文件 A──▶ READING(A, 1)
READING(A, n) ──再读 A──▶ READING(A, n+1)
READING(A, n) ──读别的文件 / 做别的事──▶ IDLE
READING(A, count >= threshold) ──▶ 触发 LOOP
```

- 阈值：`rules.loop.same_file_read_threshold`，默认 **3**；
- 「读」与「写/执行」的区分靠**工具名特征**（`read` / `cat` / `view` vs
  `write` / `edit` / `delete` / `bash` …），写特征优先于读特征判断，
  避免 `read_and_write` 之类的名字误判；
- 路径归一化：统一分隔符、去尾斜杠、转小写后比较
  （Windows 上同一文件的路径大小写可能不一致；这个方向的误报只会多一条告警）；
- **扩展接口**：新增「相同命令重复」「相同参数重复」等模式时，
  照抄 `observe(event) -> Optional[str]` 契约实现新检测器即可，
  上层 `RuleEngine` 不需要改动。

## 4. 主流程（Core）设计

文件：`src/core/engine.py`

```python
class SentinelEngine:
    def __init__(self, adapter, rule_engine, *,
                 alert_log_path=None, console=True, alert_logger=None): ...
    def run(self, log_file_path) -> dict: ...
```

`run()` 的流程：

```
for event in adapter.read_stream(log_file_path):
    verdict = rule_engine.check_event(event)
    if verdict.verdict in ("DANGEROUS", "LOOP"):
        alert = build_alert(event, verdict)
        emit(alert)     # 终端红色警告 + logs/sentinel_alert.log
```

返回摘要：

```python
{
  "log_file": "logs/agent.jsonl",
  "adapter": "mcode",
  "total_events": 13,
  "counts": {"ON_TRACK": 9, "DANGEROUS": 3, "LOOP": 1},
  "alerts": [ ... ],
}
```

**告警输出双通道**：

| 通道 | 内容 | 说明 |
| --- | --- | --- |
| 终端 | 红色高亮的一行摘要 | 等级 / 判定 / 原因 / 工具 / 命令 |
| `logs/sentinel_alert.log` | 文本摘要 + `ALERT_JSON` 结构化行 | UTF-8，便于复盘与机器消费 |

> **终端编码兜底**：Windows 控制台走 UTF-16 通道，中文天然正常；但 stdout
> 被重定向到文件或管道时会退回 ANSI 代码页，中文变乱码。
> 因此重定向场景下 stdout 会被切到 UTF-8；若终端编码实在装不下中文，
> 终端输出降级为 ASCII 摘要（保留等级 / 判定 / 规则 / 命令），
> **告警日志始终是 UTF-8，不受影响**。

**命令行入口**：

```bash
python -m src.core.engine tests/fixtures/mcode_sample.jsonl
# 有告警时退出码为 1，可直接接入 CI
```

## 5. Prompt 资产：与历史插件的取舍

文件：`src/llm/prompts.py`，模板名 `SENTINEL_EXPLAIN_TEMPLATE`。

### 5.1 来源

提取自早期插件 `dsh-speak-human工作区/dsh-plain-approval/src/prompt.js`
的 **v0.7.0** 版本 —— 那是该插件迭代中失败率最低的一版：

| 版本 | Prompt 规模 | JSON 字段 | 单次调用失败率 |
| --- | --- | --- | --- |
| 旧版 | 98 行 / 17 条硬规则 | 8 个 | **44.9%** |
| v0.7.0 | 四段 | 4 个 | 显著下降 |

### 5.2 继承下来的四条

1. **模型不判风险** —— 风险、建议、读写类型全部由本地规则给出，
   模型只负责「说人话」。凡是让模型二选一的指令，都是格式不稳定的重灾区。
2. **证据优先级** —— ① Agent 自述（思考过程）→ ② 用户最近的指令
   → ③ 命令实际行为（用于校验前两者是否自洽）。
3. **如实写出落差** —— Agent 说的和实际在做的对不上时必须写出来，
   不替 Agent 圆场。
4. **禁止编造** —— 不确定就明说「无法确定，请查看原始调用」。
   编造的理由比不写更危险，因为它会让人**跳过**检查原始调用。

### 5.3 为哨兵做的删减

- 去掉 `risk` / `advice` / `mode` 三个字段 —— 这些结论由 L1 规则层给出，
  哨兵不在模型层重复判定，更不让模型替规则层「洗白」。
- 去掉「不要瞎猜，A/B/C 照抄」整段 —— 本机地址、临时文件、系统目录这类
  情况本地规则早已判完并作为事实给出，模型再抄一遍只会引入不一致。
- 新增一条定位约束：哨兵是**只读观察者**，模型**不得**输出
  「建议终止」「建议放行」这类干预结论 —— 处置由人和规则层决定。

### 5.4 输出契约

```json
{"title": "...", "why": "...", "touch": "...", "outcome": "...", "parts": []}
```

`title` ≤ 34 个汉字（放告警最顶上，3 秒内要被看懂）。

> v0.2.0 **不接入任何模型**，该模板仅作为 v0.4.0 的资产预置。
