## 2. 任务一：真实并发压力测试

### 2.1 为什么不能只在演示模式里看

演示模式是**我们自己造的日志** —— 它当然整齐。
真正会出事的是：**两个 Agent 同时跑、看板同时推、其中一个撞红线**。

所以压测必须满足四条硬要求：

| # | 要求 | 怎么做到 |
| --- | --- | --- |
| 1 | Agent 是**真的** | 用 `run_with_sentinel.py` 的 `AgentSession` 起真的 `codex.EXE` |
| 2 | 看板是**真的** | 进程内起真的 `uvicorn` + FastAPI 应用 |
| 3 | SSE 是**真的** | 两个真的 `requests` 流式客户端连 `/api/events` |
| 4 | 干预走**真的**链路 | 注入 codex 格式的原始载荷 → 适配器 → 规则引擎 → 守护者 |

### 2.2 ★ 一个必须说清楚的设计前提

> **意图漂移与死循环（LOOP）不是红线** —— 它们**只警告、不挂起**
> （这是 v0.7.0 起的既定设计：「意图漂移不是红线」）。

所以「让守护者精准挂起那一路」**不能**用漂移或 LOOP 来验 ——
用它们验，得到的必然是「谁也没被挂起」，那是**设计如此**，不是 bug。

压测把这件事**拆成两件分别验**：

| 验什么 | 用什么事件 | 期望结果 |
| --- | --- | --- |
| 精准干预 | **红线级**（批量删除） | A 路被挂起，**B 路继续跑** |
| 不误伤 | **死循环**（连续失败的 pytest） | B 路**只告警**，**不挂起** |

### 2.3 ★「串台」的判据不是「有没有收到别人的事件」

这是一个**很容易搞错**的地方。

`/api/events` 是**全局流** —— 所有会话的事件都走它，
靠 `session_id` 区分（前端据此分流到不同会话）。

> 所以「A 的客户端收到了 B 的事件」**本身不是 bug** —— 那是全局流的正常行为。

真正的「串台」是**归属错误**：

- 同一个 `alert_id` 出现在**两个**会话名下 → 串台；
- SSE 里的告警 `alert_id` 跟看板 API 返回的对不上 → 串台。

压测的判据就是这两条。

### 2.4 ★ 压测暴露的真 bug：多路引擎共用一个 logger

第一轮压测的结果是 **4/6**，失败的两项把根因指向了同一个地方：

```
logs/stress-a.log  →  0 行
logs/stress-b.log  →  含 A 路的红线告警
```

**A 路的告警写进了 B 路的日志文件。**

原因在 `src/core/engine.py`：

```python
# 修复前
self.logger = alert_logger or logging.getLogger("sentinel.alert")
```

所有引擎共用 `sentinel.alert` 这一个 logger。
每个引擎在构造时都会：

```python
for handler in list(self.logger.handlers):
    self.logger.removeHandler(handler)      # ← 把别人的 handler 也摘了
```

于是**后建的引擎会把先建的文件 handler 顶掉** —— 先建的那路的告警，
从此全部落进最后一个引擎的日志文件。

> 这是一个**只在多路场景下才会暴露**的 bug：
> 单路模式下「只有一个引擎」，摘来摘去都是自己的，**看不出任何异常**。

修复是**每个引擎一个专属 logger**：

```python
self.logger = alert_logger or logging.getLogger(
    f"sentinel.alert.{uuid.uuid4().hex[:8]}"
)
```

并且在摘 handler 时**只摘自己的**：

```python
for handler in list(self.logger.handlers):
    if getattr(handler, "_sentinel_owner", None) == id(self):
        self.logger.removeHandler(handler)
```

> 这个 bug 本身就是压测的价值 ——
> **演示模式永远发现不了它**。

### 2.5 ★ 第二个真 bug：「真实管道接管」路径漏接了上下文检测器

压测要验「死循环只告警不挂起」，注入连续失败的 pytest 后 —— **一条告警都没有**。

查下去发现：`run_with_sentinel.py` 装配引擎时**根本没传** `context_tracker`：

```python
self.engine = SentinelEngine(
    build_adapter(self.profile.adapter),
    _build_rule_engine(config),
    alert_log_path=self.alert_log,
    ...
    llm_client=llm_client,
    intent_tracker=intent_tracker,     # ← 有漂移追踪器
    # context_tracker=???               # ← 没有上下文追踪器
)
```

CLI 路径（`src/core/engine.py` 的 `main()`）是接了的，
**只有「真实管道接管」这条路漏了**。

后果：`[STUCK]`（连续测试失败）和 `[LEAK]`（敏感文件读取后外发）
在真实接管时**一次都不会报** —— 而 README 里把它们列为已交付能力。

> 这正是压测的价值：这两条路径**只有真跑一遍**才会发现不一样。

修法与 CLI 保持一致（上下文检测**只读**、纯状态机，接上零风险）。

### 2.6 ★ 第三个真 bug：多路模式下 Token 计数器永远停在 0

看板顶栏的「已消耗 Token」在单路下好好的，一到多路就**永远是 0**。
两个原因叠在一起：

**原因一：事件打会话 ID 时被载荷抢走了。**

引擎写进账单行的 `session_id` 是 **Agent 名**（`codex`）：

```json
TOKEN_JSON {"session_id": "codex", "total_tokens": 203841, ...}
```

而看板的会话 ID 是 `stress-b` —— **两套不同的命名空间**。
事件打 ID 时用的是 `setdefault`，载荷里的 `codex` 就把 `stress-b` 顶掉了：

```python
data.setdefault("session_id", self.session_id)   # ← 载荷里有值就不改
```

前端一看「这条不属于当前会话」，直接丢掉。

**原因二：切换会话走的接口压根没返回 `tokens`。**

`AlertStore.status()` 有 `tokens`，`AlertStore.snapshot()` **没有** ——
而前端 `loadSessionContent()` 走的正是 `snapshot()`。

两处都修了：事件**强制**打上看板的会话 ID，快照也带上 `tokens`。

> 单路模式为什么看不出来？因为单路时 `state.activeSession` 是空的，
> `isActiveSession()` 对任何 session_id 都返回 true —— **两个 bug 都被掩盖了**。

### 2.7 ★ 压测脚本踩到的第四个坑：codex 在非 Git 目录里拒绝运行

压测目录是临时目录（`tempfile.mkdtemp`），**不是 Git 仓库**。
codex 直接拒绝：

```
Not inside a trusted directory and --skip-git-repo-check was not specified.
```

两个进程都**什么也不干** —— 而压测的判据只看「有没有产出事件」，
于是会得到一个**假通过**（或者更糟：一个看起来像失败的假失败）。

脚本现在**自动补上**这个参数：

```python
if args.agent == "codex" and "--skip-git-repo-check" not in extra_args:
    extra_args.append("--skip-git-repo-check")
```

### 2.8 ★ 第五个坑：进程「退出」≠ 进程「挂起」

守护者挂起进程之后，脚本要判断「A 路是不是真的被挂起了」。

如果只判断「进程还在不在」，会把**已经跑完退出的** Agent 误判成「没被挂起」，
反过来也会把「早就退出了」误判成「被挂起」。

判据必须分两步：

```python
if proc.poll() is not None:
    return False        # 已经退出了 —— 这不是挂起
# 再逐线程查内核态
```

### 2.9 ★ NT 线程挂起态怎么读

Windows 上没有「进程挂起」这个概念 —— 挂起是**逐线程**的
（`NtSuspendProcess` 会把每个线程都挂起）。

判据：

- 用 NT 的**信息类 35**（`ThreadSuspendCount` 一类的线程状态信息）逐线程查；
- **全部线程**都处于挂起态，才算整个进程被挂起；
- 公开枚举里的 `0` 是 `ThreadBasicInformation`，
  它**永远**返回 False —— 用它判挂起会得到「永远没挂起」。

`ctypes` 调用**必须声明 `argtypes`** —— 不声明时 64 位下的参数宽度会错，
读回来的状态是垃圾数据。

> 这套探测逻辑在 `_构建与发布/scripts/fire_drill.py` 里已经有
> （`thread_suspended()`），压测直接复用，没有第二份实现。

## 3. 任务二：Webhook 真实失败重试

### 3.1 ★ 原先的致命问题：一次网络超时能卡住主循环 10 秒

```python
# 修复前
def send(self, verdict):
    requests.post(self.url, json=payload, timeout=10)   # ← 同步、阻塞
```

`send()` 是在**引擎主循环**里调的。
一个 10 秒的网络超时 = **引擎主循环卡 10 秒** ——
这直接违反架构红线 R5（审查侧的异常绝不能影响被监控 Agent）。

而「加指数退避重试」会把这件事**放大 3 倍**（1 次 → 3 次 = 30 秒）。

> **两个要求（「要重试」+「不能阻塞主流程」）同时成立，
> 唯一的干净做法就是把投递挪到后台线程。**

### 3.2 改造后的结构

```
主线程                     后台投递线程
──────                     ─────────────
send()                     ┌──────────────────────┐
  │ 校验                     │ 取任务（阻塞等待）    │
  │ 入队（有界队列 32）  ──▶ │ 尝试投递              │
  │ return「已入队」         │  失败 → 指数退避重试  │
  │ ← 微秒级                │  成功 → 记 last_delivered│
                            └──────────────────────┘
```

- `send()` **只做校验 + 入队**，**微秒级**返回；
- 真实 HTTP 在后台线程里做；
- 队列**有界**（32）—— 满了就丢弃并记日志，
  不能让**告警**把内存吃光。

### 3.3 重试策略：只重试「重试有用」的错误

| 情况 | 动作 | 为什么 |
| --- | --- | --- |
| 网络错误 / 超时 | **重试** | 可能是网络抖动 |
| 5xx（500/502/503/504） | **重试** | 服务端临时故障 |
| 408 / 425 / 429 | **重试** | 请求超时 / 过载 / 限流 |
| 4xx（400/401/403/404…） | **立刻放弃** | URL 写错、签名错 —— **重试多少次都一样** |

退避序列：`1s → 2s → 4s`（`max_retries=2` 即总共尝试 3 次）。

### 3.4 失败提示必须是人话

```
webhook 投递最终失败（共尝试 3 次）：HTTP 500 Internal Server Error。
请检查网络连通性、URL 是否正确、是否需要加签密钥。
本次告警未能推送到手机。
```

最后一句是关键 —— **明确告诉用户「手机那头什么也没收到」**，
而不是让用户对着一个 HTTP 状态码猜。

### 3.5 防骚扰占位必须在失败后释放

原先的逻辑是「记一次就占位 60 秒」。
如果这次推送**失败了**，占位却还在 —— 那么 60 秒内**同类型事件都不会再推**，
哪怕网络已经恢复了。

修复：**投递失败就撤销占位**，让下一次事件能重新尝试。

> 「没送到手机就不会静音后续同类事件」—— 这是 v1.1.0 实机验证的 5 项之一。

### 3.6 实机结果（真 HTTP，5/5 通过）

故障注入服务器：`_构建与发布/scripts/webhook_fault_server.py`
（路径 `/ok`、`/flaky`、`/always500`、`/timeout`、`/slow`、`/status/<code>`，
并记录收到的**每一个**请求，用来断言「客户端到底重试了几次」）。

| # | 检查 | 结果 |
| --- | --- | --- |
| 1 | 指数退避重试到成功 | ✅ 服务端收到 **3** 次请求，总耗时 **1399 ms**，最终投递成功 |
| 2 | 重试耗尽后有中文提示 | ✅ 服务端收到 **3** 次请求，投递失败，**中文提示存在** |
| 3 | 失败后释放防骚扰占位 | ✅ 累计失败计数 1，可再次推送 |
| 4 | **投递不阻塞主事件流** | ✅ `send()` 入队耗时 **0.50 ms** vs 网络超时 **2000 ms** —— **差 3979 倍** |
| 5 | 4xx 不做无谓重试 | ✅ 服务端只收到 **1** 次请求 |

第 4 项是这一版**最硬的一条证据**：
`0.50 ms` vs `2000 ms` —— 主事件流**完全不受网络影响**。

## 4. 任务三：Token 消耗审计

### 4.1 为什么需要它

「跑偏的 Agent 会白白烧掉 Token」是共识，但**烧了多少**一直是个黑箱。

更糟的是：**没人能凭直觉判断「该不该叫醒它」**。
一个烧了 3 万 Token 的漂移 Agent，和一个烧了 300 Token 的，
危险程度天差地别 —— 但在看板上长得一模一样。

### 4.2 估算规则：有 usage 用真值，没有才估

```python
def estimate_tokens(text: str) -> int:
    cjk = len(_CJK_PATTERN.findall(raw))     # CJK：1 字 ≈ 1 Token
    others = len(raw) - cjk                   # 其它：4 字符 ≈ 1 Token
    return int(cjk + others / 4 + 0.5)
```

- **CJK 字符**：1 字 ≈ 1 Token（中文的 tokenize 通常不吃亏，取保守值）；
- **其它字符**：4 字符 ≈ 1 Token（英文通用经验值）。

估出来的数字带 `estimated=True`，看板计数器上**带 `~` 标记和虚线边框** ——
**估算不冒充真值**。

### 4.3 ★ usage 是快照，不是增量

这是最容易踩的一个坑。

codex 的 `turn.completed` 报的是「**到目前为止的上下文总量**」：

| 回合 | `input_tokens` 含义 |
| --- | --- |
| 第 1 回合 | 第 1 回合的输入 |
| 第 2 回合 | 第 1 回合 **+** 第 2 回合的输入（**累计**） |

把它当增量累加 = **重复计数好几倍**。

所以 `TokenLedger.record_usage()` 的做法是：

> **真值来了就替换估算值** —— 不是累加。

```python
def record_usage(self, usage):
    ...
    self.estimated_tokens = 0        # 真值覆盖此前的估算
    return self.input_tokens + self.output_tokens
```

### 4.4 「挽回 Token」怎么算

一次拦截（守护者挂起 / 连续漂移告警）省下的是**两段**：

```
已烧掉的   = 本次会话累计消耗
             （这段工作正在走向危险动作，本就是无效消耗）

本来要烧的 = 每步均摊 Token × 预估剩余步数
             （Agent 若不被拦住，还会继续跑下去）

挽回 = 已烧掉的 + 本来要烧的
```

- **每步均摊** = 累计 Token ÷ 已处理事件数；
- **预估剩余步数**默认 **10** 步（`DEFAULT_REMAINING_STEPS`）——
  一次典型任务的收尾量级。

对外文案：

```
本次异常已拦截，预估为您挽回 3.2 万 Token 的无效消耗
```

**只在真的拦下来了 / 真的连续漂移时才展示** ——
拦不住时**不**给这个提示（那会是一句空话）。

### 4.5 Token 账单行：第三种机器行

告警日志的「格式契约」里现在有三种机器行，
**引擎写、看板读，两边各持一份常量**：

| 行 | 含义 |
| --- | --- |
| `ALERT_JSON {json}` | 一条完整告警 |
| `ALERT_UPDATE_JSON {json}` | 原告警的**补充更新**（人话解释回填） |
| `TOKEN_JSON {json}` | **Token 账单行**（v1.1.0 新增） |

账单行**节流**（每累计 100 个 Token 才写一行）—— 不让日志翻倍膨胀。

### 4.6 usage 事件**不进规则引擎**

`usage` 不是「Agent 做了什么动作」，它是一张**账单**。

所以它：

- **不进规则层**（不是可审查的动作）；
- **不计入 `ON_TRACK`**（否则「一切正常」的计数会被账单事件污染）；
- 只做一件事 —— 更新 Token 台账。

## 7. 已知限制

- **usage 只有 codex 会报** —— mcode / claude 目前**没有** usage 字段，
  只能按字符估算（计数器会标 `~`）；
- **「挽回 Token」是估算，不是账单** —— 「本来还要跑 10 步」是经验值，
  不是预测模型；
- **`send()` 语义变了** —— 现在返回「**已入队**」而不是「**已送达**」。
  外部集成方若需要确认送达，必须调 `flush(timeout)`；
- **挂起的是 Agent 进程，不是它派生的子进程** —— 子进程会继续跑完；
- **多路模式共用一个通知通道** —— 好处是不会重复推送，
  代价是无法给不同会话配不同的 Webhook；
- **压测的「精准干预」用的是注入的红线事件**（走真实的
  适配器 → 规则引擎 → 守护者链路），不是等 Agent 自己去踩红线 ——
  后者不可复现；
- **Claude 适配器仍未实机验证**（本机没装 `claude` CLI）。
