# v3.3.0 —— 无自启用完即走 · 引擎心跳 · 时间盒拦截

> 这一版做四件事：
>
> 1. **彻底铲除开机自启与后台静默驻留** ——
>    用户明确要求「**拒绝任何形式的开机自启动和后台静默驻留**」，
>    工具必须「**用完即走，想开才开**」。
>    这一条是**第一优先级**，不是顺手改的文案：
>    脚本、快捷方式、隐藏启动器、`--daemon` 参数、后台自检线程
>    **全部删除**，不是只从文档里抹掉名字；
> 2. **让哨兵当引擎的保姆** —— NInfer 掉线时立刻红色告警，
>    而不是「不声不响地让 L2 整个停用」；
> 3. **把《Agent 跑偏警示录》的根因变成产品逻辑** ——
>    「一个子任务吃掉整轮」从「事后写进报告」升级成「**当场拦截**」；
> 4. **给 Defender 误杀一个明确的解法** ——
>    手动双击 exe 被拦这件事，得有看得见的处置步骤。
>
> ⚠️ **红线一字未改** —— R1–R9 与 v2.1.0 **完全一致**。
> 删掉自启反而让 R7「不悄悄改系统设置」**更彻底**。

## 1. 红线：这一版一个字都没改

| 红线 | 这一版怎么守的 |
| --- | --- |
| R1 只读监听 | 心跳探活用**只读**的 `GET /models`，不写引擎任何一个字节 |
| R2 不干预代码 | 时间盒只**判定与告警**；挂起走守护者那条**已授权**的路 |
| R3 不注入进程 | 心跳是独立线程，不碰被监控进程 |
| R4 本地闭环 | 看门狗**只盯本机地址**；云端 API **不探**、不喊 |
| R5 旁路失败 | 探活抛异常只降级；看门狗线程死了不影响审查 |
| R6 不终止进程 | 看门狗**不杀也不拉**任何进程 —— 只**说**「掉了，你手动拉」 |
| R7 不悄悄改系统设置 | **删掉自启**让这一条更彻底：哨兵**不再**往「启动」文件夹、注册表 Run 键写任何东西 |
| R8–R9 | 与 v2.1.0 一致 |

⚠️ 特别说明三条容易紧张的：

- **看门狗绝不自动拉起引擎** —— 用户的要求是明确的：
  「**不要尝试自动拉起，保持只读监控的边界**」。
  哨兵**替用户启动一个进程**就不再是只读监控了；
  而且引擎启动要吃显存，在用户正被别的东西占满显存的时候自动拉它，
  只会把机器拖得更垮。所以只**说**，**不动手**；
- **时间盒挂起死磕**只在**守护者已经武装**时才发生 ——
  用户把 `intervention_mode` 设成 `guardian`，
  就等于说了「该拦的给我拦」，不必再配一遍；
  显式写 `guardian_suspend: false` 可以永远只告警；
- **清理旧残留由用户自己动手** ——
  哨兵只**检测**并**显眼地提示**，删用户系统里的文件是**用户的决定**。

## 2. 任务一：彻底铲除开机自启与后台静默驻留

### 2.1 为什么这是第一优先级

v3.1.0 ~ v3.2.1 提供的链路是：

```
双击 install_startup.bat
    → 在 Windows「启动」文件夹放一个快捷方式
        → 指向一个隐藏窗口的 VBS
            → 开机时 wscript 静默拉起 sentinel.exe --daemon
                → 后台自检线程盯着看板，崩了自己复活
```

用户的要求是：**「彻底拒绝任何形式的开机自启动和后台静默驻留」**。

这意味着**光改文档不算数** —— 得能在**代码层**证明这些东西没了。
所以这一版的验收断言方向和 v3.1.0 **正好相反**：

| | v3.1.0 | v3.3.0 |
| --- | --- | --- |
| 断言 | 自启脚本**存在**而且能用 | 自启脚本**一个都不许再存在** |
| 文件 | `tests/test_v310_persistence_and_daemon.py` | `tests/test_v330_no_autostart.py` |

### 2.2 删了什么

**文件**：

* `install_startup.bat`（仓库根目录）—— 已删除；
* `_构建与发布/scripts/install_startup.ps1` —— 已删除；
* `_构建与发布/dist/sentinel_startup.vbs` —— 已删除。

**代码**：

* `src/gui/server.py`：删掉 `--daemon` 参数、
  `_start_daemon_watchdog()`、`_probe_http()`、`_DAEMON_STATE`、
  `DAEMON_CRASH_LOG`、`_serve_with_daemon()`；
  `_serve()` 现在崩了**退出**并写 `logs/sentinel_crash.log`；
* `_构建与发布/scripts/sentinel_entry.py`：删掉 `--daemon` 的帮助、
  `_is_daemon()` 及其**全部**分支 ——
  出错一律走 `_wait_for_user()`（不闪退的老承诺保住）；
* `src/core/engine_watchdog.py`：删掉「自动重拉引擎」，
  连带 `subprocess` 导入一起删掉 —— 不导入它就**不可能**偷偷拉进程。

### 2.3 旧机器上的残留怎么办

**光删代码不够**：已经装过的机器上还有残留。
快捷方式还在「启动」文件夹里，VBS 还在 dist 目录里，
用户下次开机照样会被静默拉起来 —— 而他以为早就删干净了。

所以哨兵现在**每次启动都主动看一眼**（`src/core/autostart_residue.py`）：

```
!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!
  ⚠️  这台机器上还留着**哨兵的开机自启残留**！
!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!

  v3.3.0 起哨兵**不再有**开机自启功能 ——
  「用完即走，想开才开」，不会在开机时静默驻留。
  但下面这些东西是**旧版本**留下的，不删的话下次开机还会被拉起来：

    · [快捷方式] C:\Users\...\Startup\哨兵 Sentinel.lnk
      删掉这个文件，或跑清理脚本。

  一次清干净（管理员 PowerShell 里跑）：

    powershell -NoProfile -ExecutionPolicy Bypass -File "_构建与发布\scripts\remove_startup_residue.ps1"
```

⚠️ **这个检测器只读不写** ——
它**只检测、只提示**，不替用户删东西。
删用户系统里的文件是**用户的决定**，哨兵不越俎代庖（R7）。

真要删，跑 `_构建与发布/scripts/remove_startup_residue.ps1`：

| 它清什么 | 怎么清 |
| --- | --- |
| 「启动」文件夹里的 `哨兵 Sentinel.lnk` | `Remove-Item` |
| `dist\sentinel_startup.vbs`、`logs\sentinel_startup.vbs` | `Remove-Item` |
| 注册表 Run 键里名字或值带「哨兵 / sentinel」的条目 | `Remove-ItemProperty` |

* `-Status`：**只看不删**；
* `-KeepRunKeys`：只删快捷方式与 VBS，保留注册表条目；
* ⚠️ 这个脚本**只许清理，不许新建** ——
  新建就等于把自启又装回去。

### 2.4 本机实况

| 检查项 | 结果 |
| --- | --- |
| 「启动」文件夹 | ✅ 只剩 `desktop.ini`，哨兵快捷方式**已删** |
| `HKCU` / `HKLM` 的 `Run` 键 | ✅ **查无哨兵条目**（v3.1.0 的自启本来就只写「启动」文件夹，不碰注册表） |
| `dist` / `logs` 里的 VBS | ✅ 无 |
| `remove_startup_residue.ps1 -Status` | ✅ 输出「[干净] 没找到任何自启残留」 |

## 3. 任务二：NInfer 存活监控

### 3.1 为什么必须有

v3.2.1 实机遇到过一次：引擎进程**直接没了**，端口没人听。

后果非常隐蔽：

| 层 | 引擎掉线后 |
| --- | --- |
| L1 规则层 | ✅ 照常工作 —— 删文件、越权照样红色告警 |
| L2 判定 / 人话解释 | ❌ **整个停用** |
| 用户看到的 | 一堆干巴巴的 `[CRITICAL] DANGEROUS: rm -rf …`，**没有解释** |

用户的第一反应必然是「**哨兵坏了**」，而不是「引擎掉了」。
这一版要的就是把这件事**明明白白说出来**。

### 3.2 三条硬约束

1. **只读** —— 探活只用 `GET /models`。
   **不触发推理**、不烧显存，也不会让 27B 模型跑一轮思考
   （那要 40 秒，每 30 秒跑一次等于自己把自己拖垮）。
2. **不撞车** —— NInfer 是 `--max-concurrency 1`，
   同时两个请求**引擎会崩**。
   所以探活前会**非阻塞地**抢那台引擎的串行锁：
   抢不到就**跳过这一拍**（引擎正在推理，说明它活着）。
3. **绝不抛异常** —— 审查侧的任何异常都只降级（架构红线 R5）。

### 3.3 告警长什么样

掉线：

```
[CRITICAL] NInfer 引擎已掉线！L2 判定和解释已停用！
（地址 http://127.0.0.1:8888/v1，最近一次心跳：连不上（服务没启动？））
```

恢复：

```
[OK] NInfer 引擎已恢复！L2 判定和解释重新可用。
（地址 http://127.0.0.1:8888/v1，探活耗时 1 毫秒）
```

这两条走的是**和普通告警完全一样**的通道：
终端 + 告警日志（看板靠它显示）+ 通知通道（**手机推送**）。

⚠️ 触发标记新增 `engine_offline` —— 配了 Webhook 的用户
需要在 `alert.channels.webhook.triggers` 里加上它才会推到手机。

### 3.3.1 ⚠️ 引擎刚重启时会先回 HTTP 503（实机发现）

把引擎重新拉起来之后，`GET /v1/models` 会**先回 503**
（模型还在加载），过一会儿才回 200。

看门狗的判定是「**回 2xx 才算恢复**」——
所以这中间它会**继续**报「掉线」，直到引擎真的开始服务。

这是**对的**：503 的那一段时间里引擎确实**还没在服务**，
L2 判定和解释确实还是停用的。实测记录：

```
checks=3, failures=3, state=offline, detail=服务返回 HTTP 503。
checks=4, failures=3, state=healthy, detail=已连通（HTTP 200）。
```

⚠️ 别把这当成 bug —— 它只是说明「引擎起来」到「引擎能用」之间有一段窗口。
看到连续的 503 告警时，多等一个心跳周期就好。

### 3.4 ⚠️ 只告警，**不**自动拉起

```yaml
llm:
  watchdog:
    enabled: true
    interval: 30
    timeout: 8
```

⚠️ 配置里那个 `llm.watchdog.restart` 段**保留但被忽略** ——
它留着是为了不打断已有配置，但哨兵**不会**用它拉起引擎。
（真写了 `restart.enabled: true`，哨兵会记一条日志提醒：
「该配置项已被忽略，请手动拉起引擎。」）

**为什么砍掉自动重拉**：

* 用户的要求是明确的：「**不要尝试自动拉起，保持只读监控的边界**」；
* 哨兵**替用户启动一个进程**就不再是只读监控了；
* 引擎启动要吃显存 —— 在用户正被别的东西占满显存的时候自动拉它，
  只会把机器拖得更垮。

所以哨兵只**说**（「引擎掉了，你手动拉一下」），**不动手**。

### 3.5 只盯本机

`build_watchdog()` 会用 `is_local_endpoint()` 判断地址：

* 本机 → 建看门狗；
* 云端 → **不建** —— 那是服务商的事，
  哨兵既不该替它喊，也不该定时去戳第三方的服务器。

## 4. 任务三：时间盒（Time-Boxing）

### 4.1 它拦的是什么

《Agent 跑偏警示录》里的根因：

> 「一个子任务能吃掉整轮」——
> 下载依赖、修测试、给即将删掉的引擎装权重，
> 一件事干到天荒地老，主任务却一动没动。

而 v3.2.1 之前的哨兵**只认「行为特征」**：
删文件（红线）、读同一个文件（死循环）、偏离目标（意图漂移）。
「**一直在同一件事上磨**」这件事，**一次都没被检测过** ——
它既不删东西，又不偏离目标，看起来「很安全」。

### 4.2 判定逻辑

哨兵给「同一类操作」开一个**时间盒**（默认 15 分钟）。
只要 Agent 在盒子里**反复做同一件事**，时间用完 → 判定跑偏。

| 桶 | 触发条件 | 例子 |
| --- | --- | --- |
| **同一条命令**（不限类别） | 同一条命令 ≥ 3 次，且首次到现在 ≥ 15 分钟 | 同一个 pytest 用例反复重跑 |
| **同一类操作**（只盯配置列出的类别） | 同类操作 ≥ 3 次，且首次到现在 ≥ 15 分钟 | 换着花样跑不同的测试，但**全是测试** |

默认盯的类别：`dependency`（装依赖 / 下载）、`test`（跑测试）。

⚠️ **`edit`（改代码）默认不盯** ——
「一直在改代码」是**正常**的，盯它只会制造噪音。

⚠️ 「同一条命令」与「同一类操作」常常同时成立 ——
那是**一件事**，所以只报**一次**警，不刷屏。

⚠️ `git status` 这类**廉价查看**命令**不计入**重复统计
（Agent 反复看状态是正常的）。

### 4.3 告警长什么样

```
[CRITICAL] 严重跑偏：同一条命令「pip install -r requirements.txt」重复了 3 次，
已经耗时 15.0 分钟（时间盒 15.0 分钟）。子任务在吃掉整轮 —— 先停一停，确认它还在做主线任务。
```

* 判定名 `TIMEBOX`，规则 ID `timebox_exceeded`；
* 触发标记 `timebox_exceeded` —— 同样要在 Webhook 的 `triggers` 里加上；
* 走 L2 解释（引擎还在的话）—— 引擎也掉线了就只剩规则层的原文。

### 4.4 守护者联动：**跟着守护者的武装状态走**

```yaml
rules:
  timebox:
    enabled: true
    window_minutes: 15
    min_repeats: 3
    categories: ["dependency", "test"]
    guardian_suspend: null      # ← 默认留空 = 跟着守护者走
```

`guardian_suspend` 是**三态**：

| 取值 | 行为 |
| --- | --- |
| `null`（**默认**） | **跟着守护者的武装状态走** —— 守护者武装着（`enabled` 且 `intervention_mode: guardian`）才挂起 |
| `true` | 只要**有**守护者就挂起 |
| `false` | **永远不挂**，只告警 |

**为什么默认跟着守护者走**：守护者本身就是「用户授权我去动手」的开关 ——
用户把 `intervention_mode` 设成 `guardian`，
就等于说了「该拦的给我拦」。
「超时死磕」也是一种该拦的情况，
所以不必再要用户配一遍。

挂起是**可逆**的（看板上一键恢复）。

## 5. 任务四：防误杀

### 5.1 后果要说清楚

Defender 的**机器学习**启发式会把单文件 exe 判成木马
（v3.2.0 发布当夜就被隔离过一次，`Trojan:Win32/Bearfoos.A!ml`）。

**v3.3.0 起不自启了，所以后果也变了**：

> **手动双击 exe 被拦** ——
> 弹 Defender 警告，用户以为 exe 坏了。

### 5.2 解法：把 exe 所在目录加白名单

* `_构建与发布/scripts/add_defender_exclusion.ps1`
  —— 把**打包目录**加进 Defender 排除项。
  **需要管理员权限**；非管理员时脚本会给出
  「怎么用管理员身份重开」的具体步骤，而不是甩一屏红字。
* `build_exe.py` 打包完会**显眼地**提醒加排除项。
* README 有**【防误杀指南】**。

### 5.3 ⚠️ 仍然要靠用户

哨兵**不会**自己去改 Defender 设置 ——
那是系统级安全设置，**必须**由用户在管理员权限下确认。
哨兵能做的只有：**把这件事说清楚，并在打包时提醒**。

### 7.1.1 打包版 exe 的实拍（不是模拟 —— 真的把引擎杀了）

> 证据：[`assets/v330-packaged-watchdog.txt`](../assets/v330-packaged-watchdog.txt)

跑**打包版 exe**（`_构建与发布/dist/sentinel.exe`），然后
**真的结束掉监听 8888 的那个引擎进程**（模拟显存吃紧 / 被人手滑关掉）：

```
[SENTINEL] 雷达模式：只扫描你机器上已有的 Agent 会话日志，不监控任何进程。
[SENTINEL] 引擎心跳看门狗已启动（每 30 秒探一次 http://127.0.0.1:8888/v1）。
[看板已就绪] 请访问 http://127.0.0.1:8000 查看实时审计。
Sentinel v3.3.0 is ready.
[CRITICAL] NInfer 引擎已掉线！L2 判定和解释已停用！（地址 http://127.0.0.1:8888/v1，最近一次心跳：连不上（服务没启动？））
[OK] NInfer 引擎已恢复！L2 判定和解释重新可用。（地址 http://127.0.0.1:8888/v1，探活耗时 1 毫秒）
```

⚠️ 这一段里**哨兵自己什么都没做**：

* 它没有自动拉起引擎（用户手动拉的，配置里的 `restart` 段被**忽略**）；
* 掉线与恢复**都是心跳自己发现的**；
* 终端里**没有**「守护模式」字样 —— v3.3.0 终版里**已经没有任何守护模式**。

⚠️ 一个实机细节：引擎刚重启时会先回 `HTTP 503`（模型还在加载），
看门狗会**继续**报掉线，直到回 `200` 才转「已恢复」——
那段时间它确实还没在服务，报掉线是**对的**（见 §3.3.1）。

本仓库**没有配置 remote**，标签只存在于本地。

### 8.3 ⚠️ 打包目录里的配置是旧版（实机踩到，已处理）

打包 v3.3.0 时发现：`_构建与发布/dist/config/config.yaml` 里躺着一份
**Ollama 时代**的旧配置（`localhost:11434` / `qwen2.5:7b`）。

而打包版 exe 的配置查找顺序里，`<exe 目录>/config/config.yaml`
**优先级最高** —— 那正是用户在设置页里改出来、运行时会写回的那份。
于是打包版一直去找一个**已经不存在的引擎**，
界面上的「引擎连不上」提示还会指向**错误的引擎**。

处理：

1. 本机已把仓库配置同步过去（旧文件备份为 `config.yaml.bak-<时间戳>`）；
2. `build_exe.py` 新增 **旧配置告警** ——
   打包时如果打包目录的配置与仓库里的 `llm.base_url` 不一致，
   就**显眼地**提醒，并给出复制命令
   （同时提醒：那份通常是**设置页写回**的，复制前先确认要不要丢掉那些改动）。

⚠️ 这条**没有**改产品行为 —— `<exe 目录>` 优先是**设计**
（用户在设置页改的就是那份），这里只是把「它会盖住一切」这件事**说清楚**。

## 9. 尚未解决的事（如实记录）

1. **Defender 误报仍未根治** ——
   哨兵**不能**替用户改系统级安全设置，
   只能把「怎么改」说清楚并在打包时提醒。
   用户不设排除项，**手动双击 exe 仍会被拦**。
2. **时间盒看不到「一条命令跑了 30 分钟」** ——
   哨兵只读日志流，看不到进程的运行时间。
   这类长耗时操作靠「同一条命令重复出现」兜底，
   而**只跑一次**的长命令**兜不住**。
3. **v3.2.0 第一轮演习收尾卡死的根因仍未查清** ——
   看门狗只留了线程栈证据。
4. **引擎掉线的「静默」只解决了一半** ——
   哨兵能告诉你**掉了**，
   但**为什么掉**（显存不足？模型文件被占？）仍然查不出来。
5. **引擎为什么会自己死，暂时没查清** ——
   v3.3.0 发布期间它掉了**两次**
   （一次是演示脚本拔的，一次是**自己掉的**）。
   看门狗只能告诉你「掉了」和「什么时候掉的」，
   死因仍然要靠引擎自己的日志。
6. **旧版残留无法由哨兵自动清理** ——
   这是**故意的**（R7）：哨兵只检测、只提示，
   真删要用户自己跑 `remove_startup_residue.ps1`。
